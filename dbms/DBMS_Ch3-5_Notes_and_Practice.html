Part 1, Chapter 3: Relational Database Design

3.1 Design guidelines for relational schemas

GuidelineWhat it says
1. SemanticsEach tuple represents one entity or one relationship instance. Do not mix attributes of different entities (EMPLOYEE, DEPARTMENT, PROJECT) in one relation; refer to other entities only through foreign keys. The schema should be easy to explain relation by relation.
2. No redundancy / update anomaliesRedundant storage wastes space and causes anomalies. Design so there are no insertion, deletion or modification anomalies (or note them for applications).
3. Few NULLsAvoid attributes that are often NULL; move them to a separate relation with the primary key. NULL can mean: not applicable, unknown, or known but unavailable.
4. No spurious tuplesRelations must satisfy the lossless join condition: a natural join of the decomposed relations must not create tuples that were not in the original.
Update anomalies, using EMP_PROJ(Emp#, Proj#, Ename, Pname, No_hours):
  • Modification: renaming project P1 must be done in every row of its 100 employees.
  • Insertion: a project cannot be stored until some employee is assigned to it (and vice versa).
  • Deletion: deleting a project deletes its employees; deleting the only employee on a project loses the project.

Functional dependencies (FDs)

  • X → Y: X functionally determines Y if any two tuples that agree on X also agree on Y. X is the determinant. Example: EmpNum → {EmpEmail, EmpFname, EmpLname}; {SSN, PNUMBER} → HOURS.
  • FDs come from the meaning of the data, not from one table instance.
  • Full FD: Y → Z where removing any attribute from Y breaks it ({SSN, PNUMBER} → HOURS). Partial dependency: a non-key attribute depends on part of a composite key ({SSN, PNUMBER} → ENAME, because SSN → ENAME).
  • Transitive dependency: A → B and B → C give A → C, with C depending on A through B (EmpNum → DeptNum → DeptName).
  • Prime attribute: belongs to some candidate key. Superkey: any attribute set whose closure is all attributes; a candidate key is a minimal superkey.
Armstrong's inference rulesStatement
IR1 ReflexivityIf Y ⊆ X then X → Y
IR2 AugmentationIf X → Y then XZ → YZ
IR3 TransitivityIf X → Y and Y → Z then X → Z
DecompositionIf X → YZ then X → Y and X → Z
UnionIf X → Y and X → Z then X → YZ
PseudotransitivityIf X → Y and WY → Z then WX → Z
Closure F+: all FDs that can be inferred from F. Attribute closure X+ (used to find keys): start with X; repeatedly, for every FD L → R with L ⊆ X+, add R; stop when nothing changes. X is a superkey if X+ contains all attributes.
Finding candidate keys quickly: attributes that never appear on any right side must be in every key; start from them and add attributes until the closure is everything.

3.2 Normalization: 1NF, 2NF, 3NF

Normalization decomposes "bad" relations into smaller ones of higher normal forms. Aim: every non-key attribute depends on the key, the whole key, and nothing but the key. BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF (every BCNF relation is in 3NF, and so on, but not the other way).

FormRuleRemovesFix
1NFAll values are atomic and single-valued: no multivalued, composite or nested attributesRepeating groupsMove the multivalued attribute to a new relation with the key (EmpNum, EmpDegree)
2NF1NF and every non-prime attribute is fully dependent on every candidate keyPartial dependenciesMove the attributes that depend on part of the key, with that part, to a new relation
3NF2NF and no non-prime attribute is transitively dependent on a key. Formal test: for every X → A, X is a superkey or A is primeTransitive dependenciesMove the transitively dependent attributes with their determinant (Employee(EmpNum, EmpName, DeptNum) + Dept(DeptNum, DeptName))
Class examples: InvLine(InvNum, LineNum, ProdNum, Qty, InvDate) is only 1NF because InvNum → InvDate is partial; split into InvLine(InvNum, LineNum, ProdNum, Qty) and Invoice(InvNum, InvDate). EmployeeDept(ssn, ename, bdate, address, dnumber, dname) is 2NF but not 3NF because ssn → dnumber → dname.

Multivalued dependency X →→ Y: for one X value there is a set of Y values independent of the other attributes, so every combination must be stored (redundancy).
Lossless decomposition of R into R1 and R2: lossless if R1 ∩ R2 → R1 or R1 ∩ R2 → R2 (the common attributes are a key of one side). Dependency preserving: every FD can be checked inside one of the new relations.
Key facts from the slides: any relation can be decomposed losslessly into BCNF, but dependency preservation is not guaranteed; any relation can be decomposed losslessly and dependency-preserving into 3NF. So 3NF is sometimes preferred. OLTP systems aim for BCNF and may denormalize for performance.

BCNF decomposition algorithm

  1. Find an FD X → Y in R that violates BCNF (X is not a superkey).
  2. Replace R by R1 = X ∪ Y and R2 = R − (Y − X).
  3. Repeat on each new relation until all are in BCNF. The result is always lossless.

3.4 Database design and implementation process

  1. Requirements collection and analysis: data and functional requirements from users.
  2. Conceptual design: ER/EER model, independent of any DBMS.
  3. Choice of DBMS: technical, economic and organisational factors.
  4. Logical design (data model mapping): ER/EER to relational schemas, then normalization.
  5. Physical design: storage structures, indexes, access paths, performance tuning.
  6. Implementation and tuning: DDL to create schemas, load data, write application programs, monitor and tune.

Part 1, Chapter 4: Indexing, Hashing, Query Processing and Optimization

4.1 Indexing: basic concepts and ordered indices

  • An index is an auxiliary file of (search-key, pointer) entries that speeds up lookups. Measured by access time, insertion time, deletion time and space overhead.
  • Search key: attribute(s) used to look up records (not necessarily the primary key).
Index typeMeaning
Primary (clustering) indexOn the attribute by which the data file is physically ordered. Usually sparse. Only one per file.
Secondary (non-clustering) indexOn an attribute the file is not ordered by. Must be dense; for non-key attributes it points to a bucket of record pointers. Many per file allowed.
Dense indexAn entry for every search-key value (every record). Faster lookups, more space.
Sparse indexEntries for only some values (typically one per block, the block's first key). Find the largest entry ≤ the key, then scan the block. Less space; needs an ordered file.
Multilevel indexWhen the index itself is too large, build a sparse index (outer) on the index (inner), and so on, until the top level fits in one block. Search cost ≈ number of levels.

B-trees and B+-trees (search, insert, delete)

B-tree of order m (max m children per node): every node has at most m − 1 keys; every node except the root has at least ⌈m/2⌉ children (⌈m/2⌉ − 1 keys); the root has at least 2 children unless it is a leaf; all leaves are at the same level; keys inside a node are sorted.
B+-tree: all data pointers are in the leaves; internal nodes only guide the search; leaves are linked left to right, which makes range queries fast. Most DBMS indexes are B+-trees.
OperationSteps
SearchFrom the root, follow the child pointer whose key range contains the key; repeat to a leaf. Cost = height ≈ log⌈m/2⌉(n).
InsertInsert into the correct leaf in sorted order. If it overflows (m keys), split: the middle key moves up to the parent, left and right halves become two nodes. A split can cascade up; splitting the root adds a level (the tree grows at the top).
DeleteRemove the key (an internal key is first replaced by its in-order predecessor or successor). If a node underflows: borrow from a sibling with spare keys (through the parent), else merge with a sibling, pulling the separating key down from the parent. A merge can cascade; if the root becomes empty, the tree loses a level.

4.2 Hashing and comparison with ordered indexing

  • Static hashing: a hash function h(K) maps a key to one of a fixed number of buckets (e.g. h(K) = K mod M). Overflow is handled by chaining overflow buckets (or open addressing). Problem: the number of buckets is fixed, so the file grows badly.
  • Dynamic hashing (extendible / linear hashing): the number of buckets grows and shrinks with the data, e.g. extendible hashing uses a directory of 2d pointers and doubles it when a bucket splits.
  • A good hash function is uniform (each bucket gets about the same number of keys) and random (independent of key patterns).
Ordered indexing (B+-tree)Hashing
Good for range queries (salary BETWEEN 20000 AND 30000) and ordered outputBest for equality lookups (dno = 5); usually 1 block access
Search cost log of n, grows slowlyConstant expected cost, but worse with many collisions
Handles growth gracefully (splits)Static hashing needs reorganisation as the file grows
Supports prefix and sorted scansNo order: a range query must scan every bucket

4.3 Query processing

Steps: SQL query → scanner, parser and validator (syntax, names) → intermediate form (query tree / relational algebra) → query optimizer (chooses an execution plan using statistics from the catalog) → query code generator → runtime database processor executes the plan → result.
A query block is one SELECT-FROM-WHERE (with GROUP BY / HAVING); nested queries become separate blocks. Example: the inner block MAX(SALARY) of DNO 5 is evaluated to a constant C, then πLNAME, FNAME(σSALARY>C(EMPLOYEE)).

Measures of query cost

Cost components: access cost to secondary storage (block transfers, the dominant one), storage cost of intermediate files, computation (CPU) cost, memory usage cost, communication cost. Catalog statistics used: number of records r, record size R, blocks b, blocking factor bfr = ⌊block size / R⌋ so b = ⌈r / bfr⌉, index levels x, first-level index blocks bI1, distinct values d, selectivity sl, selection cardinality s = sl × r.

For a single condition, use the access path if one exists, else S1. For conjunctive conditions, the optimizer chooses the path that retrieves the fewest records. Disjunctive (OR) conditions need an access path on every condition, otherwise a linear search.

Algorithm for PROJECT

πlist(R): if the list contains a key of R, just take those attributes from each tuple. If not, duplicates must be removed, by sorting (duplicates become adjacent) or hashing (duplicates fall in the same bucket).

4.4 Query optimization

  • Query tree: relational algebra expression as a tree, relations at the leaves, operations at internal nodes, executed bottom-up. Query graph: relational calculus form, no order of operations, one graph per query.
  • Heuristic optimization: main rule is to apply operations that reduce intermediate result size first: do SELECT and PROJECT before JOIN.
#Transformation rule
1Cascade of σ: σc1 AND c2 AND … cn(R) = σc1(σc2(…σcn(R)))
2Commutativity of σ: σc1(σc2(R)) = σc2(σc1(R))
3Cascade of π: πL1(πL2(…(R))) = πL1(R)
4Commuting σ with π: if c uses only attributes in the list, πA(σc(R)) = σc(πA(R))
5Commutativity of ⋈ and ×: R ⋈ S = S ⋈ R; R × S = S × R
6Commuting σ with ⋈: σc(R ⋈ S) = σc(R) ⋈ S if c uses only R; σc1 AND c2(R ⋈ S) = σc1(R) ⋈ σc2(S)
7Commuting π with ⋈: πL(R ⋈c S) = πA…(R) ⋈c πB…(S) (add join attributes if they are not in L, then a final π)
8∪ and ∩ are commutative; − is not
9⋈, ×, ∪, ∩ are associative: (R θ S) θ T = R θ (S θ T)
10σ commutes with ∪, ∩, −: σc(R θ S) = σc(R) θ σc(S)
11π commutes with ∪: πL(R ∪ S) = πL(R) ∪ πL(S)
12σ followed by × becomes a join: σc(R × S) = R ⋈c S
Heuristic optimization steps (outline of the algorithm): (1) break conjunctive selections into cascades (rule 1); (2) push each σ as far down the tree as possible (rules 2, 4, 6, 10); (3) put the leaf relations with the most restrictive selections first (rule 9); (4) combine × with a following σ into a ⋈ (rule 12); (5) push π down, keeping only needed attributes (rules 3, 4, 7, 11); (6) identify subtrees that can be executed by one algorithm.
Estimating statistics: equality on attribute A with d distinct values: sl = 1/d, s = r/d. Join size ≈ js × |R| × |S| with join selectivity js = 1/max(dA(R), dB(S)).
Choice of evaluation plan: a plan = query tree + the access method for each relation + the algorithm for each operator. Cost-based optimization estimates each candidate plan's cost and picks the cheapest. Results are passed by materialized evaluation (stored as temporary relations) or pipelined evaluation (each tuple forwarded straight to the next operator).

Part 1, Chapter 5: Transactions, Concurrency Control and Recovery

5.1 Transaction concepts

  • A transaction is a unit of program execution that accesses and possibly updates data, e.g. transfer ₹50 from A to B: read(A); A := A − 50; write(A); read(B); B := B + 50; write(B).
  • Transaction states: Active (executing) → Partially committed (last statement done) → Committed; or Active / Partially committed → Failed → Aborted (rolled back; then restart or kill).
ACID propertyMeaningWho ensures it
AtomicityAll operations happen or none (no half transfer)Recovery system (log / shadow copy)
ConsistencyA correct transaction takes the DB from one consistent state to another (A + B unchanged)Programmer + integrity constraints
IsolationConcurrent transactions do not see each other's intermediate results; result equals some serial orderConcurrency control
DurabilityOnce committed, updates survive failuresRecovery system

Shadow-database scheme: a db_pointer points to the current copy; a transaction updates a new copy, and commit switches the pointer after writing the copy to disk. Gives atomicity and durability, but copying the whole database is expensive.

Why concurrent execution: better CPU and disk utilisation (throughput) and lower average response time. Schedule: the order in which operations of concurrent transactions execute. Serial schedule: one transaction completely after another (always consistent).

Serializability

  • Two operations conflict if they belong to different transactions, access the same item, and at least one is a write (R-W, W-R, W-W).
  • Conflict serializable: can be turned into a serial schedule by swapping adjacent non-conflicting operations. Test: precedence graph, one node per transaction, edge Ti → Tj if an operation of Ti conflicts with a later operation of Tj. No cycle = conflict serializable; a topological order gives the equivalent serial schedule.
  • View serializable: view-equivalent to a serial schedule (same initial reads, same reads-from, same final writes). Every conflict-serializable schedule is view serializable; a view-serializable schedule that is not conflict serializable has blind writes. Testing view serializability is NP-complete.

Recoverability

TypeCondition
RecoverableIf Tj reads data written by Ti, Ti commits before Tj commits
Cascading rollbackOne failure forces rollback of many transactions that read its uncommitted data
CascadelessTj reads data written by Ti only after Ti commits (no dirty reads). Every cascadeless schedule is recoverable.
StrictNo read or write of an item until the last transaction that wrote it has committed or aborted

5.2 Concurrency control

Lock-based protocols

  • Shared lock (S): read only (lock-S). Exclusive lock (X): read and write (lock-X). Compatibility: S with S is allowed; any combination with X is not.
  • Pitfalls: deadlock (each waits for the other) and starvation (a transaction keeps waiting, e.g. for X while others keep getting S).
Two-Phase Locking (2PL): Growing phase (acquire locks, release none) then shrinking phase (release locks, acquire none). The point of the last lock is the lock point; transactions are serializable in lock-point order. 2PL guarantees conflict serializability but not freedom from deadlock or cascading rollback.
Strict 2PL: hold all X locks until commit / abort (avoids cascading rollbacks). Rigorous 2PL: hold all locks until commit (serializable in commit order).
Lock conversions: upgrade S → X only in the growing phase; downgrade X → S only in the shrinking phase.
Automatic acquisition: on read(D) the system issues lock-S if no lock is held; on write(D) it issues lock-X (upgrading S if needed); all locks are released after commit or abort.

Timestamp-based protocol

Each transaction gets TS(Ti) on entry (older = smaller). Each item Q keeps W-timestamp(Q) and R-timestamp(Q), the largest timestamps of successful writes and reads. Conflicting operations must run in timestamp order.

Ti issuesCheckAction
read(Q)TS(Ti) < W-timestamp(Q)Reject (value already overwritten), roll back Ti
TS(Ti) ≥ W-timestamp(Q)Execute; R-timestamp(Q) = max(R-timestamp(Q), TS(Ti))
write(Q)TS(Ti) < R-timestamp(Q)Reject (a younger transaction already read Q), roll back Ti
TS(Ti) < W-timestamp(Q)Reject (obsolete write), roll back Ti; Thomas' write rule: just ignore the write instead
OtherwiseExecute; W-timestamp(Q) = TS(Ti)

Timestamp ordering guarantees conflict serializability and freedom from deadlock (nobody waits), but may starve long transactions and can give non-recoverable schedules unless extended.

Validation-based (optimistic) protocol

Each transaction runs in three phases: Read (work on local copies), Validation (check it does not violate serializability), Write (apply updates if validation passes, else roll back). Timestamps Start(Ti), Validation(Ti), Finish(Ti); TS(Ti) = Validation(Ti). Tj passes if for every older Ti: Finish(Ti) < Start(Tj), or Start(Tj) < Finish(Ti) < Validation(Tj) and Ti's write set does not intersect Tj's read set. Good when conflicts are rare.

Deadlock handling

ApproachHow
PreventionLock all items before starting (pre-declaration), or impose a fixed order on items; or use timestamps:
Wait-die (non-preemptive): an older requester waits for a younger holder; a younger requester dies (rolled back, restarts with the same timestamp).
Wound-wait (preemptive): an older requester wounds (rolls back) the younger holder; a younger requester waits. Fewer rollbacks than wait-die.
Timeout-based: a transaction that waits longer than a limit is rolled back.
DetectionBuild a wait-for graph (edge Ti → Tj if Ti waits for an item held by Tj); a cycle means deadlock. Run the check periodically.
RecoveryChoose a victim with minimum cost, roll it back (total or partial), and avoid starvation by counting rollbacks in the cost.

5.3 Recovery system

  • Failure classification: transaction failure (logical error such as bad input; system error such as deadlock), system crash (power or OS failure; main memory lost, disk safe; fail-stop assumption), disk failure (head crash; recover from backups / archives).
  • Storage: volatile (main memory, lost on crash), non-volatile (disk), stable storage (survives everything; approximated by multiple copies on separate disks).
  • Recovery and atomicity: before changing the database, write information describing the change to stable storage (the log), so the system can undo or redo after a failure.
Log records: <Ti start>, <Ti, X, V1, V2> (old value V1, new value V2), <Ti commit>. The log record is written before the database is changed (write-ahead logging).
Deferred database modificationImmediate database modification
When the DB is updatedOnly after partial commit; log holds <Ti, X, V> (new value only)Updates of uncommitted transactions may reach the DB; log holds old and new values
After a crashredo(Ti) if both <Ti start> and <Ti commit> are in the log; otherwise ignore Tiundo(Ti) (restore old values, backwards) if <start> but no <commit>; redo(Ti) (set new values, forwards) if both are present. Undo first, then redo.
Needs undo?No (NO-UNDO / REDO)Yes (UNDO / REDO)

Checkpoints: periodically output all log records and modified buffer blocks to stable storage, then write <checkpoint L> (L = active transactions). After a crash, scan back to the last checkpoint: transactions that committed before it need nothing; those that committed after it are redone; those still uncommitted are undone. This avoids scanning the whole log.

Shadow paging: two page tables, the current page table (changes during the transaction) and the shadow page table (saved, never changed). A write copies the page to a free block and points the current table at it. Commit: flush the pages, write the current page table to disk, then atomically switch the root pointer to it. Abort / crash: keep the shadow table, so no undo and no redo are needed. Drawbacks: copying the table is costly, data gets fragmented, garbage pages need collection, and it is hard to extend to concurrent transactions.

Part 2: Practice questions with answers

Chapter 3

Q1. R(A, B, C, D, E) with F = {A → B, B → C, CD → E}. Find A+, the candidate key(s) and the highest normal form. Decompose to BCNF.
A+ = {A, B, C}. A and D never appear on a right side, so both are in every key: (AD)+ = {A, D, B, C, E} = all attributes, so the only candidate key is AD.
Normal form: A → B is a partial dependency (A is part of key AD, B is non-prime), so R is only in 1NF.
BCNF decomposition: A → B violates BCNF → R1(A, B), rest (A, C, D, E). In the rest, A → C holds (A → B → C) and violates BCNF → R2(A, C), rest (A, D, E). CD → E is lost there; AD → E holds with AD the key → R3(A, D, E). Result: R1(A, B), R2(A, C), R3(A, D, E), all in BCNF and lossless. (B → C and CD → E are not preserved, which is the usual BCNF trade-off. A 3NF dependency-preserving design would be R1(A, B), R2(B, C), R3(C, D, E), R4(A, D).)
Q2. R(A, B, C, D) with F = {AB → C, C → D, D → A}. Find all candidate keys. Is R in 3NF? In BCNF?
B is never on a right side, so it is in every key. (AB)+ = ABCD, (BC)+ = BCDA, (BD)+ = BDAC. Candidate keys: AB, BC, BD, so all of A, B, C, D are prime.
3NF: yes. For AB → C the left side is a key; for C → D and D → A the right sides are prime attributes.
BCNF: no. C → D and D → A have determinants (C, D) that are not superkeys.
Q3. Using Armstrong's rules, prove that if A → B and BC → D, then AC → D.
A → B (given) → augment with C: AC → BC (IR2). BC → D (given). By transitivity (IR3), AC → D. This is the pseudotransitivity rule.
Q4. Employee(EmpNum, EmpName, DeptNum, DeptName). Which normal form is it in? Normalize it.
Key: EmpNum (single attribute, so no partial dependency) → 2NF. But EmpNum → DeptNum → DeptName is a transitive dependency of a non-key attribute, so it is not 3NF (and not BCNF, since DeptNum is not a key). Decompose into Employee(EmpNum, EmpName, DeptNum) and Department(DeptNum, DeptName). This is lossless (DeptNum is the key of Department) and both relations are in BCNF.
Q5. Teaching(student_no, course_no, instr_no): each instructor teaches one course; a student taking a course has one instructor. Normal form? Decompose.
FDs: {student_no, course_no} → instr_no, instr_no → course_no. Keys: {student_no, course_no} and {student_no, instr_no}, so all attributes are prime → 3NF. instr_no → course_no has a non-superkey determinant → not BCNF. Decompose on it: (instr_no, course_no) and (student_no, instr_no): lossless, in BCNF, but {student_no, course_no} → instr_no is no longer preserved.
Q6. Emp(Employee, Skill, Language), key = all three. Each employee has several skills and speaks several languages independently. Normal form? Fix it.
All attributes form the only key, so it is in BCNF. But Employee →→ Skill and Employee →→ Language are independent multivalued dependencies, so every skill must be repeated with every language: not in 4NF. Decompose into (Employee, Skill) and (Employee, Language).
Q7. R(A, B, C) with A → B is decomposed into R1(A, B) and R2(A, C). Lossless?
R1 ∩ R2 = {A}, and A → B means A is a key of R1 (A → AB). So the decomposition is lossless. Splitting into (A, B) and (B, C) instead would be lossy unless B → A or B → C held.
Q8. Normalize this unnormalised table: Student(RollNo, Name, Phones{multivalued}, CourseID, CourseName, Marks), key {RollNo, CourseID}; RollNo → Name, CourseID → CourseName.
1NF: move the multivalued phones out: StudentPhone(RollNo, Phone). 2NF: remove partial dependencies on the composite key: Student(RollNo, Name), Course(CourseID, CourseName), Result(RollNo, CourseID, Marks). Each table now has every non-key attribute depending on the whole key and nothing else, so all are in 3NF / BCNF.

Q10. A file has 10,000 records sorted on the key, blocking factor 5. Compare block accesses to find one record by key using (a) linear search, (b) binary search, (c) a 3-level primary index.
b = ⌈10000 / 5⌉ = 2000 blocks. (a) Linear: b/2 = 1000 on average (2000 worst case). (b) Binary: ⌈log2 2000⌉ = 11. (c) Primary index: x + 1 = 3 + 1 = 4.
Q11. Static hashing with h(K) = K mod 7, bucket capacity 2. Insert 15, 22, 8, 29, 3.
15 mod 7 = 1, 22 mod 7 = 1 → bucket 1 = [15, 22] (full). 8 mod 7 = 1 → overflow bucket chained to 1: [8]. 29 mod 7 = 1 → overflow: [8, 29]. 3 mod 7 = 3 → bucket 3 = [3]. Bucket 1 is skewed, showing why a uniform hash function matters, and why dynamic hashing grows better.
Q12. Dense vs sparse index: a data file sorted on RollNo has 300 records in 30 blocks. How many entries does each index need?
Dense: one entry per record = 300. Sparse: one entry per block = 30. Sparse needs the file sorted on the search key; a secondary index on an unsorted attribute must be dense.
Q13. Optimize: SELECT LNAME FROM EMPLOYEE, WORKS_ON, PROJECT WHERE PNAME = 'Aquarius' AND PNUMBER = PNO AND ESSN = SSN AND BDATE > '1957-12-31'.

Q15. Is S: R1(A), R2(A), R1(B), R2(B), R3(B), W1(A), W2(B) conflict serializable?
Conflicts: R2(A) before W1(A) → T2 → T1; R1(B) before W2(B) → T1 → T2; R3(B) before W2(B) → T3 → T2. The graph has the cycle T1 → T2 → T1, so S is not conflict serializable.

Q18. T2 reads X written by T1, then T2 commits, then T1 aborts. Is the schedule recoverable? How do you make it cascadeless?
Not recoverable: T2 read T1's dirty value and committed first, so T2 cannot be rolled back when T1 aborts. It becomes recoverable if T2 commits only after T1 commits; it becomes cascadeless if T2 reads X only after T1 commits (strict 2PL achieves this).
Q19. TS(T1) = 10, TS(T2) = 20, and initially R-TS(Q) = W-TS(Q) = 0. Apply timestamp ordering to: read2(Q), write1(Q), write2(Q).
read2(Q): 20 ≥ W-TS 0 → OK, R-TS(Q) = 20. write1(Q): TS(T1) = 10 < R-TS(Q) = 20 → rejected, T1 rolled back (and restarted with a new, larger timestamp). write2(Q): 20 ≥ R-TS 20 and ≥ W-TS 0 → OK, W-TS(Q) = 20.
(If instead write2(Q) came first and then write1(Q) with no read in between, TS(T1) < W-TS(Q) = 20, so basic TO rolls T1 back, but Thomas' write rule just ignores the obsolete write.)

Q21. Show that this schedule follows 2PL: lock-X(A); read(A); A := A − 50; write(A); lock-X(B); unlock(A); read(B); B := B + 50; write(B); unlock(B). Is it strict 2PL?
All locks (A, then B) are acquired before the first unlock(A), so it has a growing phase then a shrinking phase: 2PL, yes. The lock point is lock-X(B). It is not strict 2PL, because the X lock on A is released before commit, so another transaction could read the uncommitted A (risk of cascading rollback).
Q22. Immediate modification log at crash: <T0 start>, <T0, A, 1000, 950>, <T0, B, 2000, 2050>, <T0 commit>, <T1 start>, <T1, C, 700, 600>. What does recovery do?
T1 has a start but no commit → undo(T1): C = 700 (old value). T0 has start and commit → redo(T0): A = 950, B = 2050. Undo first, then redo. Final: A = 950, B = 2050, C = 700.
With deferred modification, T1's write never reached the DB, so only redo(T0) is needed.
Q23. A crash happens after: T1 commits, <checkpoint {T2, T3}>, T2 commits, T4 starts, T3 still active. Which transactions are redone or undone?
T1 committed before the checkpoint → nothing to do. T2 committed after the checkpoint → redo. T3 (in the checkpoint list) and T4 (started after) never committed → undo.
Q24. Draw the wait-for graph: T1 waits for T2, T2 waits for T3, T3 waits for T1, T4 waits for T2. Is there a deadlock? How is it resolved?
Edges T1 → T2 → T3 → T1 form a cycle, so T1, T2 and T3 are deadlocked (T4 only waits). Pick a victim with the least cost (for example the one that has done the least work or holds the fewest locks) among T1, T2, T3, roll it back, and count its rollbacks to avoid starvation.
