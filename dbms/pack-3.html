3.1

Why design matters: guidelines for a good relational schema

A relation schema can be built in many ways from the same facts. Some designs store every fact once; others repeat facts, force NULLs, or lose information when they are split. The four informal guidelines used to judge a design are:

  • Clear semantics: each relation should describe one entity or one relationship. Do not mix a student, a course and a teacher in one table.
  • Reduce redundant data: the same fact should not be stored in many rows, because every copy must be changed together (update anomaly) and wastes disk space.
  • Avoid NULLs where possible: attributes that are often NULL waste space, make joins and aggregates ambiguous, and usually belong in a separate relation.
  • Avoid spurious tuples: when a relation is decomposed and joined back, the result must be exactly the original, with no extra rows. This is the lossless-join property.
3.2

The three anomalies, shown on one table

Suppose a college keeps everything in one table, STUDENT_COURSE (key: Student_ID + Course):

Student_IDStudent_NameCourseTeacherTeacher_Phone

  • Redundancy: Prof. Sharma's phone number is stored once for every student of DBMS.
  • Update anomaly: if the phone number changes, every DBMS row must be updated; missing one leaves two different numbers for the same teacher. It arises from redundancy.
  • Deletion anomaly: if Sneha drops Java and her row is deleted, we also lose the fact that Prof. Patil exists and his phone number. A deletion removes unrelated data.
  • Insertion anomaly: a new teacher cannot be recorded until a student enrols, because the key (Student_ID, Course) cannot be NULL. A fact cannot be stored for lack of other data.
3.3

What normalisation is, and why we do it

Normalisation is a step-by-step process of decomposing a relation into smaller relations with fewer attributes so that every fact is stored in one place. It is guided by normal forms, which are conditions a relation must satisfy. The normal forms apply to individual relations; a relation is "in" a normal form if it meets that form's condition.

  • Aims: minimise redundancy; remove insertion, update and deletion anomalies; keep the structure flexible so new rows and values can be added without reorganising; make queries easier to write.
  • Rule of the process: the decomposition must be lossless (joining the parts gives back the original relation with no extra rows, in any join order) and, ideally, dependency-preserving.
  • Properties of the result: each row identified by a unique key, no repeating groups, homogeneous columns, a unique name for each column.
  • Advantages: less redundancy, better organisation, consistent data, a more flexible design, relational integrity is enforced.
  • Disadvantages: more tables and more JOINs per query, so some queries slow down; the design needs the user's requirements to be known first; going to 4NF or 5NF is hard and time-consuming; careless decomposition gives a bad design.
3.4

Functional dependency (FD)

A functional dependency X → Y (read "X determines Y") holds on a relation R when any two tuples that agree on X also agree on Y. In other words, the value of X fixes the value of Y. X is the determinant (left side) and Y the dependent (right side). FDs are constraints that come from the meaning of the data, not from the rows that happen to be present.

Example: Student_ID → Student_Name holds (an ID fixes one name), Course → Teacher holds if each course has one teacher, but Student_Name → Student_ID does not (two students can share a name).

  • Trivial FD: X → Y with Y ⊆ X (e.g. {A, B} → A). Always true.
  • Non-trivial FD: at least one attribute of Y is not in X.
  • Completely non-trivial: X ∩ Y = ∅ (no attribute on both sides).
  • Full functional dependency: Y depends on all of X and on no proper subset of X.
  • Partial dependency: Y depends on only a part of a composite key (the cause of 2NF violations).
  • Transitive dependency: X → Y and Y → Z with Y not a key and not determining X, so X → Z holds only through Y (the cause of 3NF violations).
3.5

Armstrong's axioms and derived rules

The FDs implied by a given set F are found with three sound and complete rules (Armstrong's axioms), written for attribute sets X, Y, Z:

RuleStatementMeaning
ReflexivityIf Y ⊆ X then X → YA set determines its own subsets (trivial FDs)
AugmentationIf X → Y then XZ → YZAdding the same attributes to both sides keeps the FD true
TransitivityIf X → Y and Y → Z then X → ZDependencies chain
Union (derived)If X → Y and X → Z then X → YZCombine right sides
Decomposition (derived)If X → YZ then X → Y and X → ZSplit right sides
Pseudotransitivity (derived)If X → Y and WY → Z then WX → ZChain through a part of the left side

Sound means the rules never produce a false FD; complete means every FD implied by F can be produced with them. The set of all FDs implied by F is the closure of F, written F⁺.

3.6

Closure of an attribute set X⁺: the algorithm

Listing all of F⁺ is expensive. Instead we compute the attribute closure X⁺, the set of all attributes functionally determined by X under F. This one routine answers most exam questions.

  • Step 1: start with result = X.
  • Step 2: repeat: for every FD A → B in F, if A ⊆ result then add B to result.
  • Step 3: stop when a full pass adds nothing. The result is X⁺.
  • Uses: (1) test whether X → Y holds: it does exactly when Y ⊆ X⁺. (2) X is a super key when X⁺ contains all attributes of R. (3) Find candidate keys. (4) Test whether two FD sets are equivalent.
3.7

Worked example: closures for R(A, B, C, D, E) with A → B, B → C, CD → E

Compute each closure by repeatedly applying the FDs:

  • A⁺: start {A}. A → B adds B: {A, B}. B → C adds C: {A, B, C}. CD → E needs D, which is missing, so stop. A⁺ = {A, B, C}.
  • B⁺: {B} → B → C gives {B, C}. Nothing else applies. B⁺ = {B, C}.
  • (CD)⁺: {C, D}. CD → E adds E: {C, D, E}. (CD)⁺ = {C, D, E}.
  • (AD)⁺: {A, D} → B → C → then CD → E: (AD)⁺ = {A, B, C, D, E}, which is all of R, so AD is a super key.
  • Does A → E hold? E is not in A⁺ = {A, B, C}, so no. Does AD → E hold? Yes, since E is in (AD)⁺.
3.8

Keys: super, candidate, primary, alternate, composite, foreign

Keys are the foundation of normal forms. In terms of closure:

KeyDefinitionExample
Super keyAny set of attributes that uniquely identifies a row (its closure is all of R). It may contain unnecessary attributes.{student_id}, {email}, {student_id, name}, {student_id, email, name} are all super keys
Candidate keyA minimal super key: no attribute can be removed without losing uniqueness.{student_id} and {email}; {student_id, name} is not (name is extra)
Primary keyThe one candidate key chosen to identify rows. Cannot be NULL.student_id
Alternate keyA candidate key that was not chosen as primary.email
Unique keyA column constraint that stops duplicate values (NULLs may be allowed).email text UNIQUE
Composite keyA key made of two or more columns together.PRIMARY KEY (student_id, course_id) in an enrolment table
Foreign keyColumns that refer to the primary key of another table; links the tables and enforces referential integrity.enrollments.student_id REFERENCES students(student_id)

Memory chain: super key → remove extra attributes → candidate key → choose one → primary key. A prime attribute is one that belongs to some candidate key; every other attribute is non-prime. Prime and non-prime attributes are what the 2NF and 3NF tests are phrased in.

3.9

Finding candidate keys: a repeatable method

Use this order and you will not miss a key:

  • 1. Mark the essential attributes: any attribute that never appears on the right side of any FD cannot be derived, so it must be in every candidate key.
  • 2. Take their closure. If it is all of R, that set is the only candidate key (it is also minimal because each member is essential).
  • 3. Otherwise add one more attribute at a time (then pairs), computing the closure, until it covers R. Skip any set that contains a key already found.
  • 4. All attributes that appear in any candidate key are prime; the rest are non-prime.
  • Example R(A, B, C, D, E), F = {A → B, B → C, CD → E}: A and D never appear on a right side, so they are in every key; (AD)⁺ = R, so the only candidate key is AD. Prime = A, D; non-prime = B, C, E.
  • Example R(A, B, C, D, E, F), F = {AB → C, BC → AD, D → E, CF → B}: F never appears on the right, so it is essential. (F)⁺ = {F} only. Adding one attribute at a time, the candidate keys are CF, ABF.
3.10

Equivalence of FD sets and the canonical (minimal) cover

Two FD sets F and G are equivalent when F⁺ = G⁺, i.e. every FD of F follows from G and the other way round (check with attribute closures). A canonical cover (minimal cover) Fc is an equivalent set with no redundancy; it is the starting point for 3NF design.

  • Rule 1: every right side is a single attribute (use decomposition: A → BC becomes A → B and A → C).
  • Rule 2: no extraneous attribute on a left side. For AB → C, attribute B is extraneous if C ∈ A⁺ computed with the full set.
  • Rule 3: no redundant FD. Drop X → Y if Y ∈ X⁺ computed without that FD.
  • Rule 4: merge FDs that share the same left side (union).
3.10b

Worked: minimal cover of {A → BC, B → C, A → B, AB → C}

  • Split right sides: A → B, A → C, B → C, A → B, AB → C. Remove the duplicate A → B.
  • Extraneous attribute in AB → C: B → C is already given, so A is extraneous: AB → C becomes B → C (a duplicate).
  • Redundant FD: A → C is implied by A → B and B → C (A⁺ without A → C = {A, B, C}), so drop it.
  • Minimal cover: A → B, B → C.
3.11

First normal form (1NF)

A relation is in 1NF when every attribute holds only atomic (single, indivisible) values. 1NF disallows multi-valued attributes, composite attributes and any combination of them inside one cell. Every row must also be unique. Example: EMPLOYEE with a multi-valued EMP_PHONE is not in 1NF:

EMP_IDEMP_NAMEEMP_PHONEEMP_STATE
14John7272826385, 9064738238UP
20Harry8574783832Bihar
12Sam7390372389, 8589830302Punjab

Fix 1 (repeat the row): one row per phone number: (14, John, 7272826385, UP), (14, John, 9064738238, UP), (20, Harry, 8574783832, Bihar), (12, Sam, 7390372389, Punjab), (12, Sam, 8589830302, Punjab); the key becomes (EMP_ID, EMP_PHONE). Fix 2 (separate table, preferred): EMPLOYEE(EMP_ID, EMP_NAME, EMP_STATE) and EMP_PHONE(EMP_ID, EMP_PHONE). A composite attribute such as Address is split into Street, City, PIN.

3.12

Second normal form (2NF): remove partial dependencies

A relation is in 2NF if it is in 1NF and every non-prime attribute is fully functionally dependent on every candidate key (no non-prime attribute depends on only part of a composite key). A relation whose key is a single attribute is automatically in 2NF if it is in 1NF.

Teacher_IDSubjectTeacher_Age
25Chemistry30
25Biology30
47English35
83Math38
83Computer38

Key = (Teacher_ID, Subject). FD: Teacher_ID → Teacher_Age. Teacher_Age depends on a proper subset of the key, so this violates 2NF (and repeats the age: 30 twice, 38 twice). Decompose: TEACHER_DETAIL(Teacher_ID, Teacher_Age) with key Teacher_ID, and TEACHER_SUBJECT(Teacher_ID, Subject) with key (Teacher_ID, Subject). Second example: STUDENT_COURSE(Student_ID, Course_ID, Student_Name, Course_Name): Student_ID → Student_Name and Course_ID → Course_Name are partial, so split into STUDENT, COURSE and ENROLMENT(Student_ID, Course_ID).

3.13

Third normal form (3NF): remove transitive dependencies

A relation is in 3NF if it is in 2NF and has no transitive dependency of a non-prime attribute on a key. The formal test: for every non-trivial FD X → Y, at least one of these holds: (1) X is a super key, or (2) every attribute of Y is a prime attribute.

EMP_ZIP is not a key and EMP_STATE, EMP_CITY are non-prime, so EMP_ID → EMP_STATE/EMP_CITY holds only through EMP_ZIP (transitive). Decompose: EMPLOYEE(EMP_ID, EMP_NAME, EMP_ZIP) and EMPLOYEE_ZIP(EMP_ZIP, EMP_STATE, EMP_CITY) with key EMP_ZIP. Other examples: Emp_ID → Dept_ID → Dept_Name; Patient_ID → Doctor_ID → Doctor_Name.

3.14

Boyce–Codd normal form (BCNF)

BCNF is a stricter version of 3NF. A relation is in BCNF if, for every non-trivial FD X → Y, X is a super key. There is no "prime attribute" escape clause. Simple rule: only a key may determine other attributes. Every BCNF relation is in 3NF, but not every 3NF relation is in BCNF.

EMP_IDEMP_COUNTRYEMP_DEPTDEPT_TYPEEMP_DEPT_NO
264IndiaDesigningD394283
264IndiaTestingD394300
364UKStoresD283232
364UKDevelopingD283549

FDs: EMP_ID → EMP_COUNTRY and EMP_DEPT → {DEPT_TYPE, EMP_DEPT_NO}. Candidate key = {EMP_ID, EMP_DEPT} (an employee works in several departments). Neither EMP_ID nor EMP_DEPT alone is a super key, so both FDs violate BCNF. Decompose into three relations: EMP_COUNTRY(EMP_ID, EMP_COUNTRY) key EMP_ID; EMP_DEPT(EMP_DEPT, DEPT_TYPE, EMP_DEPT_NO) key EMP_DEPT; EMP_DEPT_MAPPING(EMP_ID, EMP_DEPT) key (EMP_ID, EMP_DEPT). In each, the left side of every FD is now a key.

3.16

3NF versus BCNF: where they differ

3NF allows an FD X → Y when X is not a key if Y is prime. BCNF does not. The classic case: R(A, B, C) with FDs AB → C and C → B. Candidate keys are AB and AC (so A, B, C are all prime). C → B: C is not a super key, so not in BCNF; B is prime, so it is in 3NF.

BCNF decomposition gives R1(C, B) and R2(A, C), which is lossless but loses the FD AB → C (neither relation contains A, B and C together), so it is not dependency-preserving. This is why 3NF is accepted when BCNF would lose a dependency.

  • 3NF: always achievable with a lossless and dependency-preserving decomposition.
  • BCNF: always lossless, but dependency preservation is not guaranteed.
  • Redundancy that 3NF may still allow comes exactly from the "Y is prime" clause.

3.18

Decomposition: lossless join and dependency preservation

Normalising means replacing R by R1, R2, … . Two properties decide whether the replacement is acceptable.

  • Lossless join: R1 ⋈ R2 = R exactly (no spurious tuples, nothing lost). Binary test: the decomposition of R into R1 and R2 is lossless if (R1 ∩ R2) → R1 or (R1 ∩ R2) → R2 holds, i.e. the common attributes form a key of at least one part.
  • Dependency preservation: every FD of F can be checked inside a single decomposed relation, i.e. (F1 ∪ F2 ∪ …)⁺ = F⁺ where Fi is the set of FDs of F whose attributes lie in Ri. If not, enforcing an FD needs a join, which is expensive.
  • Why both matter: lossless protects the data; dependency preservation lets the DBMS enforce rules cheaply with key constraints.
  • Example: R(A, B, C), A → B. Split into R1(A, B) and R2(A, C): common attribute A, and A → B so A is a key of R1, so lossless; A → B lives in R1, so dependency-preserving. Split into R1(A, B) and R2(B, C) instead: common B, but B → A and B → C do not hold, so the join can create spurious tuples: lossy.
3.19

Algorithms: BCNF decomposition and 3NF synthesis

BCNF decomposition (always lossless): while some relation Ri has a non-trivial FD X → Y with X not a super key of Ri: replace Ri by (Ri − Y) and (X ∪ Y). Repeat until every relation is in BCNF. Use X⁺ to find the FD to split on.

3NF synthesis (lossless and dependency-preserving):

  • 1. Compute a canonical (minimal) cover Fc of F.
  • 2. For each FD X → Y in Fc, create a relation Ri(X ∪ Y). (Merge relations that come from FDs with the same left side.)
  • 3. If none of the relations contains a candidate key of R, add one relation made of a candidate key.
  • 4. Remove any relation whose attributes are a subset of another.
  • Example: R(A, B, C, D, E), Fc = {A → B, B → C, CD → E}. Relations: R1(A, B), R2(B, C), R3(C, D, E). Candidate key AD is in none, so add R4(A, D). Result: R1(A,B), R2(B,C), R3(C,D,E), R4(A,D), all in 3NF.
3.20

Multivalued dependency (MVD) and fourth normal form (4NF)

A multivalued dependency A →→ B ("A multidetermines B") says that for one value of A there is a set of B values, independent of the other attributes. It appears when one table stores two independent multi-valued facts about the same key. A relation is in 4NF if it is in BCNF and has no non-trivial multivalued dependency.

Example: STUDENT(STU_ID, COURSE, HOBBY). Student 21 has courses Computer and Math and hobbies Dancing and Singing. Because courses and hobbies are unrelated, the table has to hold all 2 × 2 = 4 combinations (21, Computer, Dancing), (21, Computer, Singing), (21, Math, Dancing), (21, Math, Singing). STU_ID →→ COURSE and STU_ID →→ HOBBY.

  • Problems: redundancy (student 21 repeated 4 times); changing a hobby means editing several rows; a student cannot be added with courses but no hobby; deleting the last course may delete the hobby.
  • 4NF fix: STUDENT_COURSE(STU_ID, COURSE) and STUDENT_HOBBY(STU_ID, HOBBY). The 4 rows become 2 + 2.
  • How to spot it: (1) does a key have several values of an attribute? (2) are two such sets independent? (3) does the table store all combinations? If yes to all, apply 4NF.
  • Other examples: Employee skills and languages; Doctor hospitals and specialisations; Student projects and certifications.
3.21

Join dependency and fifth normal form (5NF)

A join dependency says that a relation R equals the natural join of some of its projections. 5NF (project-join normal form): a relation is in 5NF if it is in 4NF and every join dependency in it is implied by its candidate keys, so it can only be split losslessly into pieces that the keys already imply. It removes the rare redundancy that is visible only when three or more relations must be joined (e.g. Supplier–Part–Project where the three pairwise facts together define the fourth). It is mostly of theoretical interest; for exams, 1NF to BCNF are the core and 4NF is the usual extension.

Normalisation process flow and comparison

Process: unorganised table → 1NF → 2NF → 3NF → BCNF → 4NF → 5NF, each step a decomposition that must stay lossless.

3.23

Denormalisation: when to break the rules on purpose

Highly normalised designs need many JOINs. In read-heavy systems (reports, analytics) designers sometimes denormalise deliberately: duplicate a column, keep a precomputed total or merge tables, accepting redundancy for speed.

  • Gain: fewer joins, faster reads.
  • Cost: more storage, update and consistency burden, so the application or triggers must keep the copies in step.
  • Rule: normalise first, measure, then denormalise only the proven bottlenecks.
3.24

Keys and constraints in SQL (PostgreSQL)

The key types above are declared in DDL. A normalised design is enforced by exactly these constraints.

CREATE TABLE students (
    student_id integer PRIMARY KEY,
    email      text UNIQUE NOT NULL,
    name       text
);
CREATE TABLE courses (
    course_id   integer PRIMARY KEY,
    course_name text
);
CREATE TABLE enrollments (
    student_id integer REFERENCES students(student_id),
    course_id  integer REFERENCES courses(course_id),
    PRIMARY KEY (student_id, course_id)      -- composite key
);
  • PRIMARY KEY: unique and NOT NULL, one per table. UNIQUE: no duplicates (an alternate key). FOREIGN KEY / REFERENCES: a value must exist in the parent table, so you cannot insert an enrolment for a student who does not exist.
  • The enrolment table above is the 2NF result for the student–course example: the student and course details live in their own tables.
3.25

Database design and implementation process

Normalisation is one step in a larger lifecycle.

  • 1. Requirements analysis: interview users, list data and processes.
  • 2. Conceptual design: ER or EER diagram, independent of any DBMS.
  • 3. Logical design: map the ER diagram to relations, choose keys, then normalise using the FDs.
  • 4. Physical design: choose file organisation, indexes, partitioning.
  • 5. Implementation: DDL, load data, build views and security, then test.
  • 6. Maintenance: tune performance, adapt to changing requirements.

Q2

State Armstrong's axioms. Prove the union rule.

Show model answer

Reflexivity: if Y ⊆ X then X → Y. Augmentation: if X → Y then XZ → YZ. Transitivity: if X → Y and Y → Z then X → Z. They are sound (never give a false FD) and complete (give every implied FD). Derived rules: union, decomposition, pseudotransitivity.

Proof of union. Given X → Y and X → Z. Augment X → Y with X: X → XY (since XX = X). Augment X → Z with Y: XY → YZ. By transitivity on X → XY and XY → YZ we get X → YZ. ∎

Q3

What is the closure of an attribute set? Give the algorithm and its uses.

Show model answer

The closure X⁺ is the set of all attributes determined by X under F. Algorithm: result = X; repeat { for each FD A → B with A ⊆ result, add B } until no change.

  • X → Y holds iff Y ⊆ X⁺.
  • X is a super key iff X⁺ = all attributes of R; it is a candidate key if no proper subset also has this property.
  • Two FD sets are equivalent iff each FD of one is implied (via closures) by the other.
Q4

R(A, B, C, D, E) has A → B, B → C, CD → E. Find A⁺, (CD)⁺, (AD)⁺, all candidate keys and the prime and non-prime attributes.

Show model answer
  1. A⁺: {A} → B → {A, B} → C → {A, B, C}; CD → E needs D, so stop.
  2. (CD)⁺ = {C, D, E}.
  3. (AD)⁺: {A, D} → B → C → CD → E gives {A, B, C, D, E} = R, so AD is a super key.
  4. A and D never appear on a right side, so both are in every key; AD is therefore the only candidate key.
  5. Prime = A, D. Non-prime = B, C, E.
A⁺ = ABC, (CD)⁺ = CDE, (AD)⁺ = ABCDE; the only candidate key is AD.

Q6

What is BCNF? How does it differ from 3NF? Give an example of a relation in 3NF but not in BCNF.

Show model answer

A relation is in BCNF if for every non-trivial FD X → Y, X is a super key. 3NF additionally allows X → Y when Y is a prime attribute; BCNF has no such exception, so BCNF is stricter and every BCNF relation is in 3NF.

Example: R(A, B, C) with AB → C and C → B. Candidate keys: AB, AC. C → B has a non-key left side, so R is not in BCNF; B is prime, so R is in 3NF. BCNF decomposition R1(C, B), R2(A, C) is lossless but loses AB → C.

Q7

Explain the anomalies caused by redundancy using a suitable table, and how normalisation removes them.

Show model answer

Use STUDENT_COURSE(Student_ID, Student_Name, Course, Teacher, Teacher_Phone). Update anomaly: a teacher's phone is repeated for each student, so a change must be made in every row. Deletion anomaly: deleting the only student of a course also deletes the teacher's details. Insertion anomaly: a new teacher cannot be added until a student enrols.

Normalisation splits it into STUDENT(Student_ID, Student_Name), TEACHER(Teacher, Phone), COURSE(Course, Teacher) and ENROLMENT(Student_ID, Course), so each fact is stored once and each anomaly disappears.

Q8

What is lossless-join decomposition? State the test and show a lossy example.

Show model answer

A decomposition of R into R1 and R2 is lossless if R1 ⋈ R2 = R, with no spurious tuples. Test: R1 ∩ R2 → R1 or R1 ∩ R2 → R2 must hold in F⁺.

Lossy example: R(Student, Course, Teacher) with rows (S1, C1, T1), (S2, C1, T2). Split into R1(Student, Course), R2(Course, Teacher) on the common attribute Course, which is not a key of either part (no FD Course → Student or Course → Teacher). R1 ⋈ R2 returns (S1, C1, T1), (S1, C1, T2), (S2, C1, T1), (S2, C1, T2): two spurious tuples.

Q9

What is dependency preservation? Why can BCNF lose it and 3NF not?

Show model answer

A decomposition is dependency-preserving if every FD of F can be verified on a single relation, i.e. the union of the FDs projected onto the parts has the same closure as F. Then no join is needed to check constraints.

BCNF splits on a violating FD X → Y, putting X and Y together but separating the rest, so an FD whose attributes end up in different parts (like AB → C when C → B forces the split) can no longer be checked locally. The 3NF synthesis algorithm creates one relation for each FD of the minimal cover, so every FD sits inside some relation and is always preserved.

Q10

Explain the minimal (canonical) cover with an example.

Show model answer

A minimal cover is an equivalent FD set with (1) single-attribute right sides, (2) no extraneous left attributes and (3) no redundant FD.

  1. F = {A → BC, B → C, A → B, AB → C}.
  2. Split right sides: A → B, A → C, B → C, A → B (duplicate), AB → C.
  3. AB → C: since B → C holds, A is extraneous; it becomes B → C (duplicate).
  4. A → C is implied by A → B and B → C, so remove it.
Minimal cover: A → B, B → C.
Q11

Give the 3NF synthesis algorithm and apply it to R(A, B, C, D, E) with A → B, B → C, CD → E.

Show model answer
  • Find the minimal cover (here already minimal).
  • For each FD X → Y create Ri(X ∪ Y): R1(A, B), R2(B, C), R3(C, D, E).
  • If no relation contains a candidate key, add one; the key is AD, so add R4(A, D).
  • Drop any relation contained in another (none).

Result: R1(A, B), R2(B, C), R3(C, D, E), R4(A, D); lossless and dependency-preserving.

Q12

Describe the BCNF decomposition algorithm. Decompose R(Student_ID, Student_Name, Course, Instructor) with Student_ID → Student_Name, Student_ID → Course, Course → Instructor.

Show model answer

While a relation Ri has a non-trivial FD X → Y with X not a super key, replace Ri by (Ri − Y) and (X ∪ Y).

  1. Key is Student_ID. Course → Instructor violates BCNF (Course is not a key).
  2. Split: R1 = (Course, Instructor) with key Course; R2 = R − Instructor = (Student_ID, Student_Name, Course) with key Student_ID.
  3. Check R1: Course → Instructor, left side is a key. Check R2: Student_ID → Student_Name, Course, a key.
Both relations are in BCNF and the split is lossless (common attribute Course is the key of R1).
Q13

What is a multivalued dependency? Explain 4NF with an example.

Show model answer

A →→ B means for each A value there is a set of B values that does not depend on the other attributes. It arises when a table stores two independent multi-valued facts about one key. A relation is in 4NF if it is in BCNF and has no non-trivial MVD.

STUDENT(STU_ID, COURSE, HOBBY) with student 21: courses Computer, Math; hobbies Dancing, Singing needs 2 × 2 = 4 rows. Decompose into STUDENT_COURSE(STU_ID, COURSE) and STUDENT_HOBBY(STU_ID, HOBBY): 2 + 2 rows, no redundancy and no combination anomalies.

Q14

Distinguish super key, candidate key, primary key, alternate key and foreign key. How are they declared in SQL?

Show model answer

A super key uniquely identifies rows (may have extra attributes). A candidate key is a minimal super key. The primary key is the chosen candidate key (NOT NULL, unique). An alternate key is a candidate key not chosen. A foreign key refers to a primary key of another table.

CREATE TABLE employees (
  employee_id integer PRIMARY KEY,       -- primary key
  email text UNIQUE NOT NULL,            -- alternate key
  dept_id integer REFERENCES dept(dept_id)  -- foreign key
);
Q15

Why do we need normalisation? List its advantages and disadvantages. What is denormalisation?

Show model answer
  • Need: minimise redundancy, remove insertion/update/deletion anomalies, keep the design flexible and consistent.
  • Advantages: less duplicated data, easy maintenance, integrity, flexible design.
  • Disadvantages: more tables and joins, slower complex queries, needs requirements known up front, hard at 4NF/5NF, bad decomposition causes problems.
  • Denormalisation: deliberately adding redundancy back (duplicate columns, precomputed values) to speed up reads, accepting a higher cost of keeping copies consistent.

P1

Closures

R(A, B, C, D, E), F = {A → B, B → C, CD → E}. Find A⁺, B⁺, (BD)⁺, (CD)⁺ and (AD)⁺. Is AD a candidate key?

Show solution
  1. A⁺ = {A, B, C} (A → B → C; CD → E needs D).
  2. B⁺ = {B, C}.
  3. (BD)⁺ = {B, C, D, E}: B → C, then CD → E, giving B, C, D, E but never A.
  4. (CD)⁺ = {C, D, E}.
  5. (AD)⁺ = {A, B, C, D, E} = R, so AD is a super key. Remove A: D⁺ = {D}; remove D: A⁺ = {A, B, C}; neither is R, so AD is minimal and is a candidate key.
AD is a candidate key.
P2

Candidate keys of a six-attribute relation

R(A, B, C, D, E, F) with AB → C, BC → AD, D → E, CF → B. Find all candidate keys.

Show solution
  1. F never appears on any right side, so F is in every key.
  2. Try single additions: (AF)⁺ = {A, F}; (BF)⁺ = {B, F}; (CF)⁺ = {A, B, C, D, E, F}; (DF)⁺ = {D, E, F}.
  3. Which of these equal R = ABCDEF? Computing: AF: no, BF: no, CF: yes, DF: no, EF: no
  4. Candidate keys (computed by checking every attribute set, keeping only minimal ones): CF, ABF.
Candidate keys: CF, ABF.
P3

Test an FD

With F = {A → B, B → C, CD → E} on R(A, B, C, D, E), does (a) A → C hold? (b) A → E hold? (c) AD → E hold?

Show solution
  1. (a) A⁺ = {A, B, C} contains C: yes (transitivity A → B → C).
  2. (b) E ∉ A⁺: no.
  3. (c) (AD)⁺ contains E: yes (pseudotransitivity: A → C gives AD → CD, then CD → E).
(a) yes, (b) no, (c) yes.
P4

Identify the normal form (2NF test)

ENROLMENT(Student_ID, Course_ID, Student_Name, Course_Name, Grade) with key (Student_ID, Course_ID). FDs: Student_ID → Student_Name; Course_ID → Course_Name; (Student_ID, Course_ID) → Grade. Which normal form is it in? Decompose.

Show solution
  1. 1NF holds (atomic values).
  2. Student_Name depends on part of the key (Student_ID), Course_Name on part (Course_ID): partial dependencies, so it is not in 2NF; it is in 1NF.
  3. Decompose: STUDENT(Student_ID, Student_Name), COURSE(Course_ID, Course_Name), ENROLMENT(Student_ID, Course_ID, Grade).
  4. Each relation now has only full dependencies, so all are in 2NF; in fact also 3NF and BCNF.
In 1NF only; decomposes into STUDENT, COURSE and ENROLMENT.
P5

3NF test with a transitive dependency

EMP(Emp_ID, Emp_Name, Dept_ID, Dept_Name) with Emp_ID → Emp_Name, Dept_ID and Dept_ID → Dept_Name. Is it in 3NF? If not, decompose.

Show solution
  1. Key: Emp_ID.
  2. Dept_ID → Dept_Name: Dept_ID is not a super key and Dept_Name is not prime, so the 3NF test fails. Emp_ID → Dept_Name is transitive.
  3. Decompose: EMPLOYEE(Emp_ID, Emp_Name, Dept_ID), DEPARTMENT(Dept_ID, Dept_Name).
Not in 3NF; split into EMPLOYEE and DEPARTMENT.
P6

3NF but not BCNF

R(A, B, C) with FDs AB → C and C → B. Find the candidate keys, decide whether it is in 3NF and in BCNF, and decompose if needed. Is the result dependency-preserving?

Show solution
  1. (AB)⁺ = {A, B, C}; (AC)⁺ = {A, C, B}. So candidate keys: AB, AC. All of A, B, C are prime.
  2. 3NF: AB → C (AB is a key, fine); C → B (B is prime, fine). In 3NF.
  3. BCNF: C → B has left side C, which is not a super key. Not in BCNF.
  4. Decompose on C → B: R1(C, B) and R2(A, C). Common attribute C is the key of R1, so lossless.
  5. AB → C: no relation holds A, B and C, so it cannot be checked without a join. Not dependency-preserving.
In 3NF, not BCNF. BCNF split is lossless but loses AB → C.
P7

Lossless or lossy?

R(A, B, C) with A → B. Is the split (a) R1(A, B), R2(A, C) lossless? (b) R1(A, B), R2(B, C) lossless?

Show solution
  1. (a) R1 ∩ R2 = {A}; A → B so A → R1 (A⁺ ⊇ {A, B}). Lossless, and A → B is preserved in R1.
  2. (b) R1 ∩ R2 = {B}; B → A? no. B → C? no. The common attribute is a key of neither part, so lossy: joining on B can pair an A value with a C value of another tuple.
(a) lossless; (b) lossy.
P8

Minimal cover

Find the minimal cover of F = {A → BC, B → C, A → B, AB → C}.

Show solution
  1. Single right sides: A → B, A → C, B → C, A → B, AB → C; drop the duplicate A → B.
  2. AB → C: B → C already holds, so A is extraneous. It reduces to B → C (duplicate).
  3. A → C: A⁺ without it = {A, B, C}, so it is redundant.
Minimal cover: A → B, B → C.
P9

3NF synthesis

R(A, B, C, D, E, F), F = {A → B, B → C, D → E}. Find the candidate key and a 3NF decomposition.

Show solution
  1. Never on a right side: A, D, F. Closure of ADF: A → B → C, D → E, so (ADF)⁺ = all six attributes. Candidate key: ADF (and it is the only one).
  2. Minimal cover is F itself. Relations: R1(A, B), R2(B, C), R3(D, E).
  3. No relation contains the key ADF, so add R4(A, D, F).
R1(A, B), R2(B, C), R3(D, E), R4(A, D, F): all in 3NF, lossless, dependency-preserving.
P10

BCNF decomposition of the employee–department table

EMPLOYEE(EMP_ID, EMP_COUNTRY, EMP_DEPT, DEPT_TYPE, EMP_DEPT_NO) with EMP_ID → EMP_COUNTRY and EMP_DEPT → {DEPT_TYPE, EMP_DEPT_NO}. Find the key and decompose into BCNF.

Show solution
  1. Key: (EMP_ID, EMP_DEPT) since both are needed to identify a row.
  2. EMP_ID → EMP_COUNTRY: EMP_ID is not a super key, so split: EMP_COUNTRY(EMP_ID, EMP_COUNTRY) and R(EMP_ID, EMP_DEPT, DEPT_TYPE, EMP_DEPT_NO).

Three relations: EMP_COUNTRY, EMP_DEPT, EMP_DEPT_MAPPING.

Check equivalence of FD sets

Are F = {A → B, B → C} and G = {A → B, A → C, B → C} equivalent?

Show solution

  2. For G: A → C follows from F because A⁺ under F = {A, B, C}. A → B and B → C are in F.
