3

Normalisation

Functional dependencies and the normal forms.
3.1

Design guidelines for relational schemas

  • Each relation should have clear semantics (one entity or relationship).
  • Reduce redundant data and avoid insert, delete and update anomalies.
  • Avoid attributes that are often NULL.
  • Make decompositions that generate no spurious tuples.
3.2

Anomalies in a badly designed table

  • Insertion: cannot add a department until it has an employee.
  • Deletion: deleting the last employee deletes the department data.
  • Update: a changed department name must be edited in many rows or it becomes inconsistent.
3.3

Functional dependency (FD)

X → Y

X functionally determines Y if any two tuples that agree on X also agree on Y. Trivial if Y ⊆ X. A key determines every attribute.

3.4

Armstrong's axioms

  • Reflexivity: Y ⊆ X ⇒ X → Y.
  • Augmentation: X → Y ⇒ XZ → YZ.
  • Transitivity: X → Y, Y → Z ⇒ X → Z.
  • Derived: union (X → Y, X → Z ⇒ X → YZ), decomposition (X → YZ ⇒ X → Y), pseudotransitivity.
  • The axioms are sound and complete.
3.5

Attribute closure and keys

X+ = { A : X → A follows from the FDs }
  • Start with X+ = X; repeat: if a FD L → R has L ⊆ X+, add R; stop when nothing changes.
  • X is a super key iff X+ contains all attributes; a candidate key is a minimal such X.
  • Attributes that never appear on any right-hand side must be in every key.

3.6

First normal form (1NF)

All attribute values are atomic: no repeating groups, no multivalued or composite attributes. Fix by splitting into rows or a new table.

3.7

Second normal form (2NF)

1NF and no partial dependency: no non-prime attribute depends on part of a candidate key. Only matters when a key is composite; fix by moving the partially dependent attributes to their own relation.

3.8

Third normal form (3NF)

2NF and no transitive dependency of a non-prime attribute on a key. Formally, for every nontrivial FD X → A: X is a super key or A is a prime attribute (part of some candidate key).

3.9

Boyce–Codd normal form (BCNF)

For every nontrivial FD X → Y, X must be a super key. BCNF is stricter than 3NF (every BCNF relation is in 3NF). A lossless decomposition into BCNF always exists, but it may not preserve dependencies; 3NF always can be reached lossless and dependency preserving.

3.11

Decomposition using FDs

  • Lossless join: R1 ∩ R2 → R1 or R1 ∩ R2 → R2 (the common attributes are a key of one part). Natural join of the parts gives back exactly R.
  • Dependency preserving: every FD of R can be checked within one decomposed relation (the union of the projected FDs implies all of them).
  • BCNF algorithm: while a relation has a violating FD X → Y (X not a super key), split into X Y and R − Y.
3.12

Multivalued dependency and 4NF

X →→ Y holds when, for each X value, the set of Y values is independent of the remaining attributes (e.g. a person's phones and hobbies). Such a relation stores all combinations, causing redundancy. 4NF: BCNF and every nontrivial MVD has a super key on the left; decompose into (X, Y) and (X, rest).

3.13

Database design and implementation process

  • Requirements → ER design → map to relations → apply normalisation → add indexes and constraints → create the schema, load data, test and tune.
  • Denormalise deliberately only for performance.
Q

Theory questions and model answers

Tap "Show model answer" to reveal.
Q1

What is a functional dependency? State Armstrong's axioms.

Show model answer

X → Y means equal X values force equal Y values. Axioms: reflexivity (Y ⊆ X ⇒ X → Y), augmentation (X → Y ⇒ XZ → YZ) and transitivity (X → Y, Y → Z ⇒ X → Z); they are sound and complete.

Q2

Explain insertion, deletion and update anomalies.

Show model answer

In a table mixing several facts, you may be unable to insert one fact without another (insertion), lose a fact when deleting another (deletion), or leave data inconsistent after editing one of many copies (update).

Q3

Define 1NF, 2NF, 3NF and BCNF.

Show model answer

1NF: atomic values. 2NF: 1NF and no partial dependency of a non-prime attribute on part of a key. 3NF: 2NF and no transitive dependency (for every X → A, X is a super key or A is prime). BCNF: every determinant is a super key.

Q4

What is a lossless-join decomposition and dependency preservation?

Show model answer

Lossless: joining the decomposed relations gives back exactly the original (R1 ∩ R2 is a key of R1 or R2). Dependency preserving: every FD can be checked within one decomposed relation.

Q5

Explain multivalued dependency and fourth normal form.

Show model answer

X →→ Y means the set of Y values for an X is independent of the other attributes. 4NF: BCNF and every nontrivial MVD has a super key on the left; decompose into (X, Y) and (X, rest).

Q6

Describe the database design and implementation process.

Show model answer

Requirements → conceptual (ER) design → logical design (map and normalise) → physical design (indexes, storage) → implementation, testing and tuning.

P

Practice problems with solutions

Try each one first, then open the solution.
P1

Attribute closure and candidate key

R(A, B, C, D, E) with A → B, B → C, CD → E. Find A⁺, AD⁺ and the candidate keys.

Show solution
  1. A⁺: A → B gives B; B → C gives C; so A⁺ = ABC (E needs D).
  2. AD⁺: A⁺ = ABC, plus D, then CD → E: AD⁺ = ABCDE.
  3. A and D never occur on a right-hand side, so both belong to every key.
AD⁺ = ABCDE, so the candidate key is AD (the only one).
P2

Normal form of a relation

For R(A, B, C, D, E) in P1 find the highest normal form.

Show solution
  1. Key = AD. Non-prime attributes: B, C, E.
  2. A → B: B depends on part (A) of the key → partial dependency, so R is not in 2NF. It is in 1NF.
R is only in 1NF.
P3

Decompose into 3NF

Decompose R(A, B, C, D, E) of P1 to remove the anomalies.

Show solution
  1. Partial dependency A → B: split into R₁(A, B).
  2. B → C: transitive; split R₂(B, C).
  3. CD → E: R₃(C, D, E).
  4. Keep the key: R₄(A, D).
R₁(A, B), R₂(B, C), R₃(C, D, E), R₄(A, D): lossless (R₄ holds the key) and every FD is preserved.
P4

Minimal cover

Find a minimal (canonical) cover of F = {A → BC, B → C, A → B, AB → C}.

Show solution
  1. Split right sides: A → B, A → C, B → C, A → B, AB → C.
  2. Remove duplicates; AB → C is redundant (A → B and B → C already give it; B alone determines C).
  3. A → C follows from A → B and B → C, so it is redundant.
Minimal cover: A → B, B → C.
P5

BCNF check

R(S, C, T) with FDs SC → T and T → C (S = student, C = course, T = teacher). Is R in 3NF? In BCNF?

Show solution
  1. Candidate keys: SC (SC⁺ = SCT) and ST (ST⁺ = STC).
  2. T → C: T is not a super key, so R is not in BCNF.
  3. 3NF test: the right side C is a prime attribute (part of key SC), so R is in 3NF.
R is in 3NF but not in BCNF; decomposing to (T, C) and (S, T) is lossless but loses SC → T.
P6

Lossless-join test

R(A, B, C) with A → B is decomposed into R₁(A, B) and R₂(A, C). Is it lossless? Is it dependency preserving?

Show solution
  1. R₁ ∩ R₂ = {A}, and A → B means A is a key of R₁(A, B).
  2. So the decomposition is lossless.
  3. The only FD A → B lies inside R₁, so it is preserved.
Lossless and dependency preserving.
P7

Multivalued dependency

Person(name, phone, hobby) stores every phone with every hobby of a person. State the MVDs and decompose to 4NF.

Show solution
  1. name →→ phone and name →→ hobby (independent sets), and there is no non-trivial FD.
  2. The key is all three attributes, so the relation is in BCNF but not 4NF, and stores phones × hobbies rows.
  3. Decompose into (name, phone) and (name, hobby).
R₁(name, phone), R₂(name, hobby); the redundancy is gone.
