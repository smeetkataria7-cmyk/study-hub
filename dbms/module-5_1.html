5

Transactions & recovery

ACID, serializability, locking, timestamps and recovery.
5.1

Transaction concept

A transaction is a unit of work made of reads and writes that takes the database from one consistent state to another, ended by commit or abort / rollback.

5.2

ACID properties

  • Atomicity — all or nothing (recovery manager).
  • Consistency — preserves integrity constraints (the programmer and DBMS).
  • Isolation — concurrent transactions behave as if run one at a time (concurrency-control manager).
  • Durability — committed changes survive failures (recovery manager).
5.3

Transaction states

  • Active → partially committed (last statement done) → committed.
  • Active / partially committed → failed → aborted (rolled back; restart or kill) → terminated.
5.4

Problems of concurrent execution

  • Lost update (write-write), dirty read (reading uncommitted data), non-repeatable read, phantom read (new rows appear), incorrect summary.
  • Isolation levels: Read Uncommitted, Read Committed, Repeatable Read, Serializable.
5.5

Schedules and serializability

  • A schedule is an interleaving of operations preserving each transaction's order. Serial: no interleaving. Serializable: equivalent to some serial schedule.
  • Conflict: two operations of different transactions on the same item, at least one a write (R-W, W-R, W-W). Conflict equivalent schedules order every conflicting pair identically.
  • Test: build a precedence graph (edge Ti → Tj for a conflict with Ti first); conflict serializable iff no cycle; a topological order gives the equivalent serial order.
  • View serializability is weaker than conflict serializability; testing it is NP-complete.

5.6

Recoverability

  • Recoverable: if Tj reads data written by Ti, then Ti commits before Tj.
  • Cascadeless (ACA): transactions read only committed data, so no cascading rollback.
  • Strict: no read or write of an item until its last writer commits or aborts. Strict ⊂ cascadeless ⊂ recoverable.

5.8

Two-phase locking (2PL)

  • Growing phase: only acquire locks; shrinking phase: only release. Once a lock is released no new lock may be taken; the lock point is the end of growing.
  • 2PL guarantees conflict serializability but allows deadlock and cascading rollback.
  • Strict 2PL: hold all X locks until commit / abort (cascadeless). Rigorous 2PL: hold all locks until the end.
5.9

Deadlock handling

  • Deadlock: a cycle of transactions each waiting for another's lock.
  • Prevention: wait-die (older waits, younger dies) and wound-wait (older wounds the younger) using timestamps; or lock everything up front.
  • Detection: build a wait-for graph; a cycle means deadlock. Recovery: pick a victim (least cost) and roll back, avoiding starvation.
  • Timeout — abort a transaction that waits too long.
5.10

Timestamp-based protocol

Each transaction gets a timestamp TS(T); each item Q has R-TS(Q) and W-TS(Q). Older transactions come first in the equivalent serial order.

  • Read(Q): if TS(T) < W-TS(Q) → reject and roll back; else execute and set R-TS = max(R-TS, TS(T)).
  • Write(Q): if TS(T) < R-TS(Q) or TS(T) < W-TS(Q) → reject and roll back; else execute and set W-TS = TS(T).
  • Thomas write rule: an outdated write (TS(T) < W-TS(Q) only) is simply ignored.
  • Deadlock-free, but may starve and cause cascading rollbacks.
5.11

Validation-based protocol (optimistic)

  • Three phases: read (work on local copies), validation (check conflicts), write (make changes permanent).
  • For an older Ti and younger Tj it validates if Ti finished before Tj started, or Ti finished its write phase before Tj validates and the write set of Ti does not meet the read set of Tj.
  • Good when conflicts are rare.
5.12

Recovery: failure classification

  • Transaction failure: logical error (bad input, overflow) or system error (deadlock).
  • System crash: power or software failure; main memory is lost, disk survives.
  • Disk failure: head crash, data loss; handled by backups and RAID.
  • Storage types: volatile, non-volatile, stable (replicated non-volatile).
5.13

Log-based recovery

  • The log records ⟨T, start⟩, ⟨T, X, Vold, Vnew⟩, ⟨T, commit⟩ and ⟨T, abort⟩ and is written to stable storage before the data (write-ahead logging).
  • Deferred modification: updates applied only after commit; recovery needs REDO only.
  • Immediate modification: updates may reach the database before commit; recovery needs UNDO (uncommitted) and REDO (committed).
  • Recovery: REDO every transaction that has both start and commit in the log; UNDO those with start but no commit.
  • Checkpoints force the log and modified buffers to disk, so recovery starts from the last checkpoint.
5.14

Shadow paging

Two page tables: the current table and the shadow table (a copy made at transaction start and never changed). Writes go to new pages; on commit the shadow pointer is switched to the current table; on failure the current table is discarded. No log is needed, so recovery is fast, but data fragments and garbage collection is needed, and it handles concurrency poorly.
