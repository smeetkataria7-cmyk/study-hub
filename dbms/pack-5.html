5.1

Transaction concept

A transaction is a collection of operations that forms a single logical unit of work. It is a unit of program execution that accesses and possibly updates data items. A program delimits it with begin transaction and end transaction; everything between them is the transaction. A funds transfer from a checking to a savings account is one logical operation made of several steps; it is essential that either all steps occur or none do. It would be unacceptable if the checking account were debited but the savings account never credited.

A database system must therefore (1) execute transactions correctly despite failures and (2) manage the concurrent execution of transactions to avoid inconsistency.

  • read(X): transfers data item X from the database to a local buffer of the transaction.
  • write(X): transfers X from the local buffer back to the database.
  • Example, Tᵢ transfers 50 from account A to account B: read(A); A := A − 50; write(A); read(B); B := B + 50; write(B).
  • In SQL, a transaction begins implicitly with the first SQL-data statement and ends with COMMIT or ROLLBACK.
5.2

ACID properties

To preserve the integrity of data, the database system must maintain four properties, known together as ACID:

PropertyMeaningExample (transfer of 50 from A to B)Ensured by
AtomicityEither all operations of the transaction are reflected in the database, or none areIf the system fails after write(A) but before write(B), A + B no longer holds; the old values are restoredTransaction-management component (undo using the log)
ConsistencyExecution of a transaction in isolation preserves the consistency of the databaseThe sum A + B is the same before and afterThe application programmer / integrity constraints
IsolationEven though transactions run concurrently, each is unaware of the others; the result is as if they ran seriallyA second transaction that reads A and B between the two writes would see a wrong sumConcurrency-control component
DurabilityAfter a transaction completes successfully, its changes persist even if the system failsOnce "transfer done" is shown, a crash cannot undo itRecovery-management component (redo using the log)

Atomicity is violated by the failure example: suppose A = 1000 and B = 2000 and the system fails after write(A); the database holds A = 950 and B = 2000, so the sum is 2950 instead of 3000. To avoid this the system keeps track of the old values of anything a transaction writes and restores them if the transaction does not complete.

5.3

Transaction states

A transaction that completes successfully is committed. One that does not complete is aborted; its changes must be undone, and it is then said to be rolled back. A transaction is always in one of five states:

StateDescription
ActiveInitial state; the transaction stays here while it is executing
Partially committedAfter the final statement has been executed (output may still be in main memory)
FailedAfter discovering that normal execution can no longer proceed
AbortedAfter the transaction has been rolled back and the database restored to its state before the transaction began
CommittedAfter successful completion, when the final output has been safely written to disk

Transitions: Active → Partially committed (last statement done) → Committed (output written to disk). Active or Partially committed → Failed → Aborted. After an abort the system has two options: restart the transaction if the abort was caused by a hardware or software error unrelated to the transaction's logic, or kill it if the cause is an internal logical error that can be fixed only by rewriting the application.

5.4

Implementing atomicity and durability: the shadow-copy scheme

The recovery-management component supports atomicity and durability. The simplest scheme is the shadow copy. It assumes only one transaction is active at a time and that the database is a file on disk with a pointer db-pointer that names the current copy.

  • A transaction that wants to update first makes a complete copy of the database and updates only the copy.
  • If it must abort, the new copy is deleted and the old one remains current.
  • Commit: the OS writes all pages of the new copy to disk; db-pointer is then changed to point to the new copy (a single atomic write); the old copy is deleted.
  • Limits: assumes disks do not fail; useful for a text editor but very inefficient for a large database because every transaction copies the whole database. Shadow paging (5.30) improves on this by copying only the changed pages.
5.5

Why allow concurrent executions

Transaction-processing systems let many transactions run at once. This complicates consistency, but there are two good reasons:

  • Improved throughput and resource utilisation: throughput is the number of transactions completed in a given time. The CPU and the disks can work in parallel: while one transaction waits for I/O, another uses the CPU. Processor and disk idle time falls.
  • Reduced waiting time: with serial execution a short transaction may wait behind a long one, giving unpredictable delays. Running transactions that touch different parts of the database concurrently reduces average response time.
5.6

Schedules: serial and concurrent (worked example)

A schedule is the chronological order in which the instructions of concurrent transactions are executed. It must preserve the order of instructions inside each transaction. Take T1: transfer 50 from A to B, and T2: transfer 10% of A to B (temp := A × 0.1; A := A − temp; B := B + temp), with A = 1000, B = 2000.

  • Serial schedule 1 (T1 then T2): after T1, A = 950, B = 2050; T2 moves 10% of 950 = 95. Final A = 855, B = 2145, sum 3000.
  • Serial schedule 2 (T2 then T1): T2 moves 100 first (A = 900, B = 2100); then T1 moves 50. Final A = 850, B = 2150, sum 3000. Different from schedule 1, but both are correct.
  • Concurrent schedule 3: T1 does read(A), A − 50, write(A); then T2 does read(A), temp, A − temp, write(A); T1 does read(B), B + 50, write(B); then T2 does read(B), B + temp, write(B). It gives the same result as serial schedule 1 (A = 855, B = 2145).
  • Concurrent schedule 4 (bad): T1 reads A and computes A − 50 (not yet written); T2 reads A (still 1000), writes A = 900, reads B; T1 writes A = 950, reads B (2000), writes B = 2050; T2 writes B = 2000 + 100 = 2100. Final A = 950, B = 2100, sum 3050: inconsistent (50 created from nothing). T2's write to A was lost.
  • Lesson: only schedules equivalent to some serial schedule are acceptable (serializable).

5.8

Serializability

A schedule is serializable if it produces the same result as some serial execution of the same transactions. We assume each transaction is correct by itself, so any serial schedule is correct; a serializable schedule is therefore correct too. There are two forms: conflict serializability and view serializability.

Conflicting instructions: two instructions of different transactions conflict if they access the same data item and at least one is a write. Four cases for instructions Iᵢ, Iⱼ on item Q: read–read: order does not matter. read–write and write–read: order matters (one reads the old value, or the new one). write–write: order matters for the value seen by later reads and for the final value.

  • Instructions on different items, or two reads, can be swapped without changing the result.
  • Schedules S and S′ are conflict equivalent if S can be turned into S′ by a series of swaps of non-conflicting adjacent instructions.
  • S is conflict serializable if it is conflict equivalent to a serial schedule.
  • Schedule 3 (T1 and T2 interleaved) is conflict serializable: swapping the non-conflicting read(B)/write(B) of T1 with read(A)/write(A) of T2 yields the serial order T1, T2.
5.9

Testing conflict serializability: the precedence graph

Build the precedence (serialization) graph G = (V, E): V has one node for each transaction; draw an edge Tᵢ → Tⱼ if some instruction of Tᵢ conflicts with a later instruction of Tⱼ (Tᵢ must come before Tⱼ in any equivalent serial order).

  • If G has a cycle: the schedule is not conflict serializable.
  • If G is acyclic: it is conflict serializable, and a topological sort of G gives an equivalent serial order.
  • Procedure: (1) list the read/write operations per data item; (2) for each item, add an edge for every pair (earlier op, later op) from different transactions where at least one is a write; (3) look for a cycle (e.g. depth-first search); (4) if none, topologically sort.
  • Cost of the test: O(n²) for n transactions.

In the second schedule both transactions read A, and then both write it: T2's write comes after T1's read, and T1's write comes after T2's read, so each must precede the other. This is the lost update pattern.

5.11

View serializability

Schedules S and S′ over the same transactions are view equivalent if all three conditions hold:

  • 1. Initial reads: for each item Q, if Tᵢ reads the initial value of Q in S, it also reads the initial value in S′.
  • 2. Reads-from: if Tᵢ reads a value of Q produced by Tⱼ in S, it reads the value produced by the same Tⱼ in S′.
  • 3. Final writes: for each Q, the transaction that does the final write(Q) in S does it in S′.
  • S is view serializable if it is view equivalent to a serial schedule.
  • Relation: every conflict-serializable schedule is view serializable, but some view-serializable schedules are not conflict serializable. Those contain blind writes (writes without a preceding read). Example: r1(Q) w2(Q) w1(Q) w3(Q) is view equivalent to the serial order T1, T2, T3 (T1 reads the initial value, T3 does the final write) but has a cycle T1 → T2 → T1 in its precedence graph.
  • Testing view serializability is NP-complete, so DBMSs enforce the stricter but cheaper conflict serializability.
5.12

Recoverability

If Tᵢ fails we must undo it, and any transaction that depends on it must also be aborted, so schedules must restrict which dependencies are allowed:

TypeDefinitionExample
Recoverable scheduleFor every pair Tᵢ, Tⱼ where Tⱼ reads data written by Tᵢ, Tᵢ commits before Tⱼ commitsNon-recoverable: w8(A) r9(A) c9 c8; T9 committed after reading A from T8, so it cannot be undone if T8 aborts
Cascadeless (ACA) scheduleTⱼ reads a value written by Tᵢ only after Tᵢ commits; avoids cascading rollbacksw1(A) r2(A) w2(A) r3(A): if T1 fails, T2 and T3 must roll back too (cascading rollback)
Strict scheduleNo transaction reads or overwrites a value written by Tᵢ until Tᵢ commits or abortsHeld by strict 2PL; easy recovery by restoring old values

Hierarchy: strict ⊂ cascadeless ⊂ recoverable, and every cascadeless schedule is recoverable. Cascading rollback is undesirable because it undoes a lot of work; most systems require recoverable (preferably cascadeless) schedules.

5.13

Transactions in SQL and isolation levels

SQL has two statements to end a transaction: COMMIT [WORK] ends the current transaction and makes its changes permanent; ROLLBACK [WORK] ends it and undoes its changes. In SQL-92 there is no BEGIN TRANSACTION: a transaction starts with the first SQL-data statement and continues until COMMIT or ROLLBACK (PostgreSQL uses BEGIN; SAVEPOINT marks a point to roll back to). The changes are either fully persistent after COMMIT or have no effect after ROLLBACK, abnormal client termination, or abnormal termination by the DBMS (for example deadlock resolution).

Isolation levelDirty readNon-repeatable readPhantom
Read uncommittedPossiblePossiblePossible
Read committedNot possiblePossiblePossible
Repeatable readNot possibleNot possiblePossible
SerializableNot possibleNot possibleNot possible

Serializable is the highest isolation: the transaction behaves as if run alone. Lower levels allow more concurrency but more anomalies. Set with SET TRANSACTION ISOLATION LEVEL …. Example:

BEGIN;
UPDATE accounts SET balance = balance - 5000 WHERE id = 'A';
UPDATE accounts SET balance = balance + 5000 WHERE id = 'B';
COMMIT;        -- or ROLLBACK; to cancel both updates
5.14

Concurrency-control protocols: overview

A concurrency-control scheme guarantees that every schedule allowed is serializable (and recoverable). The families covered in the syllabus are:

  • Lock-based protocols (two-phase locking, tree protocol).
  • Timestamp-based protocols (timestamp ordering, Thomas' write rule).
  • Validation-based (optimistic) protocols.
  • Multiple granularity locking (intention locks).
  • Multiversion schemes (snapshot isolation).
  • Pessimistic schemes (locking) assume conflicts are likely and prevent them by blocking; optimistic schemes (validation) assume conflicts are rare and check at the end.
5.15

Lock-based protocols: lock modes and compatibility

A transaction must hold a lock on a data item before accessing it, so that access is mutually exclusive. Two modes:

Shared (S) heldExclusive (X) held
Request SGranted (compatible)Wait
Request XWaitWait

Shared lock (S): Tᵢ may read but not write Q (lock-S(Q)). Exclusive lock (X): Tᵢ may read and write Q (lock-X(Q)). unlock(Q) releases it. Only S–S is compatible; if a requested lock conflicts with one held, the requester waits until all incompatible locks are released. Example: T1 (transfer 50 from B to A): lock-X(B), read(B), B := B − 50, write(B), unlock(B), lock-X(A), read(A), A := A + 50, write(A), unlock(A). T2 (display A + B): lock-S(A), read(A), unlock(A), lock-S(B), read(B), unlock(B), display(A + B). Because T1 unlocks B early, T2 can see a state between the two writes, so just locking is not enough: we also need a locking protocol.

5.16

Problems with locking: deadlock and starvation

Deadlock: T3 holds X on B and requests S on A; T4 holds S on A and requests X on B. Each waits for the other forever; neither can proceed. The system must roll back one of them, which releases its locks.

Starvation: T2 holds S on Q and T1 requests X on Q, so T1 waits. Another transaction gets an S lock on Q (compatible with T2's), then another, each releasing quickly, and T1 never gets its X lock. Avoid it by granting a lock on Q in mode M only if (1) no other transaction holds a conflicting lock on Q, and (2) no other transaction is waiting for a lock on Q that requested it earlier (first-come, first-served).

5.17

Two-phase locking (2PL)

The two-phase locking protocol requires each transaction to issue lock and unlock requests in two phases:

  • Growing phase: the transaction may obtain locks but may not release any.
  • Shrinking phase: it may release locks but may not obtain new ones. Once the first lock is released the transaction is shrinking.
  • The lock point is the moment of the last lock acquired. Ordering transactions by lock point gives a serialisability order, so 2PL ensures conflict serializability.
  • Transactions T1 and T2 of 5.15 are not two-phase (they unlock before locking something else); the version that holds all locks to the end is two-phase. Lock conversion: a transaction may upgrade S → X only in the growing phase and downgrade X → S only in the shrinking phase.
  • Disadvantages: (1) 2PL does not prevent deadlock (T3: lock-X(B) … lock-X(A) while T4: lock-S(A) … lock-S(B)). (2) Cascading rollback can occur: T5 writes A and unlocks it before commit, T6 reads A; if T5 fails, T6 must roll back. (3) Not all serializable schedules are possible under 2PL.
5.18

Variants: strict and rigorous 2PL

To avoid cascading rollbacks, 2PL is tightened:

ProtocolRuleGuarantees
Basic 2PLGrowing then shrinking phaseConflict serializable
Strict 2PLHold all exclusive locks until the transaction commits or abortsConflict serializable and cascadeless (strict schedules)
Rigorous (strong strict) 2PLHold all locks (shared and exclusive) until commit or abortSerializable in commit order; most widely used

Strict 2PL stops other transactions from reading or overwriting data written by an uncommitted transaction. Most commercial systems implement strict or rigorous 2PL.

5.19

Graph-based (tree) protocol

If we know the order in which data items will be accessed, we can arrange them in a rooted tree (the database graph) and use the tree protocol. Only lock-X is used. Each transaction Tᵢ may lock an item at most once and must obey:

  • 1. The first lock may be on any item.
  • 2. A later item Q can be locked only if the parent of Q is currently locked by Tᵢ.
  • 3. Items may be unlocked at any time.
  • 4. An item that has been locked and unlocked by Tᵢ cannot be locked again by Tᵢ.
  • Advantages: every legal schedule is conflict serializable and free from deadlock; locks can be released early, giving more concurrency than 2PL.
  • Disadvantages: a transaction may have to lock items it does not use. To reach A and J it must also lock their ancestors B, D and H, increasing locking overhead and waiting. Schedules may also be non-recoverable.
5.20

Timestamp-ordering protocol

Instead of locks, the system picks the serialisability order in advance using timestamps. Each transaction Tᵢ gets a unique timestamp TS(Tᵢ) when it enters the system (system clock or a logical counter); an older transaction has a smaller timestamp. If TS(Tᵢ) < TS(Tⱼ), the schedule must be equivalent to a serial schedule with Tᵢ before Tⱼ. Each data item Q carries two timestamps:

  • W-timestamp(Q): the largest timestamp of any transaction that executed write(Q) successfully.
  • R-timestamp(Q): the largest timestamp of any transaction that executed read(Q) successfully.
  • Tᵢ issues read(Q): if TS(Tᵢ) < W-timestamp(Q), Tᵢ needs a value that was already overwritten → reject, roll back Tᵢ. Otherwise execute and set R-timestamp(Q) = max(R-timestamp(Q), TS(Tᵢ)).
  • Tᵢ issues write(Q): if TS(Tᵢ) < R-timestamp(Q), a later transaction already read the old value → reject, roll back. If TS(Tᵢ) < W-timestamp(Q), Tᵢ is writing an obsolete value → reject, roll back. Otherwise execute and set W-timestamp(Q) = TS(Tᵢ).
  • A rolled-back transaction gets a new timestamp and restarts.
  • Advantages: guarantees conflict serializability (conflicting operations occur in timestamp order) and is deadlock-free (nobody waits). Disadvantages: possible starvation of a long transaction repeatedly restarted by short conflicting ones; can produce non-recoverable schedules.
5.21

Thomas' write rule

In the timestamp protocol a late write is always rejected. Consider T16 (older) and T17 (younger) with schedule r16(Q) w17(Q) w16(Q). T16 is rejected at w16(Q) because TS(T16) < W-timestamp(Q) = TS(T17). But no transaction needs T16's value: T17 has already overwritten it and nobody read it in between, so the rollback is unnecessary. Thomas' write rule modifies the write test:

  • a) If TS(Tᵢ) < R-timestamp(Q): reject write(Q), roll back Tᵢ (a later transaction read the old value).
  • b) If TS(Tᵢ) < W-timestamp(Q): ignore the write (it is obsolete); Tᵢ continues. This is the only difference from basic timestamp ordering.
  • c) Otherwise execute write(Q) and set W-timestamp(Q) = TS(Tᵢ).
  • Result: fewer rollbacks; it permits schedules that are view serializable but not conflict serializable.
5.22

Validation-based (optimistic) protocol

It assumes conflicts are rare, so transactions run without blocking and are checked at the end. Each transaction Tᵢ has three phases:

  • Read phase: Tᵢ reads values from the database but writes only to local temporary variables.
  • Validation phase: Tᵢ tests whether copying its local writes to the database would violate serializability.
  • Write phase: if validation succeeds, the writes are applied; otherwise Tᵢ is rolled back.
  • Timestamps: Start(Tᵢ), Validation(Tᵢ) (end of read phase), Finish(Tᵢ) (end of write phase). The serialisability order is the order of validation timestamps.
  • Validation test for Tⱼ: for every Tᵢ with TS(Tᵢ) < TS(Tⱼ) one of these must hold: (1) Finish(Tᵢ) < Start(Tⱼ) (Tᵢ finished before Tⱼ began); or (2) the items written by Tᵢ do not intersect the items read by Tⱼ and Tᵢ finishes its write phase before Tⱼ starts validation (Start(Tⱼ) < Finish(Tᵢ) < Validation(Tⱼ)).
  • Advantages: no cascading rollbacks (writes happen only after validation); no deadlock; good when conflicts are rare. Disadvantage: long transactions may starve if repeatedly restarted by short conflicting ones.
5.23

Multiple granularity and intention locks

Locking a whole table for one row is too coarse, and locking each row for a table scan is too costly. Multiple granularity lets locks be taken at different levels of a tree: database → table (file) → page (block) → record (tuple). Besides S and X, intention locks are placed on ancestors to show that a descendant is locked:

ModeMeaning
IS (intention shared)Some descendant will be locked in S mode
IX (intention exclusive)Some descendant will be locked in X mode
SIX (shared + intention exclusive)The node is locked in S mode and some descendants will be locked in X mode

Rules: to lock a node in S or IS mode, first lock its parent in IS or IX; to lock a node in X, IX or SIX mode, first lock its parent in IX or SIX. Lock from the root downward and unlock from the leaf upward. Compatibility: IS is compatible with IS, IX, S and SIX; IX with IS and IX; S with IS and S; SIX with IS only; X with nothing. This lets a table scan (S on the table) and row updates (IX on the table, X on rows) coexist only where they do not conflict.

5.24

Multiversion schemes

Keep several versions of each data item so that a read never has to wait or be rejected: it simply reads the version appropriate to its timestamp. Multiversion timestamp ordering: each write(Q) creates a new version Qₖ with its own W-timestamp and R-timestamp; a read(Q) by Tᵢ returns the version with the largest write timestamp ≤ TS(Tᵢ); a write(Q) is rejected only if a later transaction has already read the version it would replace. Snapshot isolation (used by PostgreSQL and Oracle) gives each transaction a consistent snapshot, so readers never block writers; updates conflict only if two transactions write the same item. The cost is extra storage and garbage collection of old versions.

5.25

Deadlock handling: the problem and prevention

A set of transactions {T0, T1, …, Tn} is deadlocked if T0 waits for an item held by T1, T1 for one held by T2, …, and Tn for one held by T0. None can proceed. There are two ways to deal with it: prevention (never enter a deadlock) and detection and recovery.

Prevention schemes:

  • Ordering / all-at-once: lock all items before execution begins, or impose an order on locking. Hard to predict the items needed and gives low utilisation, since items stay locked but unused.
  • Wait–die (non-preemptive): when Tᵢ requests an item held by Tⱼ, Tᵢ may wait only if it is older (smaller timestamp); otherwise Tᵢ is rolled back (dies). Example with timestamps T1 = 5, T2 = 10, T3 = 15: T1 requests an item held by T2: T1 is older, so it waits. T3 requests an item held by T2: T3 is younger, so it dies.
  • Wound–wait (preemptive): when Tᵢ requests an item held by Tⱼ, Tᵢ wounds Tⱼ (Tⱼ is rolled back) if Tᵢ is older; if Tᵢ is younger it waits. Same example: T1 requests an item held by T2: T1 is older, so T2 is rolled back. T3 requests an item held by T2: T3 is younger, so it waits.
  • Both schemes avoid starvation because the rolled-back transaction keeps its original timestamp and eventually becomes the oldest; but both may roll back needlessly.
  • Timeout-based: a transaction waits at most a fixed time for a lock, then rolls itself back and restarts. Simple and good for short transactions, but it is hard to choose the time (too long delays after a deadlock; too short rolls back without a deadlock) and starvation is possible.
5.26

Deadlock detection and recovery

Let the system periodically build a wait-for graph G = (V, E): V is the set of transactions; an edge Tᵢ → Tⱼ exists when Tᵢ is waiting for a data item held by Tⱼ. The edge is removed when Tⱼ releases the item. A deadlock exists if and only if the wait-for graph has a cycle; every transaction on the cycle is deadlocked.

Example: T25 waits for T26 and T27, T27 waits for T26, and T26 waits for T28: edges T25 → T26, T25 → T27, T27 → T26, T26 → T28. There is no cycle, so no deadlock. If T28 now also waits for T27 (edge T28 → T27), the cycle T27 → T26 → T28 → T27 appears: deadlock.

Recovery has three actions:

  • Victim selection: roll back the transaction with minimum cost. Factors: how long it has run and how long it will still run; how many items it has used and still needs; how many transactions would be involved in its rollback.
  • Rollback: total (abort and restart) or partial (roll back only as far as needed to release the contested lock; needs more bookkeeping).
  • Starvation: the same transaction may be chosen repeatedly; limit how often a transaction can be a victim, e.g. include the number of rollbacks in the cost.
5.27

Insert, delete, the phantom phenomenon and index locking

Besides read and write, transactions use delete(Q) and insert(Q). A delete conflicts with any read or write of Q after it, and an insert conflicts with any later access of the same item.

Phantom phenomenon: a transaction that scans a relation (sum the balances of all accounts at Perryridge) and one that inserts a tuple (a new Perryridge account) conflict even though they touch no common tuple. With tuple locks only, a non-serializable schedule can result.

  • Solution 1: associate a data item with the relation itself, representing "which tuples exist". Scanning transactions take a shared lock on it; insert and delete take an exclusive lock. Correct, but allows very little concurrency for inserts and deletes.
  • Solution 2: index locking: lock the index buckets (or key ranges) a predicate touches, which prevents phantoms with higher concurrency.
  • Concurrency in index structures (B⁺-trees): index nodes are accessed far more often than data items, so two-phase locking them would cripple concurrency. It is acceptable to have non-serializable access to an index as long as the index stays accurate. Crabbing: lock the root in shared mode, then lock a child, then release the parent once the child is safe (will not split or merge). Also called lock coupling.
5.28

Failure classification and storage types

Recovery is the job of restoring the database to a correct state after a failure. Failures fall into three groups (plus others such as communication or application errors and human mistakes):

ParameterTransaction failureSystem crashDisk failure
ScopeOne or more transactionsThe whole running DBMSPersistent storage
CausesLogical error (bad input, constraint violation, divide by zero); system error (deadlock, timeout, resource limit)Power failure, OS crash, DBMS software or hardware faultHead crash, controller failure, failed transfer, corruption
Volatile memoryUsually retainedLostDepends
Stored databaseAvailableUsually survivesMay be lost
RecoveryUndo (rollback) of the transactionUndo uncommitted and redo committed work from the logRestore from backup (archive) and apply archived logs

Storage types: volatile storage (main memory) loses data in a crash; non-volatile storage (disk, tape) survives crashes but can fail; stable storage is an idealised store that never loses data, approximated by keeping several copies on separate disks. The fail-stop assumption says that a crash stops processing and does not corrupt non-volatile storage. Human error such as a DELETE without WHERE that has been committed cannot be rolled back; it needs backup restoration or point-in-time recovery.

5.29

Recovery and atomicity: the bank example

Transaction T transfers 5,000 from A (20,000) to B (10,000). If the system crashes after the debit but before the credit, the database holds A = 15,000 and B = 10,000: the total is 25,000, not 30,000. A recovery system must make sure this incomplete transaction does not become permanent and restore A = 20,000, B = 10,000.

  • Objectives: maintain atomicity (roll back incomplete transactions); maintain durability (committed results survive failures); restore consistency; prevent permanent data loss using logs and backups; let the DBMS resume normal operation.
  • Atomicity vs durability: atomicity concerns incomplete transactions and is supported by UNDO; durability concerns committed transactions and is supported by REDO and a persistent log.
  • Two schemes are covered: log-based recovery (deferred and immediate modification, with checkpoints) and shadow paging.
5.30a

Log-based recovery: the log

The log is the most widely used structure for recording database modifications: a sequence of log records, one for each update and for important events. It is kept on stable storage. Record types:

  • <Tᵢ start>: transaction Tᵢ has started.
  • <Tᵢ, Xⱼ, V1, V2> (update record): Tᵢ wrote item Xⱼ, whose value was V1 before and will be V2 after. It holds the transaction id, the data-item id, the old value and the new value.
  • <Tᵢ commit>: Tᵢ has committed. <Tᵢ abort>: Tᵢ has aborted.
  • Write-ahead logging (WAL): the log record for an update must reach stable storage before the updated data block does.
  • The old value allows undo; the new value allows redo.
5.30b

Deferred database modification (with the T0, T1 example)

Deferred modification records all updates in the log but defers executing the writes until the transaction partially commits. If the system crashes before that, or the transaction aborts, the log is simply ignored (no undo is ever needed). Update records need only the new value. All log records are forced to stable storage before the deferred writes begin.

Example: T0 transfers 50 from A to B; T1 withdraws 100 from C; initial A = 1000, B = 2000, C = 700, executed in the order T0, T1. The log is: <T0 start>, <T0, A, 950>, <T0, B, 2050>, <T0 commit>, <T1 start>, <T1, C, 600>, <T1 commit>. Recovery procedure: redo(Tᵢ) sets every item written by Tᵢ to its new value. Tᵢ must be redone iff the log has both <Tᵢ start> and <Tᵢ commit>.

  • Crash case (a): after <T0, B, 2050>, before <T0 commit>: no commit record, so no redo; A = 1000, B = 2000, C = 700 remain.
  • Crash case (b): after <T0 commit> but before <T1 commit>: redo(T0) gives A = 950, B = 2050; T1 has no commit record and is ignored: C = 700.
  • Crash case (c): after <T1 commit>: redo(T0) and redo(T1): A = 950, B = 2050, C = 600.
5.30c

Immediate database modification (with the same example)

Immediate modification lets writes reach the database while the transaction is still active. Update records therefore need both the old and new values: <Tᵢ, X, V1, V2>. The log for T0 and T1 is: <T0 start>, <T0, A, 1000, 950>, <T0, B, 2000, 2050>, <T0 commit>, <T1 start>, <T1, C, 700, 600>, <T1 commit>.

Recovery uses two procedures: undo(Tᵢ) restores all items written by Tᵢ to their old values; redo(Tᵢ) sets them to the new values. Tᵢ must be undone if the log has <Tᵢ start> but no <Tᵢ commit>; Tᵢ must be redone if the log has both <Tᵢ start> and <Tᵢ commit>. Undo is performed before redo.

  • Case 1: crash after write(B) of T0 (no commit): undo(T0): A = 1000, B = 2000.
  • Case 2: crash after the update record of T1 but before <T1 commit>: undo(T1) (C back to 700) and redo(T0): A = 950, B = 2050, C = 700. The undo of T1 is performed before the redo of T0.
  • Case 3: crash after <T1 commit>: redo(T0) and redo(T1): A = 950, B = 2050, C = 600.
5.30d

Checkpoints

Without checkpoints, recovery must search the whole log, which is slow, and most transactions that would be redone have already written their updates. A checkpoint performed periodically does, in order:

  • 1. Output all log records in main memory to stable storage.
  • 2. Output all modified buffer blocks to disk.
  • 3. Write a <checkpoint> record to the log on stable storage.
  • A transaction Tᵢ that committed before the checkpoint (its <Tᵢ commit> precedes <checkpoint>) needs no redo, since its updates were written to disk before or during the checkpoint.
  • Recovery with a checkpoint: scan the log backwards to the most recent <checkpoint>, then further back to find the most recent <Tᵢ start> before it. Let T be Tᵢ and all transactions that started after Tᵢ. For immediate modification: undo every Tₖ in T with no <Tₖ commit>; redo every Tₖ in T with a <Tₖ commit>. With deferred modification no undo is needed.
5.31

Shadow paging

Shadow paging is an alternative to log-based recovery. The database is divided into fixed-length pages, stored anywhere on disk, and a page table with n entries points to the n pages. Two page tables are kept during a transaction:

  • Current page table: used for all reads and writes; changes as the transaction writes.
  • Shadow page table: a copy of the page table at the start of the transaction; never changed during the transaction and kept in non-volatile storage.
  • write(X) on page i: (1) if page i is not in memory, input it; (2) if this is the first write to page i by this transaction: find an unused disk page, remove it from the free-page list, copy page i into it, and make entry i of the current page table point to the new page; (3) assign the new value to X in the buffer page. Example: a transaction writes to the 4th of 10 pages; the current table entry 4 now points to a new page, while the shadow table still points to the old one.
  • Commit: (1) output all modified buffer pages to disk; (2) output the current page table to disk; (3) overwrite the fixed location holding the address of the shadow page table with the address of the current page table. The current table is now the new shadow table. A crash before step 3 leaves the old shadow table (state before the transaction); a crash after step 3 keeps the new state.
  • Recovery: just use the shadow page table; no undo or redo is needed.
  • Advantages: fewer disk accesses than log-based recovery; no log-record overhead; recovery after a crash is much faster.
  • Disadvantages: commit overhead (data pages, current table and its address must all be written); data fragmentation (pages move on update, so related pages are no longer together); garbage collection (old page versions become inaccessible and must be reclaimed periodically); hard to extend to concurrent transactions.

5.33

Backup, disk failure and advanced recovery

Log-based recovery survives crashes but not the loss of the disk holding the database. For disk failure and human error the DBMS relies on:

  • Backups (archival dumps): periodically copy the database to tape or another disk (a full dump, with incremental dumps between).
  • Archive of the log: after restoring the latest dump, replay the archived log to redo committed transactions up to the point of failure (point-in-time recovery).
  • Remote backup / hot standby: a second site receives the log and takes over if the primary site fails.
  • ARIES (the recovery algorithm used in practice) uses write-ahead logging, a redo pass that repeats history, and an undo pass for uncommitted transactions with compensation log records, plus fuzzy checkpoints.
  • Recovery is possible up to the point of failure only if the backup and log are intact.

Q1

What is a transaction? Explain the ACID properties with an example.

Show model answer

A transaction is a collection of operations that forms a single logical unit of work: for example, a transfer of 50 from account A to B is read(A); A := A − 50; write(A); read(B); B := B + 50; write(B).

PropertyExplanationExample
AtomicityAll operations are reflected, or noneA failure after write(A) must restore A
ConsistencyA transaction run alone preserves database consistencyA + B is unchanged
IsolationConcurrent transactions are unaware of one anotherNo other transaction sees A debited but B not credited
DurabilityCommitted changes survive failuresAfter commit, a crash does not lose the transfer

Atomicity is the responsibility of the transaction manager, isolation of concurrency control, durability of recovery management; consistency is the programmer's responsibility.

Q2

Draw and explain the state diagram of a transaction.

Show model answer

States: Active (executing) → Partially committed (last statement executed) → Committed (all output safely on disk). From Active or Partially committed a transaction can go to Failed (normal execution cannot continue), then Aborted (rolled back; database restored to the state before the transaction).

  • After an abort the system can restart the transaction (hardware or software error not caused by its logic) or kill it (internal logical error that needs the program rewritten).
  • Committed and Aborted are the two terminated states.
Q3

Why is concurrent execution of transactions allowed? What problems can it cause?

Show model answer

Reasons: improved throughput and resource utilisation (CPU and disk work in parallel) and reduced waiting time and average response time (short transactions do not wait behind long ones).

Problems: lost update, dirty read, non-repeatable read, phantom read and incorrect summary, which can leave the database inconsistent. Example: schedule 4 of the transfer example ends with A = 950 and B = 2100, sum 3050 instead of 3000.

Q4

What is a schedule? Differentiate serial and serializable schedules with an example.

Show model answer

A schedule is the chronological order of execution of the instructions of a set of transactions, preserving the order inside each transaction. A serial schedule runs one transaction completely before the next starts (for n transactions, n! serial schedules). A serializable schedule is an interleaved schedule whose result equals that of some serial schedule.

Example: T1 (transfer 50) and T2 (transfer 10%) with A = 1000, B = 2000: serial T1, T2 gives A = 855, B = 2145; serial T2, T1 gives A = 850, B = 2150; an interleaving where T1 writes A, T2 writes A, T1 writes B, then T2 writes B gives 855 and 2145 (serializable). The interleaving that gives 950 and 2100 is not serializable.

Q5

Explain conflict serializability. How is it tested using a precedence graph?

Show model answer

Two instructions of different transactions conflict if they use the same item and at least one is a write. A schedule is conflict serializable if it can be turned into a serial schedule by swapping adjacent non-conflicting instructions.

  • Draw a node per transaction; draw Tᵢ → Tⱼ if an instruction of Tᵢ conflicts with a later instruction of Tⱼ.
  • If the graph has a cycle, the schedule is not conflict serializable; otherwise it is, and a topological order is an equivalent serial order.

Example: r1(A) r2(A) w1(A) w2(A) gives T1 → T2 (r1(A), w2(A)) and T2 → T1 (r2(A), w1(A)): a cycle, so not conflict serializable.

Q6

Explain view serializability and compare it with conflict serializability.

Show model answer

S and S′ are view equivalent if (1) each transaction that reads the initial value of Q in S does so in S′; (2) each read(Q) reads the value written by the same transaction in both; (3) the transaction doing the final write(Q) is the same. S is view serializable if it is view equivalent to a serial schedule.

  • Every conflict-serializable schedule is view serializable; the converse is false (schedules with blind writes, e.g. r1(Q) w2(Q) w1(Q) w3(Q)).
  • Testing view serializability is NP-complete; conflict serializability is tested in polynomial time, so systems use it.
Q7

What are recoverable and cascadeless schedules? Why is cascading rollback undesirable?

Show model answer

A schedule is recoverable if whenever Tⱼ reads data written by Tᵢ, Tᵢ commits before Tⱼ. It is cascadeless if Tⱼ reads a value written by Tᵢ only after Tᵢ commits. Every cascadeless schedule is recoverable.

Non-recoverable example: w8(A) r9(A) c9 c8; T9 has committed after reading uncommitted data, so if T8 aborts it cannot be undone. Cascading example: T1 writes A, T2 reads A and writes A, T3 reads A; if T1 fails, T2 and T3 must roll back too. A single failure undoing a chain of transactions wastes a lot of work.

Q8

Explain the lock-based protocol. What are shared and exclusive locks? Give the compatibility matrix.

Show model answer

A transaction must obtain a lock before accessing an item, so that access is mutually exclusive. Shared (S) lock: read only. Exclusive (X) lock: read and write.

S heldX held
Request SYesNo
Request XNoNo

A request is granted only if it is compatible with all locks already held on the item; otherwise the transaction waits. Locking alone does not guarantee serializability: a locking protocol (such as 2PL) is needed.

Q9

Explain the two-phase locking protocol. State its advantages and disadvantages. What are strict and rigorous 2PL?

Show model answer
  • Growing phase: acquire locks, release none. Shrinking phase: release locks, acquire none.
  • Advantage: guarantees conflict serializability (serial order = order of lock points).
  • Disadvantages: does not prevent deadlock; may cause cascading rollbacks; limits concurrency.
  • Strict 2PL: hold all exclusive locks until commit/abort (cascadeless). Rigorous 2PL: hold all locks until commit/abort.
Q10

Explain the timestamp-ordering protocol. What are R-timestamp and W-timestamp?

Show model answer

Each transaction gets a unique timestamp TS(Tᵢ) at entry; the serial order must follow timestamps. For each item Q: W-timestamp(Q) = largest timestamp of any transaction that wrote Q successfully; R-timestamp(Q) = largest timestamp of any successful reader.

  • read(Q): if TS(Tᵢ) < W-timestamp(Q) reject and roll back; else execute and set R-timestamp(Q) = max(R-timestamp(Q), TS(Tᵢ)).
  • write(Q): if TS(Tᵢ) < R-timestamp(Q) reject; if TS(Tᵢ) < W-timestamp(Q) reject; else execute and set W-timestamp(Q) = TS(Tᵢ).
  • Rolled-back transactions restart with a new timestamp. The protocol is deadlock-free but can starve long transactions and produce non-recoverable schedules.
Q11

What is Thomas' write rule? How does it differ from the timestamp-ordering protocol?

Show model answer

In basic timestamp ordering, a write(Q) with TS(Tᵢ) < W-timestamp(Q) causes Tᵢ to be rolled back. Under Thomas' write rule that write is simply ignored (it is an obsolete value that no later transaction would read), and Tᵢ continues. The test TS(Tᵢ) < R-timestamp(Q) still causes a rollback. The rule reduces unnecessary rollbacks and allows view-serializable schedules that are not conflict serializable.

Q12

Explain the validation-based (optimistic) protocol.

Show model answer

Each transaction has three phases: read (reads database, writes to local copies), validation (checks whether its writes can be applied without violating serializability), write (applies the writes if validation succeeded; else rollback). Timestamps Start, Validation, Finish are recorded. For every Tᵢ with TS(Tᵢ) < TS(Tⱼ), one of these must hold for Tⱼ to validate: (1) Finish(Tᵢ) < Start(Tⱼ); or (2) Tᵢ's write set does not intersect Tⱼ's read set and Finish(Tᵢ) < Validation(Tⱼ). It avoids cascading rollbacks and deadlock but may starve long transactions.

Q13

What is a deadlock? Explain prevention using wait–die and wound–wait.

Show model answer

A deadlock is a state where every transaction in a set waits for a data item held by another in the set, so none can proceed. Prevention uses timestamps:

SchemeTᵢ requests an item held by TⱼType
Wait–dieTᵢ older (smaller TS): waits. Tᵢ younger: dies (rolled back)Non-preemptive
Wound–waitTᵢ older: wounds Tⱼ (Tⱼ rolled back). Tᵢ younger: waitsPreemptive

With TS(T1) = 5, T2 = 10, T3 = 15 and T2 holding the item: wait–die: T1 waits, T3 dies. Wound–wait: T1 wounds T2, T3 waits. Rolled-back transactions keep their original timestamps, so starvation is avoided.

Q14

How are deadlocks detected and recovered from? What is a wait-for graph?

Show model answer

A wait-for graph has transactions as nodes and an edge Tᵢ → Tⱼ when Tᵢ waits for a lock held by Tⱼ. A deadlock exists iff the graph has a cycle. The system runs a detection algorithm periodically.

  • Victim selection: minimum-cost transaction (progress made, items used, items needed, number of transactions affected).
  • Rollback: total or partial.
  • Starvation: avoid choosing the same victim repeatedly by counting rollbacks in the cost.
Q15

What is the phantom phenomenon? How can it be prevented?

Show model answer

A transaction scanning a relation (sum of balances of accounts at one branch) and another inserting a new tuple (a new account at that branch) conflict even though they share no tuple, so tuple-level locking can give a non-serializable schedule. Prevention: lock a data item representing the relation (shared by scans, exclusive by inserts and deletes), or index locking (lock the index buckets or key ranges involved), which gives higher concurrency.

Q17

Explain log-based recovery. Differentiate deferred and immediate database modification with an example.

Show model answer

The log records every update as <Tᵢ, X, V1, V2> plus <Tᵢ start>, <Tᵢ commit>, <Tᵢ abort>, on stable storage. After a crash the log decides what to undo and redo: Tᵢ is undone if <Tᵢ start> is present without <Tᵢ commit>, and redone if both are present.

Deferred modificationImmediate modification
When writes reach the databaseOnly after the transaction partially commitsWhile the transaction is active
Log record<Tᵢ, X, new><Tᵢ, X, old, new>

Example: T0 (A: 1000 → 950, B: 2000 → 2050) committed, T1 (C: 700 → 600) not committed at the crash. Both schemes finish with A = 950, B = 2050, C = 700.

Q18

Explain checkpoints. How do they speed up recovery?

Show model answer

A checkpoint (1) writes all log records in memory to stable storage, (2) writes all modified buffer blocks to disk, (3) writes a <checkpoint> log record. A transaction that committed before the checkpoint needs no redo. At recovery the system finds the most recent checkpoint and the last transaction that started before it; only that transaction and those that started after it (set T) are considered: undo those without a commit record, redo those with one. The whole log need not be scanned.

Q19

Explain shadow paging. What are its advantages and disadvantages?

Show model answer

The database is divided into pages addressed through a page table. During a transaction two tables are kept: the shadow page table (not modified, in non-volatile storage) and the current page table (used for all access). On the first write to a page, a copy is made on a free disk page and the current table is pointed at it. Commit: write modified pages, write the current table, then switch the pointer to it. Crash before the switch: the shadow table gives the old state; after: the new state.

  • Advantages: no log overhead; fewer disk accesses; no undo/redo, fast recovery.
  • Disadvantages: commit overhead, data fragmentation, garbage collection, hard to use with concurrent transactions.
Q20

Explain multiple-granularity locking and intention locks.

Show model answer

Data are organised as a tree (database, table, page, record). A transaction can lock any node, which implicitly locks all descendants. Intention modes IS, IX and SIX are set on ancestors to show that descendants are locked in S or X mode. To lock a node in S or IS, hold IS or IX on its parent; to lock in X, IX or SIX, hold IX or SIX on its parent. Locking proceeds root to leaf and unlocking leaf to root. This lets a transaction lock a whole table cheaply while another locks individual rows safely.

Show solution

P9

Two-phase or not?

Which of these transactions is two-phase? (a) lock-X(B), read(B), write(B), unlock(B), lock-X(A), read(A), write(A), unlock(A); (b) lock-X(B), read(B), write(B), lock-X(A), read(A), write(A), unlock(B), unlock(A).

P10

Wait-for graph

T1 waits for T2, T2 waits for T3, T3 waits for T4, T4 waits for T2. Is there a deadlock? Which transactions are deadlocked and which can be chosen as victim?

Show solution
  1. Edges: T1 → T2, T2 → T3, T3 → T4, T4 → T2.
  2. Cycle: T2 → T3 → T4 → T2. So the system is in deadlock.
  3. T2, T3 and T4 are deadlocked. T1 is only waiting for T2 and is not on the cycle (it will proceed once the cycle is broken).

P11

Wait–die and wound–wait

Show solution
  1. Wait–die: (a) T1 is older than T2, so T1 waits. (b) T3 is younger than T2, so T3 dies (is rolled back).
  2. Wound–wait: (a) T1 is older, so it wounds T2: T2 is rolled back and T1 gets Q. (b) T3 is younger, so T3 waits.
Wait–die: T1 waits, T3 dies. Wound–wait: T2 is rolled back for T1, T3 waits.
P12

Deferred modification recovery

Log (deferred modification): <T1 start>, <T1, A, 50>, <T1 commit>, <T2 start>, <T2, B, 70>, <T2 commit>, <T3 start>, <T3, C, 90> (crash). Which transactions are redone? What are A, B, C afterwards if they were 10, 20, 30 originally?

Show solution
  1. Redo rule: <Tᵢ start> and <Tᵢ commit> both present.
  2. T1: start and commit: redo (A = 50). T2: start and commit: redo (B = 70). T3: start only: ignored (no commit); C stays 30.
  3. Deferred modification never wrote T3's changes to the database, so no undo is needed.
Redo T1 and T2; A = 50, B = 70, C = 30.
P13

Immediate modification recovery

Log (immediate modification): <T1 start>, <T1, A, 10, 50>, <T1 commit>, <T2 start>, <T2, B, 20, 70>, <T2 commit>, <T3 start>, <T3, C, 30, 90> (crash, and the database already contains C = 90). Which operations are performed and what are the final values?

Show solution
  1. T1 and T2 have start and commit: redo(T1), redo(T2) (A = 50, B = 70).
  2. T3 has start but no commit: undo(T3) restores the old value, C = 30.
  3. Order: undo uncommitted first (undo T3), then redo committed (T1, T2).
undo(T3); redo(T1), redo(T2); A = 50, B = 70, C = 30.
P14

Recovery with a checkpoint

Log: <T1 start>, <T1, A, 5, 6>, <T1 commit>, <T2 start>, <T2, B, 7, 8>, <checkpoint>, <T2 commit>, <T3 start>, <T3, D, 1, 2>, <T4 start>, <T4, C, 9, 10>, <T4 commit> (crash). Immediate modification. Which transactions are undone and redone?

Show solution
  1. Scan back to the last <checkpoint>, then further back to the nearest <start>: it is <T2 start>. So T2 is the most recent transaction that started before the checkpoint, and T = {T2, T3, T4} (T2 and all that started after it).
  2. T1 committed before the checkpoint: ignored (its updates are on disk).
  3. T2: commit present: redo. T4: commit present: redo. T3: no commit: undo (restore D = 1).
Undo T3; redo T2 and T4; T1 untouched.
P15

Shadow paging walk-through

A database has 10 pages. A transaction writes to page 4. Describe the page tables before and after the write, at commit and after a crash before commit.

Show solution
  1. Start: the shadow and current page tables are identical (entry i → page i on disk).
  2. The write to page 4: find a free disk page (say 11), copy page 4 into it and change current table entry 4 → page 11; the shadow table still points entry 4 → page 4 (old data).
  3. Commit: write page 11 to disk, write the current table, then switch the fixed pointer to the current table. It becomes the new shadow table; page 4 is now garbage.
  4. Crash before the pointer switch: on restart use the shadow table: entry 4 → page 4, the old state. No undo needed.
The shadow table preserves the old state until the single pointer switch at commit.
P16

Isolation levels

For each anomaly, name the lowest isolation level that prevents it: (a) dirty read, (b) non-repeatable read, (c) phantom.

Show solution
  1. (a) Read committed prevents dirty reads.
  2. (b) Repeatable read prevents non-repeatable reads (and dirty reads).
  3. (c) Serializable prevents phantoms as well.
(a) Read committed, (b) Repeatable read, (c) Serializable.
P17

Intention locks

A transaction wants an S lock on a whole table and another wants an X lock on one row of the same table. Can they run together? What locks are taken?

Show solution
  1. T1 (table scan): S on the table (after IS on the database).
  2. T2 (row update): IX on the database and on the table, then X on the row.
  3. S and IX conflict at the table node (S is compatible with IS and S only). T2 must wait until T1 releases the table lock.
  4. If T1 instead read single rows (IS on the table, S on rows), T2's IX would be compatible with IS and both could proceed on different rows.
No: S on the table conflicts with IX on the table, so the row updater waits.
