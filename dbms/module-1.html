Database concepts

Why we use a DBMS, its architecture, languages and NoSQL.
1.1

Database, DBMS and purpose

A database is an organised collection of related data; a DBMS is the software that creates, stores, queries and protects it. A plain file-processing system suffers from:

  • Redundancy and inconsistency — the same data is copied in many files.
  • Difficulty in accessing data (a new query needs a new program), isolation of data in different formats.
  • Integrity problems, atomicity problems (a failure leaves a half-done update), concurrent-access anomalies, and weak security.
1.2

Advantages of using a DBMS

  • Controlled redundancy and consistency, data sharing, integrity constraints.
  • Security and authorisation, backup and recovery, concurrent access.
  • Data independence, standard query language, reduced application development time.

1.4

DBMS system architecture (three-schema)

  • External level (view): what each user sees; many views.
  • Conceptual (logical) level: the whole database — entities, attributes, relationships, constraints; one schema.
  • Internal (physical) level: files, indexes, storage structures.
  • Components: query processor (DDL interpreter, DML compiler, query evaluation engine) and storage manager (buffer manager, file manager, authorisation, transaction manager).
1.5

Data independence

  • Physical data independence: change the internal schema (new index, file organisation) without changing the conceptual schema.
  • Logical data independence: change the conceptual schema (add an attribute) without changing the external views or programs. It is harder to achieve.
1.6

Data models

  • Hierarchical (tree) and network (graph) — early models with pointers.
  • Relational — tables of rows and columns; the dominant model.
  • Entity-Relationship — a conceptual design model.
  • Object-oriented / object-relational, and semi-structured (XML, JSON) and NoSQL models.
1.7

1.8

Database users and administrator

  • Naive users (use ready applications), application programmers, sophisticated users (write queries / analysts), specialised users (CAD, expert systems).
  • Database administrator (DBA): schema definition, storage structure, authorisation, backup and recovery, performance tuning and monitoring.
1.9

Introduction to NoSQL databases

"Not only SQL": non-relational stores built for scale-out, flexible schemas and high availability.

  • Key-value (Redis, DynamoDB), document (MongoDB, JSON), column-family (Cassandra, HBase), graph (Neo4j).
  • CAP theorem: a distributed store can guarantee only two of consistency, availability and partition tolerance.
  • BASE (basically available, soft state, eventually consistent) versus relational ACID.
  • Use for big data, real-time web apps and unstructured data; use SQL where strong consistency and joins matter.
