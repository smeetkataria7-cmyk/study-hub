Experiment 1: Problem definition and ER/EER diagram

Aim: formulate a problem definition and draw an ER/EER diagram.

Theory to know

  • ER model: a conceptual (high-level) data model showing the logical structure of a database as entities, attributes and relationships.
  • Entity: a real-world object (Employee). Entity set: entities of the same type. It becomes a table.
  • Relationship: an association between entities (Employee WORKS_FOR Department). Relationship set: relationships of the same type.
  • Attribute: a property of an entity. Types:
    • Simple/atomic vs composite (name = fname + mname + lname)
    • Single-valued vs multivalued (phone numbers)
    • Derived (age from birthdate)
    • Key attribute (ssn), which is unique
  • Weak entity: has no key of its own and depends on a strong (owner) entity. Example: Dependent depends on Employee. It has a partial key (discriminator) plus the owner's key.
  • Mapping cardinality: 1:1, 1:N, N:1, M:N.
  • Participation: total (every entity must participate) or partial (some may not).

EER (extended ER) concepts

  • Specialization: top-down. Split an entity set into sub-groups that have their own extra attributes (Person → Customer with rating, Employee with salary).
  • Generalization: bottom-up. Combine entity sets that share attributes into a higher-level one (Customer + Employee → Person, sharing name, address, age).
  • Aggregation: treat a relationship as a higher-level entity so it can take part in another relationship.
  • Constraints on specialization:
    • Disjoint: an entity belongs to at most one subclass.
    • Overlapping: an entity can belong to more than one subclass.
    • Total: every superclass entity must be in some subclass.
    • Partial: it may be in none.
  • Union / category: a subclass whose members come from a union of different superclasses.

IN YOUR MANUAL Explain total and partial participation with an example.

Total: every entity in the set must take part in the relationship. Partial: only some do.

Example: Employee WORKS_FOR Department. Every employee must belong to a department, so Employee has total participation (double line). Not every employee manages a department, so in MANAGES Employee has partial participation (single line). Department has total participation in MANAGES because every department has a manager.

Total participation maps to a NOT NULL foreign key in the relational model.

Why do we formulate a problem definition before drawing the ER diagram?

It gives a detailed description of the problem domain, so entities, attributes, relationships and constraints can be picked out easily. Nouns usually become entities or attributes, and verbs become relationships. It also helps find missing functional dependencies, which are needed later to reach the right normal form.

Steps to draw an ER/EER diagram?
  1. Identify entities (real-world objects).
  2. Identify attributes and their types, and mark the keys.
  3. Identify relationships and their cardinality and participation.
  4. Apply specialization, generalization and aggregation where needed.
  5. Draw the diagram.
What is a weak entity? Give an example.

An entity that cannot be uniquely identified by its own attributes alone. It depends on an owner (strong) entity through an identifying relationship. Example: Dependent(depname, relation) depends on Employee. Its key is (Employee.ssn + depname). It is drawn with a double rectangle, and the identifying relationship with a double diamond.

Types of keys?
  • Super key: any set of attributes that uniquely identifies a row.
  • Candidate key: a minimal super key.
  • Primary key: the candidate key chosen to identify rows.
  • Alternate key: a candidate key that was not chosen.
  • Composite key: a key made of more than one attribute.
  • Foreign key: an attribute that references the primary key of another table.
Difference between a composite attribute and a multivalued attribute?

Composite: one value that can be split into sub-parts (address = street + city + pin). Multivalued: several values for one entity (phone numbers). In the relational model, composite becomes separate columns, and multivalued becomes a separate table.

Disjoint vs overlapping specialization?

Disjoint: at most one subclass per entity (a Person is either Student or Faculty). Overlapping: several subclasses are possible (a Person can be both Student and Employee).

What is aggregation and why is it needed?

ER cannot show a relationship between a relationship and an entity. Aggregation wraps a relationship set into a higher-level entity so it can take part in another relationship. Example: Employee WORKS_ON Project is aggregated, and then it is related to Manager through MONITORS.

Experiment 2: Mapping the EER diagram to the relational model

Aim: convert your ER/EER diagram into relational schemas.

Relational model terms

  • Relation = table. Tuple = row. Attribute = column. Domain = set of allowed values.
  • Degree = number of columns. Cardinality = number of rows.
  • Schema = the structure, which rarely changes. Instance = the data at a moment in time.
  • The relational model is a record-based model.

Questions

IN YOUR MANUAL Explain generalization and specialization with an example.

Specialization goes top-down (split). Generalization goes bottom-up (merge).

Specialization: the entity set Person has customers and employees. Employees have a special attribute salary, and customers have rating. So Person is specialized into Employee and Customer, each with its own extra attributes.

Generalization: Customer and Employee both have name, address and age. We pull these common attributes up into a higher-level entity Person. Customer and Employee become its subclasses.

Same result, opposite direction of design. Subclasses inherit the superclass attributes and relationships (an IS-A relationship).

IN YOUR MANUAL What is physical and logical data independence in DBMS?

Data independence means you can change one level of the schema without changing the level above it.

Logical data independence: change the conceptual schema (add a column, split a table) without changing the external schemas (views) or application programs. It is harder to achieve.

Physical data independence: change the internal schema (file organization, indexes, storage device, partitioning) without changing the conceptual schema. It is easier to achieve.

These come from the three-schema architecture: external (views) → conceptual (whole logical design) → internal (physical storage). Example of physical: adding an index to employee(salary) changes no query. Example of logical: adding a column email to employee does not break existing views that do not use it.

Why is a separate table needed for an M:N relationship but not for 1:N?

In 1:N, each "many" row points to exactly one "one" row, so a single foreign key column is enough. In M:N, one row on either side relates to many rows on the other, and a single FK column cannot hold multiple values (it would break 1NF). So a table of pairs is needed.

How do you map a weak entity?

Make a table for it that includes the owner's primary key as a foreign key. The primary key is (owner PK + partial key). Example: dependent(ssn, depname, relation) with PK (ssn, depname) and FK ssn → employee. Often with ON DELETE CASCADE, because a dependent cannot exist without its employee.

What are integrity constraints in the relational model?
  • Domain constraint: values must come from the column's domain (data type, CHECK).
  • Key constraint: no two rows have the same key value.
  • Entity integrity: a primary key cannot be NULL.
  • Referential integrity: a foreign key must match an existing primary key value in the referenced table, or be NULL.

Theory to know

  • DDL (Data Definition Language) creates and modifies the schema. Statements: CREATE, ALTER, DROP (also TRUNCATE, RENAME in most systems).

IN YOUR MANUAL Differentiate between primary key and unique key.

Same question as in Exp 1. Primary key: one per table, no NULLs, identifies the row. Unique key: many per table, NULLs allowed, only prevents duplicates. Both create a unique index and can be referenced by a FK. See the table in Exp 1.

What is DDL? Which commands does it include?

Data Definition Language. It defines or changes the structure (schema) of the database: CREATE, ALTER, DROP, TRUNCATE, RENAME. It does not deal with the data inside the tables.

What does ALTER do? Give three uses.

It modifies an existing table without dropping it: add or drop a column, add or drop a constraint, change a data type, rename a column, set or drop NOT NULL or DEFAULT.

What is a foreign key? What is referential integrity?

A foreign key is a column (or set of columns) that refers to the primary key (or a unique key) of another table. Referential integrity means every FK value must match an existing value in the parent table, or be NULL. You cannot insert an employee with dno = 999 if there is no such department.

What happens if you delete a row that is referenced by a foreign key?

By default (NO ACTION / RESTRICT) the DELETE fails with an error. Other options: ON DELETE CASCADE (delete the child rows too), SET NULL, SET DEFAULT.

dno integer REFERENCES department(dno) ON DELETE CASCADE
What is the CHECK constraint? NOT NULL? DEFAULT?
  • CHECK: a condition that every row must satisfy (CHECK (price > 0)).
  • NOT NULL: the column cannot be empty.
  • DEFAULT: the value used when none is supplied in INSERT.
Difference between CHAR and VARCHAR?

char(n) is fixed length. It is padded with spaces up to n. varchar(n) is variable length, up to n characters, with no padding. Use char for fixed-size codes and varchar for names. In PostgreSQL, text is unlimited varchar.

Experiment 4: DML operations and basic SQL queries

Aim: use DML to populate the database and run queries. The lab needs 12 SELECT, 4 UPDATE and 4 DELETE queries.

Theory to know

  • DML (Data Manipulation Language) works on the data inside tables: SELECT, INSERT, UPDATE, DELETE. (Strictly, SELECT is often called DQL, but your manual lists it under DML.)
  • INSERT INTO t VALUES (...) needs a value for every column in order. INSERT INTO t (col1, col2) VALUES (...) lets you skip columns, which then get their default or NULL.
  • UPDATE needs: table, new value, which rows (WHERE). Without WHERE it updates every row.
  • DELETE FROM t WHERE .... Without WHERE it deletes every row.

IN YOUR MANUAL What is an OUTER JOIN and why is it used? Explain its types with an example.

An inner join drops rows that have no match. An outer join keeps the unmatched rows from one or both tables and fills the missing side with NULL.

Why used: to find things with no match ("departments with no employees") or to list everything even where related data is missing.

TypeKeeps
LEFT OUTER JOINAll rows from the left table + matches from the right (NULLs where none)
RIGHT OUTER JOINAll rows from the right table + matches from the left
FULL OUTER JOINAll rows from both tables. Unmatched rows on either side get NULLs.

Example with your data: departments 102 (COMP) and 105 (account) have no employees.

SELECT d.dname, e.fname
FROM department d
LEFT OUTER JOIN employee e ON d.dno = e.dno;

ETRX     krupita
EXTC     juhi
EXTC     anita
account  NULL      <- kept as well

To find only the unmatched ones, add WHERE e.ssn IS NULL.

Difference between DELETE and UPDATE? What if you forget WHERE?

DELETE removes whole rows. UPDATE changes column values in existing rows. Without WHERE, DELETE removes all rows and UPDATE changes all rows. That is why you run a SELECT with the same WHERE first.

What does SELECT DISTINCT do?

It removes duplicate rows from the result. SELECT DISTINCT ecity FROM employee returns delhi and mumbai only once each.

Difference between INSERT with and without column names?

Without names you must give a value for every column in table order. With names you can skip columns and the skipped ones become DEFAULT or NULL. Naming the columns is safer, because it keeps working if the table gets a new column.

What are the operators for the WHERE clause?

Comparison (= <> < > <= >=), logical (AND OR NOT), BETWEEN, IN, LIKE, IS NULL. Use IS NULL, not = NULL, because NULL is never equal to anything.

What is NULL? How is it different from 0 or an empty string?

NULL means unknown or missing. It is not 0 and not ''. Any comparison with NULL gives UNKNOWN, so NULL = NULL is not true. Aggregates ignore NULLs (except COUNT(*)).

Experiment 5: Aggregates, ORDER BY, GROUP BY, LIKE, HAVING

Aim: 13 queries. 5 aggregate, 3 using clauses with aggregates, 5 using LIKE.

Theory to know

  • Aggregate functions collapse many rows into one value: COUNT, SUM, AVG, MIN, MAX. They ignore NULLs (except COUNT(*)).
  • ORDER BY: sorts the result. ASC (default) or DESC, on one or more columns.
  • GROUP BY: groups rows that have identical values in the given columns, so aggregates are computed per group.
  • HAVING: filters groups after GROUP BY. WHERE filters rows before grouping.
  • LIKE: pattern matching. % = zero or more characters. _ = exactly one character. Without a wildcard, LIKE behaves like =.

Clause order (fixed)

SELECT   columns / aggregates
FROM     tables
WHERE    row conditions
GROUP BY grouping columns
HAVING   group conditions
ORDER BY sort columns

Logical execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

Questions

IN YOUR MANUAL Can we apply the LIKE operator on an integer value? Explain with an example.

Not directly in PostgreSQL. LIKE works on text, so you cast the number to text first.

SELECT * FROM company WHERE salary::text LIKE '2%';
-- or: WHERE CAST(salary AS text) LIKE '2%'

Without the cast, PostgreSQL gives the error operator does not exist: integer ~~ unknown. (MySQL converts implicitly, but PostgreSQL is strict about types.) The example finds all salaries starting with 2, such as 20000 and 25000.

IN YOUR MANUAL Why are aggregate functions used more with ORDER BY, GROUP BY and HAVING? Can we change the order of these clauses in one query?

Why used together: an aggregate on its own gives one number for the whole table. Real questions are per group ("average salary per department"), so GROUP BY splits the rows into groups. HAVING filters those groups by the aggregate result (WHERE cannot use aggregates). ORDER BY sorts the summarized results (highest total first).

Can we change the order? No. The syntax order is fixed: WHERE → GROUP BY → HAVING → ORDER BY. It mirrors the order in which the database processes them. Putting them in another order is a syntax error. Reason: HAVING needs groups, which exist only after GROUP BY. ORDER BY comes last so it can sort the final result.

Difference between COUNT(*), COUNT(column) and COUNT(DISTINCT column)?

COUNT(*) counts all rows (including those with NULLs). COUNT(col) counts rows where col is not NULL. COUNT(DISTINCT col) counts unique non-NULL values.

What if you SELECT a column that is not in GROUP BY and not aggregated?

It is an error in PostgreSQL: column must appear in the GROUP BY clause or be used in an aggregate function. Every non-aggregated column in SELECT must be in GROUP BY.

What is the difference between % and _ in LIKE? What is ILIKE?

% matches any number of characters (including none). _ matches exactly one. ILIKE is the PostgreSQL case-insensitive LIKE.

Default order of ORDER BY? How to sort on two columns?

Ascending by default. ORDER BY name, salary DESC sorts by name first, then by salary descending within the same name.

Experiment 6: Nested queries, views and JOIN operations

Aim: create nested queries and views, and use joins.

Nested queries (subqueries)

A subquery is a SELECT inside another query (in WHERE, FROM or SELECT). The result of the inner query feeds the outer one.

OperatorMeaning
INValue is in the set the subquery returns
NOT INValue is not in the set
> ALLGreater than all values (greater than the maximum)
> ANY / SOMEGreater than at least one value (greater than the minimum)
EXISTSTrue if the subquery returns at least one row
NOT EXISTSTrue if the subquery returns no rows

= ANY is the same as IN. <> ALL is the same as NOT IN.

-- IN
SELECT fname FROM employee WHERE ssn IN (SELECT ssn FROM works_on);
-- NOT IN
SELECT fname FROM employee WHERE ssn NOT IN (SELECT ssn FROM works_on);
-- greater than all
SELECT fname FROM employee
WHERE salary > ALL (SELECT salary FROM employee WHERE dno = 104);
-- ANY
SELECT fname FROM employee
WHERE salary > ANY (SELECT salary FROM employee WHERE dno = 103);
-- EXISTS (correlated)
SELECT dname FROM department d
WHERE EXISTS (SELECT * FROM employee e WHERE e.dno = d.dno);
-- scalar subquery
SELECT fname FROM employee WHERE salary > (SELECT AVG(salary) FROM employee);
-- set operations
SELECT dno FROM employee UNION SELECT dno FROM project;
SELECT dno FROM employee INTERSECT SELECT dno FROM project;
SELECT dno FROM department EXCEPT SELECT dno FROM employee;
Trap: NOT IN returns nothing if the subquery result contains a NULL. Use NOT EXISTS instead when NULLs are possible.

Views

  • A view is a virtual table defined by a stored SELECT. It does not store data itself (except a materialized view).
  • Uses: restrict access (show only some columns or rows), simplify complex queries, summarize data for reports, provide logical data independence.
CREATE VIEW emp_public AS
  SELECT fname, lname, ecity, dno FROM employee;

SELECT * FROM emp_public;
UPDATE emp_public SET ecity = 'pune' WHERE fname = 'juhi';  -- changes the base table
INSERT INTO emp_public (fname, lname, dno) VALUES ('ravi', 'kumar', 101);
DROP VIEW emp_public;

Questions

IN YOUR MANUAL Explain the disadvantages of using a view on the update function.

Not every view can be updated, because the DB cannot always map the change back to the base table rows.

  • Not updatable if the view uses joins over several tables, GROUP BY, aggregates, DISTINCT, UNION or subqueries in SELECT. The DBMS cannot tell which base row to change.
  • Missing columns: if a view leaves out a NOT NULL column with no default, INSERT through the view fails.
  • Rows vanish: updating a row through the view can make it no longer satisfy the view's WHERE, so it disappears from the view. Fix: WITH CHECK OPTION.
  • Derived or computed columns cannot be updated.
  • Ambiguity and side effects: a change through the view affects the base table, and other views that use it.
  • Performance: each access re-runs the underlying query.
  • Structure changes in the base table (drop a column) can break the view.

Note: PostgreSQL auto-updates only simple views (one base table, no aggregates, etc.). Complex views need INSTEAD OF triggers or rules.

IN YOUR MANUAL Can we use the WHERE clause with GROUP BY? Justify.

Yes. WHERE filters rows first, then GROUP BY groups the remaining rows.

SELECT dno, COUNT(*) FROM employee
WHERE ecity = 'mumbai'
GROUP BY dno;

Only the mumbai employees get counted per department. WHERE goes before GROUP BY. The limit is that WHERE cannot use aggregate functions. For conditions on groups, use HAVING.

IN YOUR MANUAL Can we use HAVING and GROUP BY without aggregate functions? Justify.

Yes, both can be used without aggregates.

GROUP BY without an aggregate: it works like DISTINCT.

SELECT ecity FROM employee GROUP BY ecity;   -- same as SELECT DISTINCT ecity

HAVING without an aggregate: allowed, as long as the condition uses grouped columns (or constants).

SELECT dno FROM employee GROUP BY dno HAVING dno > 101;

It works but is less efficient than putting the condition in WHERE, since WHERE filters before grouping. HAVING is designed for aggregate conditions. (Also, HAVING without GROUP BY treats the whole table as a single group.)

Difference between a correlated and a non-correlated subquery?

Non-correlated: the inner query runs once, independently, and passes the result to the outer query (salary > (SELECT AVG(salary) ...)). Correlated: the inner query refers to a column of the outer query, so it runs once per outer row (EXISTS ... WHERE e.dno = d.dno).

IN vs EXISTS?

IN compares a value with a list of values from the subquery. EXISTS only checks whether the subquery returns any row (true/false), and it is usually correlated. EXISTS is safer with NULLs and is often faster for large subquery results.

What is the difference between a view and a table?

A table stores data physically. A view stores only a query, and shows fresh data from the base tables every time it is used. A materialized view stores the result and must be refreshed.

Inner join vs outer join? Union vs join?

Inner: matching rows only. Outer: also keeps unmatched rows (NULL-filled). UNION stacks the rows of two queries vertically (same number and type of columns), and removes duplicates unless UNION ALL. JOIN combines columns from two tables horizontally.

What is a self join? A cross join?

Self join: a table joined with itself using aliases, for example listing each employee with the name of their supervisor. Cross join: the Cartesian product, m × n rows, with no join condition.

How do you modify or drop a view?
CREATE OR REPLACE VIEW name AS SELECT ...;
DROP VIEW name;

Experiment 7: Authorization with GRANT and REVOKE

Aim: implement database authorization using GRANT and REVOKE (done on a virtual lab).

Theory to know

Access control decides who may view, change or manage data. Three models:

ModelIdea
DAC (Discretionary)The owner of an object decides who gets access, using GRANT and REVOKE. Flexible, but privileges can spread through WITH GRANT OPTION.
MAC (Mandatory)The system decides, based on security labels (classifications like Top Secret / Secret) and user clearance. Users cannot change permissions. Used in military and government.
RBAC (Role-based)Privileges go to roles (Manager, Clerk), and users get roles. Easy to administer.

Commands

CREATE USER alice WITH PASSWORD 'secret';   -- a role that can log in
CREATE ROLE hr_team;                        -- a group role

GRANT SELECT ON employee TO alice;
GRANT SELECT, INSERT, UPDATE ON employee TO alice;
GRANT ALL PRIVILEGES ON employee TO alice;
GRANT SELECT (fname, ecity) ON employee TO alice;     -- column-level
GRANT SELECT ON employee TO PUBLIC;                   -- everyone

GRANT SELECT ON employee TO bob WITH GRANT OPTION;    -- bob can pass it on

GRANT hr_team TO alice;                               -- give a role to a user

REVOKE INSERT ON employee FROM alice;
REVOKE ALL PRIVILEGES ON employee FROM alice;
REVOKE GRANT OPTION FOR SELECT ON employee FROM bob;  -- remove only the ability to re-grant
REVOKE SELECT ON employee FROM bob CASCADE;           -- also revoke from those bob granted it to

Privileges in PostgreSQL on tables: SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER. Also on other objects: CREATE, CONNECT, USAGE, EXECUTE. GRANT and REVOKE belong to DCL (Data Control Language).

Questions

IN YOUR MANUAL What is an Access Control List and an Access Control Matrix?

The matrix is the full table of who can do what to which object. An ACL is one column of that matrix, stored with the object.

Access Control Matrix (ACM): a table with subjects (users/roles) as rows and objects (tables, views) as columns. Each cell holds the rights that subject has on that object.

employeedepartmentproject
aliceSELECT, UPDATESELECT—
bobSELECTSELECT, INSERTALL

Access Control List (ACL): for each object, a list of (user, rights) pairs. It is the matrix stored column-wise. Example: ACL of employee = {alice: SELECT, UPDATE; bob: SELECT}. The row-wise version (per subject) is called a capability list.

The matrix is mostly empty (sparse), so real systems store ACLs or capability lists instead of the full matrix. PostgreSQL stores ACLs in the relacl column of pg_class, shown by \dp employee.

IN YOUR MANUAL Differentiate between the GRANT command and GRANT WITH GRANT OPTION. Give an example.

Plain GRANT gives the user the privilege for themselves only. WITH GRANT OPTION also lets them grant it to others.

GRANT SELECT ON employee TO alice;                    -- alice can read, cannot share
GRANT SELECT ON employee TO bob WITH GRANT OPTION;    -- bob can read AND share

-- logged in as bob:
GRANT SELECT ON employee TO carol;    -- works
-- logged in as alice:
GRANT SELECT ON employee TO carol;    -- ERROR: permission denied

Risk: privileges spread in a chain and the owner loses control. Revoking from bob then needs CASCADE to also take it away from carol (otherwise the REVOKE fails with a dependency error). This is why WITH GRANT OPTION is a DAC risk.

What is REVOKE? What is CASCADE vs RESTRICT?

REVOKE takes back privileges given earlier. RESTRICT (default) refuses if others depend on that privilege. CASCADE also removes it from everyone who received it through that user.

What is DCL? Which commands?

Data Control Language: GRANT and REVOKE. It controls permissions and security.

How can views help authorization?

Create a view exposing only certain columns or rows (for example employees without salary), then GRANT SELECT on the view only. The user cannot see the base table. This is a form of content-based access control.

DAC vs MAC vs RBAC?

DAC: the owner decides (flexible, less secure). MAC: the system decides using security labels (strict, most secure). RBAC: permissions attach to roles and users take on roles (scales well for organizations).

Who can GRANT privileges on a table?

The owner of the table, a superuser, or a user who was given the privilege WITH GRANT OPTION.

What is a DBMS? Advantages over a file system?

Software to define, store, manage and retrieve data. Advantages: less redundancy and inconsistency, data sharing, integrity constraints, security, concurrent access, backup and recovery, and data independence.

What is normalization? Explain 1NF, 2NF, 3NF, BCNF.

Normalization is organizing tables to remove redundancy and avoid insert, update and delete anomalies, using functional dependencies.

  • 1NF: all values atomic (no repeating groups or multivalued cells).
  • 2NF: 1NF + no partial dependency (no non-key attribute depends on part of a composite key).
  • 3NF: 2NF + no transitive dependency (non-key attribute depending on another non-key attribute).
  • BCNF: for every dependency X → Y, X must be a super key.

A functional dependency X → Y means that if two rows have the same X, they have the same Y (ssn → fname).

What are ACID properties?

Atomicity: all or nothing. Consistency: the database moves from one valid state to another. Isolation: concurrent transactions do not interfere. Durability: once committed, the change survives a crash.

What is an index? What is a view? What is a transaction?

Index: a data structure (usually a B-tree) that speeds up lookups at the cost of extra storage and slower writes. View: a stored query, a virtual table. Transaction: a logical unit of work made of one or more SQL statements that either all succeed (COMMIT) or all fail (ROLLBACK).

What is a data model? Name a few.

A collection of concepts to describe the structure of a database. Examples: hierarchical, network, relational, object-oriented, ER (conceptual). The relational model is the most widely used.

What is the difference between a database and a DBMS? Schema vs instance?

The database is the collection of data. The DBMS is the software that manages it. Schema is the design or structure (rarely changes). Instance is the actual data at a particular moment.
