1.1

DBMS: what it is and where it is used

A Database Management System (DBMS) holds the information about one enterprise and consists of three things: a collection of interrelated data, a set of programs to access that data, and an environment that is both convenient and efficient to use. Databases can be very large and touch almost every part of our lives.

  • Banking: transactions. Airlines: reservations and schedules. Universities: registration and grades.
  • Sales: customers, products, purchases. Online retailers: order tracking and customised recommendations.
  • Manufacturing: production, inventory, orders, supply chain. Human resources: employee records, salaries, tax deductions.
  • University example (from the slides): add new students, instructors and courses; register students for courses and generate class rosters; assign grades, compute GPA and generate transcripts. In the early days such applications were built directly on top of file systems.
1.2

Purpose of a DBMS: drawbacks of file systems

The DBMS was developed to remove the difficulties of file-processing systems supported by conventional operating systems:

DrawbackWhat goes wrongExample
Data redundancy and inconsistencyMultiple file formats; the same information is duplicated in different files, so copies drift apartA student's address stored in the library file and in the hostel file; one is updated, the other is not
Difficulty in accessing dataA new program must be written for every new taskList all students from Pune with CGPA above 8: no program exists, so write one
Data isolationData lies in multiple files and formats, so combining it is hardMarks in a spreadsheet, fees in a text file
Integrity problemsConstraints (e.g. account balance > 0) are buried in program code; hard to add or change a constraintEach program re-checks "balance > 0" in its own way
Atomicity of updatesA failure leaves the database in an inconsistent state with partial updates carried outFund transfer: debit done, credit not done
Concurrent access by multiple usersNeeded for performance, but uncontrolled access causes inconsistencyTwo people read a balance of 100 and each withdraw 50 at the same time
Security problemsHard to give users access to some, but not all, dataA clerk may see names but not salaries

Database systems offer solutions to all of the above problems.

1.3

Advantages of using a DBMS

  • Controlled redundancy and therefore consistent data; data sharing among many users and programs.
  • Integrity constraints are stated explicitly in the schema, not hidden in programs.
  • Atomic transactions, concurrency control and recovery after failures.
  • Security and authorisation: different users see different parts of the data (views, privileges).
  • Data independence: changing storage or schema does not break applications.
  • A standard query language (SQL) and faster application development.
1.4

Database users

Users are differentiated by how they expect to interact with the system.

  • Naive users use previously written programs through forms, e.g. a "Transfer" program where the user only fills in the accounts and the amount.
  • Application programmers write application programs in a general-purpose language (C, COBOL, Visual Basic and so on) that call the database through DML; these programs retrieve, create, delete and change information.
  • Sophisticated users form their requests in a database query language and submit them to the query processor; analysts who explore the data fall here.
  • Specialised users write specialised database applications that do not fit the traditional data-processing framework, such as computer-aided design, knowledge-base and expert systems.
1.5

The database administrator (DBA)

The life cycle of a database runs from design and implementation to administration. As data grows, performance falls and unused space builds up, so a DBA looks after it. A good-performing database is in the hands of the DBA.

  • Installing and upgrading DBMS servers, and reverting an upgrade that fails; applying service packs, hot fixes and patches.
  • Design and implementation: memory management, file organisation, error handling and log maintenance.
  • Performance tuning: queries and programs should run in a fraction of a second even as tables, constraints and indexes grow.
  • Migration of database servers (for example Oracle to SQL Server) without data loss.
  • Backup and recovery: regular backups so a crash can be recovered with little loss; one of the main duties.
  • Security: create users and roles and give them different access rights.
  • Documentation: keep installation, backup, recovery and security procedures and performance reports so a new DBA can take over easily.
1.6

View of data: three levels of abstraction

The architecture hides complexity from users in three levels.

LevelDescribesExample (instructor record)
Physical levelHow a record is actually stored (files, indices, blocks)The instructor records stored as fixed-length blocks in a file with an index on ID
Logical levelWhat data is stored and the relationships among the datatype instructor = record ID: string; name: string; dept_name: string; salary: integer; end
View levelPart of the database a user or application sees; hides details and can hide information for securityA view that shows ID, name and dept_name but hides the salary

If a database system is not multi-layered, it becomes difficult to make changes. Views can hide data (such as salary) for security.

1.7

Instances and schemas

Similar to types and variables in a programming language.

TermMeaningProgramming analogy
Logical schemaThe overall logical structure of the database (e.g. customers and accounts in a bank and their relationship)Type information of a variable
Physical schemaThe overall physical structure (files, indices)How the variable is laid out in memory
InstanceThe actual content of the database at a particular point in timeThe value of a variable

A database schema is the skeleton structure of the logical view of the whole database: it defines the entities, the relationships among them and all constraints, and is shown by schema diagrams. Schemas are designed by database designers. Two kinds: physical (files and indices on secondary storage) and logical (tables, views and integrity constraints).

1.8

Data independence

A database holds metadata (data about data) in addition to user data, and a DBMS must change over time. If everything depended on everything else, change would be tedious. Metadata therefore follows a layered architecture: a change at one level does not affect another level, though the levels are mapped to each other.

  • Physical data independence: the ability to change the physical schema without changing the logical schema. Example from the slides: replacing hard disks by SSDs should have no impact on the logical data or schemas. Applications depend on the logical schema.
  • Logical data independence: the ability to change the logical (conceptual) schema without changing the external views or application programs; changes to a table format should not change the data on disk. It is harder to achieve than physical independence.
  • Interfaces between levels must be well defined so that changes in one part do not seriously influence the others.
1.9

Database languages

A DBMS provides different languages for different jobs.

LanguageUsed forCommands (from the slides)
DDL: Data Definition LanguageDefine the metadata: create the schema, tables, constraints and indexes; the DDL compiler stores table templates in the data dictionaryCREATE, ALTER, DROP, TRUNCATE, COMMENT, RENAME
DML: Data Manipulation LanguageInsert, retrieve, change and delete data; also called the query languageSELECT, INSERT, UPDATE, DELETE
DCL: Data Control LanguageControl access: who may read, write or delete; remove access of users who leftGRANT, REVOKE
TCL: Transaction Control LanguageSave or undo work: commit a transaction, roll it back after an error, mark savepointsCOMMIT, ROLLBACK, SAVEPOINT, SET TRANSACTION

The data dictionary contains metadata: database schema, integrity constraints (such as the primary key: ID uniquely identifies instructors) and authorisation (who can access what).

1.10

DML classes and SQL

  • Pure languages are used for proving properties about computational power and for optimisation: relational algebra, tuple relational calculus, domain relational calculus.
  • Commercial languages are used in real systems; SQL is the most widely used.
  • SQL is not a Turing-machine-equivalent language; to compute complex functions it is usually embedded in a higher-level language.
  • Application programs reach databases through language extensions (embedded SQL) or an application program interface such as ODBC or JDBC, which send SQL queries to the database.

1.12

Database design

The process of designing the general structure of the database has two parts:

  • Logical design: decide the database schema, i.e. find a "good" collection of relation schemas. A *business* decision (which attributes to record) and a *computer-science* decision (which relation schemas, and how attributes are distributed among them).
  • Physical design: decide the physical layout of the database.
  • Two ways to get good relations: the Entity-Relationship model (model the enterprise as entities and relationships, drawn as an ER diagram) and normalisation theory (formalise what makes a design bad and test for it).
1.13

Database engine: storage, query processing, transactions

  • Storage manager: the interface between the low-level data on disk and the application programs and queries. It interacts with the OS file manager and handles efficient storing, retrieving and updating. Issues: storage access, file organisation, indexing and hashing.
  • Query processing: (1) parsing and translation, (2) optimisation, (3) evaluation. A query has alternative equivalent expressions and algorithms; the cost difference between a good and a bad plan can be enormous, so costs are estimated from statistics kept by the database.
  • Transaction manager: a transaction is a collection of operations that performs a single logical function. The transaction-management component keeps the database consistent despite system and transaction failures; the concurrency-control manager controls the interaction among concurrent transactions.
1.14

Database architectures and history

  • Architecture depends on the underlying computer system: centralised, client-server, parallel (multi-processor), distributed.
  • 1950s–early 1960s: magnetic tapes (sequential access only) and punched cards. Late 1960s–1970s: hard disks give direct access; network and hierarchical models; Ted Codd defines the relational model (ACM Turing Award); IBM System R and Berkeley Ingres prototypes.
  • 1980s: relational systems become commercial, SQL becomes the standard, parallel / distributed and object-oriented systems appear. 1990s: decision support, data mining, multi-terabyte warehouses, web commerce. 2000s: XML and XQuery, automated administration, giant stores such as Google BigTable.
1.15

What is a data model?

A database model defines how data is organised, stored, connected, retrieved, updated and controlled. It gives the logical structure of the database and explains the relationships between data items and the rules for accessing them. A data model is a collection of tools for describing data, data relationships, data semantics and data constraints.

Models are needed to organise large amounts of data, reduce duplication, represent relationships, speed up retrieval, keep data consistent, improve security, support application development and make design easy to understand.

1.16

Hierarchical model

Data is organised as a tree: the top record is the root, each record has one or more children, and every child has only one parent; relationships are one-to-many, like a folder system.

AspectPoints
ExampleCollege → departments (IT, CSE) → students; each student belongs to one department
AdvantagesSimple and easy to understand; fast access when relationships are fixed; good for tree-structured data; good integrity (one parent); efficient for predictable access paths
LimitationsDoes not support many-to-many relationships easily; structure is hard to change; a child cannot have several parents; duplication possible; access depends on a predefined path
ApplicationsFile systems, organisation charts, XML documents, banking, telecommunication, DNS
1.17

Network model

Data is a graph of records joined by links or pointers; a child may have more than one parent, so it supports one-to-one, one-to-many and many-to-many relationships.

AspectPoints
ExampleStudent S101 → C101 and C102; S102 → C101: a many-to-many student-course relationship
AdvantagesSupports many-to-many; more flexible than hierarchical; efficient navigation between related records
LimitationsComplex design; users must understand the connection paths; structural change is difficult; programs depend heavily on structure; hard to maintain when large
ApplicationsRailway and airline reservation, telecommunication networks, manufacturing, supply chain, course registration
1.18

Relational model

Data is stored in tables (relations); a row is a record or tuple and a column is a field or attribute; tables are connected by keys. Proposed by E. F. Codd.

TermMeaningExample
RelationA tableSTUDENT
TupleA row(S101, Kunal, D01)
AttributeA columnStudent_ID, Student_Name, Dept_ID
DomainThe set of valid values of an attributeSemester = {1, …, 8}
Primary keyUniquely identifies each recordStudent_ID
Foreign keyRefers to the primary key of another tableDept_ID in STUDENT → DEPARTMENT
Candidate keyAttribute(s) that could uniquely identify a recordStudent_ID, email
Composite keyKey of two or more attributesStudent_ID + Course_ID in ENROLLMENT

Advantages: simple table structure, SQL, reduced duplication through normalisation, integrity constraints, flexible queries, security through users, roles and privileges, suited to transaction processing. Limitations: complex joins can be slow; poor fit for unstructured data; horizontal scaling is difficult; object data and large multimedia need conversion. Examples: MySQL, PostgreSQL, Oracle, SQL Server, SQLite, MariaDB.

1.19

Relational model example: student, course, enrollment

The ENROLLMENT table resolves the many-to-many relationship between students and courses.

CREATE TABLE Student (
    Student_ID   VARCHAR(10) PRIMARY KEY,
    Student_Name VARCHAR(50) NOT NULL,
    Semester     INT
);
CREATE TABLE Course (
    Course_ID   VARCHAR(10) PRIMARY KEY,
    Course_Name VARCHAR(100) NOT NULL
);
CREATE TABLE Enrollment (
    Student_ID VARCHAR(10),
    Course_ID  VARCHAR(10),
    Marks      INT,
    PRIMARY KEY (Student_ID, Course_ID),
    FOREIGN KEY (Student_ID) REFERENCES Student(Student_ID),
    FOREIGN KEY (Course_ID)  REFERENCES Course(Course_ID)
);
1.20

Entity-Relationship (ER) model

A conceptual design model made of entities, attributes and relationships; the final ER model is converted into tables.

SymbolMeaning
RectangleEntity
OvalAttribute
DiamondRelationship
Double ovalMultivalued attribute
Dashed ovalDerived attribute
Double rectangleWeak entity

Cardinality: 1:1 (person–passport), 1:M (department–student), M:N (student–course). Attribute types: simple (gender), composite (name = first + middle + last), single-valued (date of birth), multivalued (phone number), derived (age from date of birth), key (student ID). 1.21

Object-oriented and object-relational models

Object-oriented databases store objects (data + methods + object identity); object-relational databases keep tables but add object features.

BasisObject-orientedObject-relational
StoresObjects with attributes and methodsTables that may hold user-defined types, arrays and objects

1.22

Semi-structured model (XML and JSON)

Data without a fixed tabular structure; tags or keys describe its structure, and different records may have different fields. Common formats: XML, JSON, YAML.

XML (Extensible Markup Language, defined by the W3C) was meant as a document markup language, but the ability to define new tags and nest them made it a way to exchange data; it is the basis of new data-interchange formats, with many tools for parsing and querying.

  • Advantages: flexible and easy to change, nested structures, works well with web, mobile and REST APIs.
  • Limitations: validation is difficult, duplicates may occur, complex queries are hard, weaker transaction support.
  • Uses: web applications, content management, product catalogues, data integration, configuration files.

Q1

What is a DBMS? Name five application areas.

Show model answer

A DBMS contains information about a particular enterprise: a collection of interrelated data, a set of programs to access it, and an environment that is both convenient and efficient to use.

Applications: banking (transactions), airlines (reservations and schedules), universities (registration and grades), sales (customers, products, purchases), online retail (order tracking, recommendations), manufacturing (production, inventory, supply chain) and human resources (employee records, salaries, tax deductions).

Q2

Explain the purpose of a DBMS with the drawbacks of a file-processing system.

Show model answer

Early applications were built directly on file systems. The DBMS removes these drawbacks:

  • Redundancy and inconsistency: the same data duplicated in many files with different formats.
  • Difficulty in accessing data: a new program is needed for every new task.
  • Data isolation: data scattered over multiple files and formats.
  • Integrity problems: constraints such as balance > 0 are buried in program code and hard to change.
  • Atomicity problems: a failure leaves partial updates (a fund transfer that debits but never credits).
  • Concurrent-access anomalies: two people each withdraw 50 from a balance of 100 read at the same time.
  • Security problems: hard to expose some data but not all.

A database system provides a solution to each of these.

Q3

List the advantages of a DBMS.

Show model answer
  • Reduced redundancy and consistent data; sharing of data.
  • Explicit integrity constraints in the schema; enforcement of business rules.
  • Atomic transactions, controlled concurrency, recovery from failure.
  • Authorisation and views for security.
  • Data independence; a standard language (SQL); faster development.
Q4

Describe the types of database users.

Show model answer

Naive users work through ready-made forms and programs (a bank "Transfer" program). Application programmers write programs in languages such as C or COBOL that call the database using DML. Sophisticated users write queries in a query language and submit them to the query processor (analysts). Specialised users build special applications such as CAD or expert systems that do not fit traditional data processing.

Q5

What are the responsibilities of a database administrator?

Show model answer
  • Installing and upgrading DBMS servers (and rolling back a failed upgrade); applying patches.
  • Database design and implementation: memory management, file organisation, error handling, log maintenance.
  • Performance tuning so queries run in a fraction of a second.
  • Migration of servers without data loss.
  • Backup and recovery; one of the main duties.
  • Security: creating users and roles and granting access rights.
  • Documentation of installation, backup, recovery and security, and performance reports.
Q6

Explain the three levels of data abstraction.

Show model answer

Physical level: how a record is stored. Logical level: what data is stored and the relationships among the data, e.g. `type instructor = record ID, name, dept_name, salary`. View level: the part of the database a user or application sees; views can hide details such as an employee's salary for security. Many views can exist over one logical schema, and one logical schema over one physical schema.

Q7

Differentiate schema and instance. What are the physical and logical schemas?

Show model answer

The schema is the overall structure of the database (like the type of a variable); an instance is the actual content at a given time (like the value of a variable). The logical schema defines tables, views and integrity constraints; the physical schema defines how data is stored on secondary storage (files and indices). The schema changes rarely; the instance changes continuously.

Q8

What is data independence? Explain its two types with examples.

Show model answer

Data independence is the ability to change the schema at one level without changing the schema at the next higher level, because metadata is layered and the levels are mapped to each other.

  • Physical data independence: change the physical schema without changing the logical schema, e.g. replace hard disks by SSDs or add an index.
  • Logical data independence: change the logical schema without changing views or application programs, e.g. add a column to a table. It is harder because programs depend closely on the logical structure.
Q9

What is a data dictionary and what is metadata?

Show model answer

Metadata is data about data (number of tables, names, columns, indexes, constraints). The DDL compiler stores table templates in the data dictionary, which holds the database schema, the integrity constraints (such as the primary key) and authorisation (who can access what). The DBMS consults it for every operation.

Q10

Explain DDL, DML, DCL and TCL with commands.

Show model answer

DDL defines the structure: CREATE, ALTER, DROP, TRUNCATE (removes all records and their space), COMMENT, RENAME. DML works on data: SELECT, INSERT, UPDATE, DELETE. DCL controls access: GRANT gives privileges and REVOKE withdraws them (needed, for example, when a user leaves the organisation). TCL controls transactions: COMMIT saves, ROLLBACK undoes after an error, SAVEPOINT marks a point to roll back to, SET TRANSACTION sets its characteristics.

Q11

Differentiate pure and commercial query languages. Is SQL a complete programming language?

Show model answer

Pure languages (relational algebra, tuple relational calculus, domain relational calculus) are used to prove properties about computational power and for optimisation. Commercial languages, chiefly SQL, are used in real systems. SQL is not Turing-machine equivalent, so complex functions are written in a host language with embedded SQL, or through an API such as ODBC or JDBC that sends SQL queries to the database.

Q12

Explain the database design process and the two design approaches.

Show model answer

Logical design decides the schema (a business decision on which attributes to record and a computer-science decision on relation schemas); physical design decides the layout on disk. To make every relation "good" there are two approaches: the Entity-Relationship model (entities and relationships drawn as an ER diagram) and normalisation theory (formalise what is a bad design and test for it).

Q13

Explain the components of a database system: storage manager, query processor and transaction manager.

Show model answer

The storage manager is the interface between low-level stored data and applications; it works with the OS file manager and handles storage access, file organisation, indexing and hashing. The query processor parses and translates queries, optimises them by estimating cost from statistics, and evaluates the chosen plan. The transaction manager keeps the database consistent despite failures, and its concurrency-control manager controls interaction among concurrent transactions.

Q15

Explain the relational model with an example.

Show model answer

Data is stored in tables (relations) made of rows (tuples) and columns (attributes), connected through keys; each attribute has a domain. Example: STUDENT(Student_ID, Student_Name, Dept_ID) and DEPARTMENT(Dept_ID, Department_Name), where Dept_ID in STUDENT is a foreign key to the primary key in DEPARTMENT. A many-to-many relationship (students and courses) is resolved by a third table ENROLLMENT(Student_ID, Course_ID, Marks) with a composite key.

  • Advantages: simple, SQL, less duplication, integrity constraints, flexible queries, security.
  • Limitations: costly joins, weak for unstructured data, difficult horizontal scaling.
Q16

Explain the ER model, its symbols, cardinality and attribute types.

Show model answer

The ER model is a conceptual design model of entities (rectangle), attributes (oval) and relationships (diamond); double oval = multivalued attribute, dashed oval = derived attribute, double rectangle = weak entity. Cardinality: 1:1, 1:M, M:N. Attributes: simple, composite, single-valued, multivalued, derived, key. It is used during requirement analysis and conceptual design and is then converted into tables.

Q17

Explain the object-oriented and object-relational models.

Show model answer

Object-oriented databases store objects containing data, methods and an object identity, with encapsulation, inheritance (PERSON → STUDENT, TEACHER) and polymorphism; good for CAD, GIS, multimedia, but lacking a universal query language. Object-relational databases keep tables and SQL but add user-defined types, arrays, inheritance and methods (PostgreSQL, Oracle, Db2).

Q18

What are semi-structured databases? Give XML and JSON examples.

Show model answer

They hold data without a fixed table structure: tags or keys describe the data, nested structures are allowed and records may differ in fields. JSON example: `{"studentID":"S101","name":"Kunal","skills":["Python","SQL"]}`; XML example: `<student><studentID>S101</studentID><name>Kunal</name></student>`. They are flexible and suit APIs and web applications but make validation and complex queries harder.

Q19

Explain the four types of NoSQL databases.

Show model answer

Key-value (Redis, DynamoDB): key → value, very fast lookup, caching. Document (MongoDB, CouchDB): JSON documents, flexible schema, catalogues and profiles. Column-family (Cassandra, HBase): rows with column families, very large distributed write-heavy data. Graph (Neo4j): nodes, edges and properties, for connected data such as social networks and recommendations.

Q21

Distinguish conceptual, logical and physical data models.

Show model answer

Conceptual: high-level entities and relationships (STUDENT — ENROLLS — COURSE) with no attribute detail. Logical: attributes, primary and foreign keys and normalised tables, independent of the DBMS. Physical: table and column names, data types, indexes, constraints and storage details for a specific DBMS.

Q22

Define primary key, candidate key and foreign key. What do NOT NULL and UNIQUE do?

Show model answer

A key is an attribute (or combination) that uniquely identifies each record. The primary key is the key chosen to identify records; candidate keys are the other equally unique attributes (passport number, SSN, licence number); a foreign key is the primary key of one table placed in another to relate them (DEPARTMENT_ID in EMPLOYEE). NOT NULL forces a column to always have a value; UNIQUE forbids duplicate values in the column.

Q23

Describe the architectures of database systems and the history of databases.

Show model answer

Architectures: centralised, client-server, parallel (multi-processor) and distributed. History: tape and punched cards (1950s) → hard disks, network and hierarchical models, Codd's relational model, System R and Ingres (1970s) → commercial relational systems and SQL (1980s) → data warehouses and web commerce (1990s) → XML (early 2000s) → giant distributed stores such as BigTable (later 2000s).

Q24

How would you select an appropriate database model? Give examples.

Show model answer

Choose by the data and the workload: relational for structured, transactional data (banking); document for changing JSON data (e-commerce catalogue); key-value for fast lookup and sessions (login); graph when relationships dominate (friend recommendation); column-family for huge write-heavy data (IoT sensors); object-oriented for complex objects (CAD).

Lost update

Show solution

  2. T1: write balance = 100 − 50 = 50. T2: write balance = 100 − 50 = 50 (T2 used the old value).

Final stored balance 50, instead of 0: one withdrawal was lost. A DBMS prevents this with concurrency control.
P3

Atomicity of a transfer

Accounts A = 1000 and B = 500. Transfer 200 from A to B fails after the debit. What is the state? What does the DBMS do?

Show solution
  1. Debit done: A = 800. Credit not done: B = 500.
  2. Total money = 1300 instead of 1500: the database is inconsistent.
  3. The DBMS treats the transfer as one transaction: on failure it rolls back the debit so A = 1000 again.
Without atomicity 200 disappears; with a transaction either both A = 800, B = 700 or neither changes.
