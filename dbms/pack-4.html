4.1

Why indexes exist

An index is a data structure that locates records quickly without scanning the whole table. It reduces the number of disk (block) accesses, which dominate query time because disk is far slower than memory. An index entry has a search key (the column value) and a pointer to the record or block that holds it. Like a book index, it is smaller than the data and sorted, so searching it is cheap.

Example from the class notes: a table of employees whose IDs start at 1, each record 10 bytes. To find ID 543 with no index the DBMS reads 543 × 10 = 5430 bytes from the start; with an index entry of 2 bytes it reads about 542 × 2 = 1084 bytes, much less. Real indexes use trees or hashing so the gain is far larger.

  • Search key: the attribute(s) the index is built on. It need not be the primary key.
  • Index entry: (search-key value, pointer).
  • Two basic kinds: ordered indices (entries sorted by key) and hash indices (entries spread over buckets by a hash function).
  • Evaluation criteria: access type supported (point or range), access time, insertion time, deletion time, space overhead.
4.2

Classification of ordered indices

In an ordered index the entries are stored sorted by search-key value, so equality and range queries are fast. The kinds differ in what the key is and how the data file is arranged:

IndexBuilt onData file orderEntries
Primary (clustering) indexThe key that the data file is sorted on (often the primary key)Data file is sorted on this keyDense or sparse
Clustering indexA non-unique, non-primary attribute that the file is sorted onRecords with the same value are grouped (clustered) togetherOne entry per distinct value, pointing to the first block of the cluster
Secondary (non-clustering) indexAny attribute whose order differs from the file orderFile is not sorted on this keyMust be dense; pointers go to a bucket or record
Multilevel indexAn index on the indexAs aboveOuter levels are sparse

A file can have at most one primary or clustering index (the data can be sorted only one way) but any number of secondary indices. The terms "primary index" and "clustered index" are used loosely in some books to mean an index whose search key fixes the physical order of the file.

4.3

Dense and sparse indices

Dense index: an index record for every search-key value in the data file. Number of index entries = number of records. It finds a record directly (no scan of the block) but needs more space and more maintenance. A dense index is mandatory for secondary indices.

Sparse index: index records for only some search-key values, typically one per block. To find key K: find the largest index entry ≤ K, follow its pointer to the block, then scan that block sequentially. It is smaller and cheaper to maintain but slower per lookup and only usable when the file is sorted on the key.

  • Dense: faster lookups, more space, works for unsorted (secondary) data.
  • Sparse: less space and less insert/delete work; needs sorted data.
  • Good compromise: a sparse index with one entry per block, so an index lookup costs one index-block read plus one data-block read.
4.4

Primary index worked example (sparse)

A file of 30,000 records, 10 records per block, sorted on the key, so it occupies 3,000 blocks. A sparse primary index has one entry per data block: 3,000 entries. If an index block holds 100 entries, the index needs 3,000 / 100 = 30 blocks.

  • Search with binary search on the index: ⌈log₂ 30⌉ = 5 index-block reads, plus 1 data-block read = 6 block accesses.
  • Search with no index (binary search on the data file): ⌈log₂ 3000⌉ = 12 block reads.
  • Linear scan: up to 3,000 block reads (about 1,500 on average).
  • The index is small enough to keep in memory, so in practice only the data-block read touches the disk.
4.5

Clustering index

A clustering index is built on a non-unique attribute, and the data file is sorted on it, so records with the same value sit together. The index has one entry per distinct value, pointing to the first block that contains that value; the rest of the cluster is read sequentially.

Example: an EMPLOYEE file sorted on Dept_ID. All employees of department 10 are in one cluster, all of department 20 in the next, and so on. The index entry for 10 points to the first block of that cluster. It is better still to give each cluster its own block(s), so a block never mixes two departments; this makes insertion easier because a full cluster can grow without moving other clusters.

4.6

Secondary index and multilevel indexing

A secondary index is on an attribute that does not determine the file order, so records with nearby key values are scattered. It must be dense, with one entry for every record (or one per distinct value pointing to a bucket of record pointers when the key is non-unique). Scanning the file in the secondary-key order costs a block access per record, so secondary indices help selective queries but not full scans.

As the file grows, the index itself becomes too big to keep in memory, and a binary search on it costs several block reads. Multilevel indexing treats the index as a file and builds a sparse index on it, repeating until the top level fits in one block. Example: to find roll 111, the first-level (in memory) entry with the largest key ≤ 111 is 100; it points into the second level, where the largest key ≤ 111 is 110; that pointer leads to the data block, which is scanned for 111. Insertion, update and deletion follow the same path. The B-tree and B⁺-tree are the dynamic version of this idea.

4.7

Indexing in SQL

Indexes are created with DDL and are chosen by the DBA (or the optimiser) for columns used in WHERE, JOIN and ORDER BY clauses.

  • CREATE INDEX idx_name ON student(roll_no); builds a (usually B⁺-tree) index.
  • CREATE UNIQUE INDEX enforces uniqueness; a PRIMARY KEY or UNIQUE constraint creates one automatically.
  • Composite index: CREATE INDEX idx_dept_sal ON employee(dept_id, salary); helps queries that filter on dept_id, or on dept_id and salary (leftmost-prefix rule).
  • Trade-off: each index speeds up reads but slows INSERT/UPDATE/DELETE (the index must be updated) and uses disk space. Index selective columns, not every column.
  • DROP INDEX idx_name; removes it.
4.8

B⁺-tree: structure and properties

The B⁺-tree is the standard index of commercial databases. It is a balanced multilevel tree (all leaves at the same depth) that stays balanced automatically on insert and delete, with no need to reorganise the whole file. For order n (n pointers per node):

  • Leaf node: holds up to n − 1 search-key values, each with a pointer to a record (or bucket), and a last pointer to the next leaf, so leaves form a sorted linked list (good for range queries). At least ⌈(n − 1)/2⌉ values in every leaf.
  • Internal node: holds up to n pointers to children and n − 1 keys that separate the sub-trees; it must have at least ⌈n/2⌉ children (the root may have as few as 2 if it is not a leaf).
  • All data pointers are in the leaves; internal nodes only guide the search. Keys in internal nodes are copies.
  • Height: about log⌈n/2⌉(K) for K search-key values, so with n around 100 and a million keys the tree has only 3 or 4 levels: a lookup costs 3 to 4 block reads.
  • Search for key k: start at the root; at each internal node follow the pointer for the range containing k; at the leaf look for k. Range search: locate the first key, then follow the leaf chain.
4.9

B⁺-tree insertion, step by step (order n = 4: at most 3 keys per node)

Rule: find the leaf, insert the key in sorted position. If the leaf now has n keys it overflows: split it into two nodes (⌈n/2⌉ keys in the left, the rest in the right), and copy up the first key of the right leaf into the parent. If the parent overflows, split it too, but push up (move, not copy) the middle key. If the root splits, a new root is created and the tree grows one level. Inserting 2, 3, 5, 7, 11, 17, 19, 23, 29, 31 gives (each level shown, nodes separated by | and levels by ‖):

4.10

B⁺-tree deletion

Find the leaf and remove the key. If the leaf still has at least ⌈(n − 1)/2⌉ keys, stop (and, if the deleted key was copied to an internal node, it may remain there as a separator, which is harmless). Otherwise it underflows and is repaired:

  • Redistribution (borrow): if a neighbouring sibling has more than the minimum, move one entry from it and update the separator key in the parent.
  • Merge (coalesce): if the sibling has exactly the minimum, combine the two nodes into one, delete the separator from the parent and the pointer to the removed node.
  • The parent may now underflow, and the same repair is applied upward. If the root is left with a single child, that child becomes the new root and the height decreases by one.
  • Every insertion or deletion touches only the nodes on one root-to-leaf path, so cost is O(log n) block accesses.

4.12

Hashing: the idea

Hashing computes the location of a record directly from its search key with a hash function h(K), instead of searching an index. Records are stored in buckets (disk blocks). Searching, inserting, updating and deleting all start by computing h(K) to find the bucket.

The hash function should spread keys uniformly (every bucket equally likely) and randomly (no pattern with the data). Simple functions: mod B (B = number of buckets), mid-square, folding. For example with h(K) = K mod 5, the keys 103, 108, 51, 14, 22 hash to buckets 3, 3, 1, 4, 2.

  • Strength: an equality lookup takes about one block read.
  • Weakness: it cannot do range queries (neighbouring keys go to unrelated buckets), and it handles growth badly unless it is dynamic.
4.13

Static hashing and bucket overflow

In static hashing the number of buckets B is fixed when the file is created, so h(K) always returns the same bucket address. Operations: search = compute h(K) and read that bucket; insert = store the record in bucket h(K); delete = find the record and remove it; update = find it, then change it.

Bucket overflow: a record hashes to a bucket that is already full. It happens when too few buckets were created (capacity shortage) or the keys are skewed (skew: many keys hash to the same bucket). Overflow is handled in two ways:

  • Open hashing / linear probing: put the record in the next free bucket. Example: R3 hashes to address 112, which is full, so it is stored at 113 if that is free. (Textbooks call open addressing the alternative that places records in other slots of the table.)
  • Closed hashing / overflow chaining: allocate a new overflow bucket, link it to the full bucket, and keep linked overflow buckets for the same hash value. Example: bucket 110 is full, so a new bucket is chained after 110. The chain is searched sequentially on lookup.
  • Disadvantage of static hashing: if the file grows, chains get long and lookups slow; if it shrinks, space is wasted. Rebuilding with a new hash function and bucket count is expensive.
4.14

Dynamic hashing: extendible and linear hashing

Dynamic hashing lets the number of buckets change as the file grows or shrinks, so there are no long overflow chains and no full rebuild.

  • Extendible hashing: the hash function produces a long binary string (e.g. 32 bits), but only the first i bits (the global depth) are used to index a bucket address table (directory) of 2ⁱ entries. Several directory entries may point to the same bucket; each bucket has a local depth j ≤ i saying how many bits distinguish its records.
  • Insert into a full bucket: if the local depth j < i, split the bucket and update the entries that pointed to it (no directory growth). If j = i, first double the directory (i becomes i + 1), then split. Only the full bucket's records are rehashed.
  • Linear hashing: buckets are split in a fixed order (bucket 0, 1, 2, …) as the load factor passes a limit, not necessarily the bucket that overflowed; overflow buckets are used until their turn comes. No directory is needed.
  • Advantage: performance does not degrade as the file grows; space is used efficiently. Cost: extendible hashing adds one extra directory lookup.
4.15

Ordered indexing versus hashing

Which one to use depends on the queries:

Rule of thumb: if the query has a range condition or ORDER BY, use an ordered index; if it is mostly equality on the key, hashing is a good choice. Most systems implement B⁺-trees and use hashing internally (for example in hash joins).

4.16

Query processing: the three steps

Query processing is the set of activities that extract data from the database. A SQL query goes through three steps:

StepWhat happensOutput
1. Parsing and translationThe parser checks syntax, verifies that relations and attributes exist, replaces views by their definitions and builds a parse tree. It is translated into an internal form, relational algebra.Relational-algebra expression
2. OptimisationThe optimiser considers equivalent expressions and algorithms and picks the one with the lowest estimated cost, using catalog statistics.Query-evaluation plan (execution plan)
3. EvaluationThe query execution engine runs the plan and returns the result.Result tuples

SQL is good for people but not for internal use; relational algebra is well suited to representing a query inside the system. The plan is the algebra expression annotated with the algorithm to use for each operation (for example "use the index on salary") and is also called a query-execution plan. The annotated operations are called evaluation primitives.

4.17

Translating a query to relational algebra

Take: SELECT emp_name FROM Employee WHERE salary > 10000; It can be written in algebra in two equivalent ways:

  • π emp_name (σ salary>10000 (Employee)): select the rows first, then project the name.
  • σ salary>10000 (π emp_name, salary (Employee)): project first, then select.
  • Both give the same answer, but their costs can differ. Choosing the cheaper one is the job of the optimiser. Each algebra operation can then be executed by one of several algorithms (linear scan, index lookup, and so on).
  • The system also generates the code for the plan (query code generator) and the query processor executes it.
4.18

Measures of query cost

The cost of a plan is the total time to answer the query: disk accesses, CPU time and, in distributed systems, communication time. Disk access dominates and is the easiest to estimate, so cost is measured as the number of block transfers (plus the number of seeks).

  • Cost of a block transfer t_T and cost of a seek t_S: cost = b × t_T + S × t_S for b blocks and S seeks.
  • Factors: the operations (joins, unions, intersections), their order, the algorithms chosen, memory (buffer) available, and whether indexes exist.
  • Statistics kept in the catalog: nr number of tuples in relation r; br number of blocks of r; sr size of a tuple; fr blocking factor (tuples per block, so br = ⌈nr / fr⌉); V(A, r) number of distinct values of A in r; SC(A, r) selection cardinality = average number of records that satisfy an equality on A = nr / V(A, r); height of the B⁺-tree HTi.
  • Example: 10,000 records of 100 bytes, block size 4,096 bytes: fr = ⌊4096/100⌋ = 40, br = ⌈10000/40⌉ = 250 blocks.

4.20

Sorting and the PROJECT and set operations

External sort-merge sorts relations that do not fit in memory (M buffer blocks). Pass 0 (run creation): read M blocks at a time, sort them in memory, write each as a sorted run: ⌈b_r / M⌉ runs. Merge passes: merge up to M − 1 runs at a time (one buffer for output) until a single sorted run remains. Number of passes = 1 + ⌈log_(M−1)(b_r / M)⌉; total block transfers ≈ b_r (2⌈log_(M−1)(b_r / M)⌉ + 1) (the final write is not counted).

PROJECT π: apply to each tuple, then eliminate duplicates by sorting (duplicates become adjacent) or by hashing. Without DISTINCT, SQL keeps duplicates and the cost is one pass over the input. Set operations (union, intersection, difference) are done by sorting both relations and merging, or by hashing one relation into buckets and probing with the other.

4.21

Join algorithms

Joins are the most expensive operation, so the algorithm matters. For relations r (outer) and s (inner), with n tuples and b blocks:

  • Nested-loop join: for each tuple of r, scan all of s. Cost = n_r × b_s + b_r (very expensive).
  • Block nested-loop join: for each block of r, scan s. Cost = b_r × b_s + b_r; with M buffer blocks, read M − 2 blocks of r at a time: ⌈b_r / (M − 2)⌉ × b_s + b_r.
  • Indexed nested-loop join: if s has an index on the join attribute, look up each tuple of r in it. Cost = b_r + n_r × c, where c is the cost of one index lookup.
  • Merge join: sort both on the join attribute (if not already) and merge. Cost = b_r + b_s (when sorted), plus the sorting cost. Best for equi-joins and for already-sorted inputs.
  • Hash join: partition both relations with a hash function on the join attribute, then join matching partitions in memory. Cost ≈ 3(b_r + b_s) + 4 n_h. Best for large equi-joins with no index.

Take r with n_r = 10000 tuples in b_r = 400 blocks and s with n_s = 5000 tuples in b_s = 100 blocks; M = 12 buffer blocks:

4.23

Query optimisation: what the optimiser does

A user can write a query in many equivalent ways, and the system can execute each in many ways; the costs can differ by orders of magnitude. Query optimisation is choosing the cheapest plan, so the user need not write an efficient query. The optimiser produces a good execution plan, the code generator turns it into code and the query processor runs it.

A query tree is a tree for a relational-algebra expression: input relations are the leaves and algebra operations are the internal nodes; it is evaluated from the leaves up. The optimiser transforms the tree into cheaper equivalent trees.

  • Two approaches: heuristic (rule-based) uses rules that nearly always help, such as "do selections early"; cost-based estimates the cost of several plans using catalog statistics and picks the cheapest. Real optimisers combine both.
  • Steps: (1) generate logically equivalent expressions using equivalence rules; (2) annotate each with algorithms to get physical plans; (3) estimate the cost of each; (4) choose the cheapest.
4.24

Equivalence rules of relational algebra

Two expressions are equivalent if they produce the same result on every valid database. The rules used to transform a query tree:

RuleStatement
1. Cascade of selectionσθ1∧θ2(E) = σθ1(σθ2(E))
2. Commutative selectionσθ1(σθ2(E)) = σθ2(σθ1(E))
3. Cascade of projectionπL1(πL2(…πLn(E))) = πL1(E) when L1 ⊆ L2 ⊆ … ⊆ Ln
4. Selection into joinσθ(E1 × E2) = E1 ⋈θ E2
5. Commutative joinE1 ⋈ E2 = E2 ⋈ E1
6. Associative join(E1 ⋈ E2) ⋈ E3 = E1 ⋈ (E2 ⋈ E3)
7. Push selection through joinσθ0(E1 ⋈ E2) = σθ0(E1) ⋈ E2 when θ0 uses only attributes of E1
8. Push projection through joinπL1∪L2(E1 ⋈ E2) = πL1(E1) ⋈ πL2(E2) when the join attributes are in L1 ∪ L2
9. Set operationsUnion and intersection are commutative and associative; selection distributes over them
4.25

Heuristic optimisation: the standard procedure

The rule-based optimiser applies these heuristics in order:

  • 1. Break up conjunctive selections into a cascade (rule 1).
  • 2. Push selections down the tree as far as possible, so fewer tuples reach the joins (rules 2, 7).
  • 3. Choose the most restrictive selections and joins first, and the join order that gives the smallest intermediate results; replace a Cartesian product followed by a selection with a join (rule 4).
  • 4. Push projections down to discard unneeded columns early (rules 3, 8).
  • 5. Identify sub-trees that can be pipelined (results passed on without writing to disk) and choose algorithms for each node.
4.26

Worked example: the Patients and Doctors query

Query: SELECT p.pname, d.dname FROM Patients p, Doctors d WHERE p.doctor = d.dname AND d.dgender = 'M'. Patients has 2,000 tuples and Doctors has 50.

Initial (naive) query tree: the leaves are scan(Patients) and scan(Doctors); a join on p.doctor = d.dname is above them; above that is a filter d.dgender = 'M'; at the top is the projection (p.pname, d.dname). This joins 2,000 patients with all 50 doctors before filtering.

Optimised tree: push the filter below the join onto Doctors: filter dgender = 'M' is applied to scan(Doctors) first. If, say, 25 of the 50 doctors are male, the join now has 25 tuples on that side instead of 50, so the join input and the intermediate result are about halved. Then project the two needed columns above the join. The cost-based transformation compares both trees using the statistics and chooses the second.

4.27

Estimating selection size and choosing a plan

The optimiser estimates the size of each intermediate result using the catalog statistics, and chooses the plan with the smallest total cost.

  • Selection σ(A = v)(r): about SC(A, r) = n_r / V(A, r) tuples (assuming a uniform distribution). Example: n = 10,000 and V(dept) = 50 gives 200 tuples.
  • Selection σ(A ≤ v)(r): about n_r × (v − min(A)) / (max(A) − min(A)) tuples.
  • Conjunction: multiply the selectivities (assuming independence): n_r × s1 × s2.
  • Join r ⋈ s on attribute A: if A is a key of r, at most n_s tuples; otherwise about n_r × n_s / max(V(A, r), V(A, s)).
  • Join order: with n relations there are many orders; dynamic programming keeps only the cheapest plan for each subset of relations, and left-deep trees are considered so the result of each join can be pipelined into the next.
  • Statistics must be refreshed (ANALYZE / UPDATE STATISTICS) because stale statistics give bad plans; EXPLAIN shows the chosen plan.
4.28

Looking at a plan: EXPLAIN

Most systems show the chosen plan. In PostgreSQL:

CREATE INDEX idx_sal ON employee(salary);
EXPLAIN SELECT emp_name FROM employee WHERE salary > 10000;
-- Bitmap Heap Scan / Index Scan on employee using idx_sal
--   Index Cond: (salary > 10000)
  • If few rows qualify the optimiser picks the index scan; if most rows qualify it prefers a sequential (linear) scan because following many pointers costs more than reading the file.
  • Materialised views and pipelining reduce cost too: a pipelined plan passes tuples from one operator to the next without writing temporary results to disk.

Q3

Explain multilevel indexing with an example. Why is it needed?

Show model answer

When the index grows too big for memory, a search in it costs several disk reads. A multilevel index builds a sparse index on the index, repeating until the top level fits in a block, which is kept in memory.

Q4

Explain the structure of a B⁺-tree. State its properties for order n.

Show model answer
  • Balanced tree; all leaves at the same depth; leaves are linked in key order.
  • Leaf: between ⌈(n − 1)/2⌉ and n − 1 keys with record pointers, and a pointer to the next leaf.
  • Internal node: between ⌈n/2⌉ and n children (root: at least 2 unless it is a leaf) with keys separating the sub-trees; internal nodes hold no record pointers.
  • Height about log⌈n/2⌉(K), so even for a million keys a search needs only 3 to 4 block reads.
  • Insert and delete are done locally with splits and merges, keeping the tree balanced.

Q6

Explain deletion in a B⁺-tree.

Show model answer

Find the leaf and delete the key. If the leaf still has at least ⌈(n − 1)/2⌉ keys, nothing more is needed. On underflow: (1) borrow an entry from a sibling that has more than the minimum and fix the separator in the parent; or (2) if the sibling is at the minimum, merge the two nodes and delete the separator and a pointer from the parent. The parent may underflow, and the repair is repeated upward; if the root is left with one child, that child becomes the root and the height decreases.

Q8

What is hashing? Explain static hashing and the ways of handling bucket overflow.

Show model answer

A hash function h(K) maps a search key directly to a bucket address, so a record is found without searching an index. In static hashing the number of buckets is fixed, so h(K) always gives the same address (for example K mod 5 sends EMP_ID 103 always to bucket 3).

Bucket overflow occurs when the target bucket is full (too few buckets, or skewed keys). Open hashing (linear probing): store in the next free bucket (if 112 is full, use 113). Closed hashing (overflow chaining): link a new overflow bucket to the full one. Both degrade as the file grows.

Q9

Explain extendible hashing and linear hashing (dynamic hashing).

Show model answer
  • Extendible: a directory of 2^i pointers indexed by the first i bits (global depth) of h(K); buckets have a local depth j ≤ i. On overflow, if j < i split the bucket; if j = i double the directory and then split. Only one bucket is rehashed.
  • Linear: buckets are split one by one in a fixed order when the load exceeds a limit, with overflow chains until their turn; no directory.
  • Both grow and shrink with the file, so there are no long overflow chains and no full rebuilds.

Q11

Explain the steps in query processing with a diagram description.

Show model answer

Query → Parser and translator → relational-algebra expression → Optimiser (uses statistics from the catalog) → execution plan → Evaluation engine (reads data) → output.

  • Parsing and translation: syntax check, name verification, views replaced; parse tree; converted to relational algebra.
  • Optimisation: choose the minimum-cost plan.
  • Evaluation: the execution engine runs the plan, using the chosen algorithms and indexes.
Q12

How is the cost of a query measured? Which statistics are kept in the catalog?

Show model answer

Cost is the time to answer the query; since disk access dominates, it is measured mainly as the number of block transfers (and seeks): cost = b × t_T + S × t_S. CPU and communication costs are secondary.

  • n_r (tuples), b_r (blocks), s_r (tuple size), f_r (blocking factor, b_r = ⌈n_r / f_r⌉).
  • V(A, r) (distinct values), SC(A, r) = n_r / V(A, r) (selection cardinality).
  • Index height and number of leaf blocks.

Q15

What is query optimisation? Explain heuristic and cost-based optimisation.

Show model answer

Query optimisation selects the cheapest evaluation plan among many equivalent ones, so users need not write efficient queries. Heuristic (rule-based) optimisation applies rules that almost always reduce cost: do selections and projections early, replace products by joins, put the smallest intermediate results first. Cost-based optimisation generates alternative plans, estimates their costs from catalog statistics and picks the cheapest. Real systems combine them.

Q17

What is a query evaluation plan? What are evaluation primitives and pipelining?

Show model answer

A query evaluation (execution) plan is the relational-algebra expression annotated with the algorithm (and index) to use for each operation. Each annotated operation is an evaluation primitive. The execution engine takes the plan, runs it and produces the output. Pipelining passes the output tuples of one operation straight to the next without writing a temporary relation to disk; materialisation writes each intermediate result to disk first. Pipelining saves disk I/O.

Blocking factor and file size

A file has 10,000 records of 100 bytes each and the block size is 4,096 bytes. Find the blocking factor, the number of blocks, and the cost of (a) a linear search for a unique key (worst case and average), (b) a binary search on the sorted file.

Show solution

  2. Blocks b = ⌈10000 / 40⌉ = 250.
  3. (a) Linear search: worst case 250 block reads; average for a key that exists 125.
  4. (b) Binary search: ⌈log₂ 250⌉ = 8 block reads.

Sparse index size

A sorted file of 30,000 records, 10 records per block. A sparse index has one entry per data block, and an index block holds 100 entries. Find the number of index entries, the number of index blocks and the cost of a lookup using a binary search on the index.

P5

Search path and cost in a B⁺-tree

A relation has 1,000,000 search-key values and a B⁺-tree with n = 101 pointers per node. Find the minimum and maximum height and the cost to find one record.

Show solution
  1. Maximum keys per node n − 1 = 100; maximum fan-out 101. Minimum fan-out ⌈101/2⌉ = 51.
  2. Minimum height (full nodes): 101^h ≥ 1,000,000 gives h = 3 (101³ = 1,030,301).
  3. Maximum height (nodes half full): ⌈log₅₁(1,000,000)⌉ = 4 (51³ = 132,651; 51⁴ ≈ 6.8 million).
  4. Cost to find one record = height + 1 (the data block): 4 to 5 block reads.
Height 3 to 4; a lookup costs 4 to 5 block reads.
P6

Static hashing with chaining

Insert the keys 103, 108, 51, 14, 22, 28, 33 into a static hash file with 5 buckets, h(K) = K mod 5, each bucket holding 2 records. Show the buckets and where overflow occurs.

Show solution
  1. Hash values: 103 → 3, 108 → 3, 51 → 1, 14 → 4, 22 → 2, 28 → 3, 33 → 3.
  2. Primary buckets before overflow handling: bucket 0 empty; 1: 51; 2: 22; 3: 103, 108, 28, 33 (4 keys for 2 slots); 4: 14.
  3. Capacity is 2, so bucket 3 overflows when 28 arrives. Overflow chaining: link an overflow bucket to bucket 3 holding 28 and 33. Linear probing: 28 goes to the next bucket with room (bucket 4 has one free slot, so 28 joins 14); 33 then finds bucket 3 full and bucket 4 full, and wraps to bucket 0.
Bucket 3 overflows; chaining adds an overflow bucket for 28 and 33.

External sort

A relation has 1,000 blocks and the buffer holds M = 11 blocks. How many initial runs and how many merge passes does external sort-merge need? Give the total block transfers (ignoring the final write).

Show solution
