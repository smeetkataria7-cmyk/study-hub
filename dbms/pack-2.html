2.1

Database design phases and why we model

Building a database system is a complex process with three broad steps: requirement analysis, design and implementation. A data model is a set of concepts that describe the structure of a database (data types, relationships, constraints). Design moves through four phases:

  • Real-world problem → requirements: interview users, collect the data and processes.
  • Conceptual schema (ER / EER diagram): a high-level, DBMS-independent description. Only what data exists, not how it is stored.
  • Logical schema (relational): the conceptual schema mapped to tables, keys and constraints for a chosen model; then normalised.
  • Physical schema: files, indexes, storage.
  • Benefits of data modelling: focus on essentials (ignore details such as book editions); ease of communication among designer, librarians and students; improving the process; exploring alternatives (such as online enrolment) through prototypes.
  • Types of models: descriptive (describe and understand), prescriptive (specify exactly what the system does; normally used for databases), representative (simulate).
2.2

The ER model: entities and attributes

The Entity–Relationship (ER) model, introduced by Peter Chen in 1976, is the most widely used high-level conceptual data model. It is not implemented directly in any commercial DBMS but is a powerful shorthand for the first design of the "mini world". We use the COMPANY database as the running example: departments (name, number, manager and manager start date), projects (name, number, one location), employees (SSN, address, salary, gender, birthdate, one department, several projects with hours per week, a direct supervisor) and dependents (name, gender, birthdate, relationship).

  • Entity: an object in the mini world (employee John Smith, the Research department, ProductX project).
  • Entity type: the set of entities with the same attributes (intension): EMPLOYEE(Name, Age, Salary). Entity set: the collection of entities at a moment (extension): e1, e2, e3, …
  • Attribute: a property with a value from a value set (domain) such as integer, string, enumerated type.
  • Key attribute: its value uniquely identifies an entity, e.g. SSN of EMPLOYEE. A composite key combines attributes: VehicleTagNumber = (Number, State). An entity type can have more than one key (CAR: VIN and licence plate).
  • NULL is used when no value applies.

2.4

Relationships, relationship types and degree

A relationship associates two or more entities with a specific meaning: employee John Smith works on the ProductX project; Franklin Wong manages the Research department. Relationships of the same kind form a relationship type (a relationship set is its extension), e.g. WORKS_FOR between EMPLOYEE and DEPARTMENT.

  • Degree: the number of participating entity types. Unary (recursive) degree 1, binary degree 2 (WORKS_FOR, MANAGES, WORKS_ON), ternary degree 3 (SUPPLY: supplier, part, job), n-ary degree n. An n-ary relationship is in general not equivalent to n binary ones.
  • Roles: the function each entity plays. Essential for a recursive relationship where one entity type participates twice in different roles: SUPERVISION relates an EMPLOYEE (role supervisor) to another EMPLOYEE (role supervisee or subordinate).
  • Descriptive attributes: a relationship type can have its own attributes: HOURS of WORKS_ON is the number of hours per week an employee works on a project; start date of MANAGES.
  • More than one relationship type can exist between the same two entity types with different meanings: MANAGES and WORKS_FOR between EMPLOYEE and DEPARTMENT.
  • COMPANY relationship types: WORKS_FOR, MANAGES, WORKS_ON, CONTROLS, SUPERVISION, DEPENDENTS_OF.

2.6

Weak entity types

A weak entity type has no key attribute of its own; its entities are identified only through their relationship with an owner (identifying) entity. It must participate (totally) in an identifying relationship type with the owner. Entities are identified by the combination of the partial key (discriminator) of the weak entity and the primary key of the owner.

Example: DEPENDENT of an EMPLOYEE is identified by the dependent's first name together with the employee they belong to. DEPENDENT is the weak entity (double rectangle), EMPLOYEE the identifying entity, DEPENDENTS_OF the identifying relationship (double diamond), and Dependent_name the partial key (dashed underline). Deleting an employee deletes their dependents. An entity set with its own primary key is a strong entity.

2.8

ER design issues

Typical choices a designer must make:

  • Entity or attribute? If a property has its own attributes or relationships (e.g. the department of an employee has a name, manager and projects), make it an entity; otherwise an attribute.
  • Entity or relationship? A bank loan might be an entity (with its own attributes) or a relationship between customer and branch. Use a relationship when it just links entities and has few attributes.
  • Binary or n-ary? A ternary relationship (supplier supplies part to job) cannot always be replaced by three binary ones without losing information, but can be converted by making the relationship an entity.
  • Strong or weak entity? Use a weak entity if the entity has no natural key and is existence-dependent on another.
  • Avoid redundancy: do not store as an attribute something that is already shown by a relationship (the department number in EMPLOYEE when WORKS_FOR is drawn).
  • Pitfalls of design tools: boxes and lines only, poor methodology support, and no trade-off analysis.
2.9

Extended ER (EER): subclasses, superclasses, specialisation, generalisation

The Enhanced / Extended ER (EER) model adds subclasses and superclasses, specialisation and generalisation, categories and attribute inheritance (concepts borrowed from object orientation). ER alone could not represent set–subset relationships.

  • Subclass / superclass: a subgrouping of entities of an entity type: SECRETARY, ENGINEER, TECHNICIAN, MANAGER, SALARIED_EMPLOYEE and HOURLY_EMPLOYEE are subclasses of EMPLOYEE (the superclass). This is the IS-A relationship (SECRETARY IS-A EMPLOYEE).
  • A subclass member is the same real-world entity as a member of the superclass in a more specific role. An entity cannot exist merely as a member of a subclass; it must also belong to the superclass. A superclass member may belong to any number of subclasses (a salaried employee who is also an engineer) or to none.
  • Attribute inheritance: a subclass entity inherits all attributes and relationships of the superclass. It also has specific (local) attributes (TypingSpeed of SECRETARY) and may take part in specific relationships (BELONGS_TO for HOURLY_EMPLOYEE).
  • Specialisation (top-down): defining subclasses of a superclass by distinguishing characteristics, e.g. {SECRETARY, ENGINEER, TECHNICIAN} by job type; another specialisation by method of pay: {SALARIED, HOURLY}.
  • Generalisation (bottom-up): the reverse. CAR and TRUCK share features, so generalise them into the superclass VEHICLE. In practice both processes are combined.

Hierarchy versus lattice: in a hierarchy each subclass has only one superclass (single inheritance); in a lattice a subclass can have several superclasses (multiple inheritance); a subclass with more than one superclass is a shared subclass (STUDENT_ASSISTANT is both EMPLOYEE and STUDENT).

2.11

Aggregation and categories (union types)

Aggregation: an ER feature that lets a relationship set take part in another relationship, shown by a dashed box around the aggregation. Example: a student works on a project (relationship WORKS_ON) and each such pair is guided by an instructor; and a student–instructor–project combination may have an evaluation. Treating "student works on project" as an aggregated entity lets EVALUATION relate to it without duplicating data. Without it you would need a ternary relationship with redundancy.

Category (union type): a subclass with more than one superclass of different entity types; each member belongs to at least one (the union) of them. Example: in a vehicle registration database, the OWNER of a vehicle may be a PERSON, a BANK (holding a lien) or a COMPANY, so OWNER is a subset of the union of the three. A shared subclass, by contrast, is a subset of the intersection of its superclasses (members must exist in all of them).

ER and EER to relational mapping: steps 1 to 7

The standard algorithm converts a conceptual schema to relations (COMPANY example):

StepConstructMapping ruleCOMPANY example
1Regular (strong) entity typeRelation with all simple attributes (components of composites); choose a key as primary keyEMPLOYEE(SSN, …), DEPARTMENT(DNUMBER, …), PROJECT(PNUMBER, …)

A recursive 1:N relationship such as SUPERVISION adds a foreign key SUPER_SSN in EMPLOYEE referring to EMPLOYEE.

2.16

Relational algebra: query languages and the basic operators

A query language lets a user request information. A procedural language specifies the sequence of operations to compute the answer (relational algebra); a non-procedural (declarative) language describes the desired result only (relational calculus, SQL). Relational algebra is procedural: operations take one or two relations and produce a new relation, so they can be composed. It is the internal form used by the query optimiser.

Two groups of operations: set operations (union, intersection, set difference, Cartesian product) and relational operations (select σ, project π, rename ρ, join ⋈, division ÷).

  • Basic (fundamental) operations: σ, π, ∪, −, ×, ρ. All others (∩, ⋈, ÷) can be expressed with these.
  • A basic expression is a relation name or a constant relation such as {(A-101, Downtown, 500), (A-215, Mianus, 700)}. If E1 and E2 are expressions, so are σP(E1), πS(E1), ρx(E1), E1 ∪ E2, E1 − E2, E1 × E2.

Union, intersection, difference and Cartesian product

These need the two relations to be union compatible: the same number of attributes, and each pair of corresponding attributes has the same (or convertible) domain. Take Depositor(Customer_name, City) and Borrower(Customer_name, City):

Rename ρ x (E) gives the result of E the name x (and optionally renames attributes: ρ x(A1, A2)(E)); it is needed in self-joins and to avoid ambiguity. Joins combine related tuples of two relations: R ⋈ θ S = σ θ (R × S).

2.21

SQL: data definition (DDL)

SQL is the standard language; it has DDL (define structure), DML (manipulate data), DCL (control access) and TCL (control transactions). A table is defined with column types and constraints:

CREATE TABLE department (
    dept_id   INT PRIMARY KEY,
    dname     VARCHAR(30) NOT NULL UNIQUE,
    city      VARCHAR(30) DEFAULT 'Mumbai'
);
CREATE TABLE employee (
    emp_id    INT PRIMARY KEY,
    name      VARCHAR(50) NOT NULL,
    salary    NUMERIC(10,2) CHECK (salary > 0),
    dept_id   INT,
    manager_id INT,
    FOREIGN KEY (dept_id)    REFERENCES department(dept_id) ON DELETE SET NULL,
    FOREIGN KEY (manager_id) REFERENCES employee(emp_id)
);
ALTER TABLE employee ADD COLUMN email VARCHAR(80);
ALTER TABLE employee DROP COLUMN email;
TRUNCATE TABLE employee;   -- remove all rows, keep structure
DROP TABLE employee;       -- remove structure and data
  • Data types: INT, NUMERIC(p,s), CHAR(n), VARCHAR(n), DATE, TIMESTAMP, BOOLEAN. Constraints: PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, CHECK, DEFAULT.
  • Composite key: PRIMARY KEY (student_id, course_id). A constraint may be named: CONSTRAINT chk_sal CHECK (salary > 0).
  • DELETE removes chosen rows (can be rolled back); TRUNCATE removes all rows quickly (DDL); DROP removes the table itself.

2.23

SELECT: clauses and logical order

The general query is SELECT [DISTINCT] columns FROM tables WHERE row-condition GROUP BY columns HAVING group-condition ORDER BY columns [ASC|DESC] [LIMIT n]. It corresponds to relational algebra: FROM is the product or join, WHERE is σ, SELECT is π, and aggregates are 𝒢.

The logical order of evaluation is different from the order we write it:

  • 1. FROM (and JOIN): form the working set of rows.
  • 2. WHERE: filter individual rows.
  • 3. GROUP BY: form groups.
  • 4. HAVING: filter groups (can use aggregates).
  • 5. SELECT: compute the output columns and aggregates; DISTINCT.
  • 6. ORDER BY: sort the final result (can use output aliases).
  • 7. LIMIT / OFFSET.
  • Key difference: WHERE → filters rows before grouping and cannot use aggregates; HAVING → filters groups after grouping; GROUP BY → creates groups; ORDER BY → sorts the output.

2.31

Views

A view is a virtual table defined by a query; only the query is stored, and the data is read from the base tables each time it is used (so base-table changes show up automatically). A view gives a customised representation of data to different users.

CREATE VIEW AI_Students AS
SELECT Name, Marks FROM Student WHERE Department = 'AI';

SELECT * FROM AI_Students;
UPDATE AI_Students SET Marks = 95 WHERE Name = 'Raj';   -- updates the base table
DROP VIEW AI_Students;
  • Why use views: simplify complex queries (store a long JOIN as a view); security (hide columns such as salary: CREATE VIEW Employee_Public AS SELECT Name FROM Employee); data abstraction and independence; different views for student, teacher and admin; consistent, always up-to-date data.
  • Types: simple view (one table, no functions or grouping; usually updatable); complex view (joins, aggregates; usually not updatable); materialised view (the result is stored physically, faster but must be refreshed; used in data warehouses).
  • Updatable view: generally needs a single base table, no DISTINCT, GROUP BY, aggregates or joins, and includes the primary key; WITH CHECK OPTION stops updates that would make a row disappear from the view.
  • Limitations: complex views can be slow (the query runs every time); restricted updates; a view becomes invalid if the base table structure changes.
  • View vs table: a table stores actual data physically and persistently; a view stores only the query definition and retrieves rows from tables.
2.32

Security and authorisation

Database security protects data from unauthorised access, modification, destruction or disclosure. Goals: confidentiality (only authorised users see data), integrity (no improper modification) and availability (authorised users can access when needed). Mechanisms: user accounts, authentication, privileges, roles and access controls.

Privileges (permissions): SELECT (read), INSERT, UPDATE, DELETE, REFERENCES (create foreign keys), plus TRUNCATE, TRIGGER and system-level privileges. Access-control models: DAC (discretionary: owners grant privileges to others), MAC (mandatory: security classes such as Top Secret > Secret > Confidential > Public; users cannot pass on permissions), RBAC (role-based: Manager = read + update, Clerk = read + insert, Guest = read only).

2.33

Data control language: GRANT, REVOKE and roles

A role is a named set of privileges: privileges → role → users, which makes administration easier when many users need the same rights.

GRANT SELECT ON student TO student1;
GRANT SELECT, INSERT, UPDATE ON student TO student1;
GRANT ALL PRIVILEGES ON student TO student1;
GRANT SELECT (name, city) ON student TO student1;       -- column-level privilege
GRANT SELECT ON student TO student1 WITH GRANT OPTION;   -- student1 may pass it on

REVOKE SELECT ON student FROM student1;
REVOKE ALL PRIVILEGES ON student FROM student1;

CREATE ROLE clerk;
GRANT SELECT, INSERT ON student TO clerk;
GRANT clerk TO student1, student2;
  • GRANT gives privileges to a user or role; REVOKE removes them. With WITH GRANT OPTION the grantee can grant the privilege further; revoking it can cascade (REVOKE … CASCADE) to those who received it from them.
  • PostgreSQL table privileges: SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER; column-level privileges apply to SELECT, INSERT, UPDATE, REFERENCES.
  • Views plus GRANT give fine-grained access: grant users SELECT on a view that exposes only some columns or rows instead of the base table.
  • Exam answer: authorisation is the process of specifying the privileges given to a database user; it determines which objects a user can access and which operations (SELECT, INSERT, UPDATE, DELETE) they can perform.
2.34

Triggers: the event–condition–action (ECA) model

A trigger (active rule) is a procedure the DBMS runs automatically when a specified event occurs. Triggers are used to enforce complex integrity constraints, maintain derived data, audit changes and notify users. Rules follow the ECA model, with three components:

  • Event: what triggers the rule: usually INSERT, UPDATE (optionally of specific columns: UPDATE OF salary) or DELETE on a table (may also be a temporal event).
  • Condition: an optional test evaluated once the event occurs; if absent the action always runs; if present the action runs only when it is true (the WHEN clause).
  • Action: a sequence of SQL statements, a transaction, or a call to an external procedure.
  • Timing: BEFORE (runs before the event is executed; used for validation or to modify the new row) or AFTER (runs after).
  • Granularity: row-level (FOR EACH ROW: once for every affected row) or statement-level (once per statement, even if many rows change). The keywords NEW (the new or updated row) and OLD (the deleted or pre-update row) are available only in row-level triggers.
  • Example of the difference: UPDATE EMPLOYEE SET Salary = 1.1 × Salary WHERE Dno = 5 fires a row-level trigger once for each employee of department 5, but a statement-level trigger only once.
2.35

Trigger examples: maintaining Total_sal of a department

Schema (derived attribute): EMPLOYEE(Name, Ssn, Salary, Dno, Supervisor_ssn), DEPARTMENT(Dname, Dno, Total_sal, Manager_ssn). Total_sal must always equal the sum of the salaries of the department's employees. Four events can change it: (1) a new employee is inserted, (2) a salary changes, (3) an employee changes department, (4) an employee is deleted. Oracle notation:

-- R1: insert
CREATE TRIGGER Total_sal1
AFTER INSERT ON EMPLOYEE
FOR EACH ROW
WHEN (NEW.Dno IS NOT NULL)
  UPDATE DEPARTMENT SET Total_sal = Total_sal + NEW.Salary WHERE Dno = NEW.Dno;

-- R2: salary change
CREATE TRIGGER Total_sal2
AFTER UPDATE OF Salary ON EMPLOYEE
FOR EACH ROW
WHEN (NEW.Dno IS NOT NULL)
  UPDATE DEPARTMENT SET Total_sal = Total_sal + NEW.Salary - OLD.Salary WHERE Dno = NEW.Dno;

-- R3: change of department (no condition: always run)
CREATE TRIGGER Total_sal3
AFTER UPDATE OF Dno ON EMPLOYEE
FOR EACH ROW
BEGIN
  UPDATE DEPARTMENT SET Total_sal = Total_sal + NEW.Salary WHERE Dno = NEW.Dno;   -- new dept
  UPDATE DEPARTMENT SET Total_sal = Total_sal - OLD.Salary WHERE Dno = OLD.Dno;   -- old dept
END;

-- R4: delete
CREATE TRIGGER Total_sal4
AFTER DELETE ON EMPLOYEE
FOR EACH ROW
WHEN (OLD.Dno IS NOT NULL)
  UPDATE DEPARTMENT SET Total_sal = Total_sal - OLD.Salary WHERE Dno = OLD.Dno;
-- R5: warn when an employee earns more than the supervisor
CREATE TRIGGER Inform_supervisor1
BEFORE INSERT OR UPDATE OF Salary, Supervisor_ssn ON EMPLOYEE
FOR EACH ROW
WHEN (NEW.Salary > (SELECT Salary FROM EMPLOYEE WHERE Ssn = NEW.Supervisor_ssn))
  inform_supervisor(NEW.Supervisor_ssn, NEW.Ssn);
  • The condition NEW.Dno IS NOT NULL avoids useless work when an employee has no department. R3 needs no condition and updates both the old and the new department.
  • General Oracle syntax: CREATE TRIGGER name {BEFORE | AFTER} events ON table [FOR EACH ROW [WHEN condition]] actions. SQL-99 standardises triggers.
2.36

Triggers in PostgreSQL (a trigger function plus a trigger)

In PostgreSQL the action is a trigger function, attached by CREATE TRIGGER:

CREATE FUNCTION audit_salary() RETURNS trigger AS $$
BEGIN
  IF NEW.salary <> OLD.salary THEN
    INSERT INTO salary_log(emp_id, old_salary, new_salary, changed_at)
    VALUES (OLD.emp_id, OLD.salary, NEW.salary, now());
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_audit_salary
AFTER UPDATE OF salary ON employee
FOR EACH ROW EXECUTE FUNCTION audit_salary();

DROP TRIGGER trg_audit_salary ON employee;
  • A BEFORE row trigger can change NEW or return NULL to cancel the operation. An AFTER trigger cannot change the row but can update other tables (audit trail).
  • Uses: audit logs, derived-value maintenance, enforcing rules CHECK cannot express, cascading changes. Cautions: hidden logic, performance cost, and triggers firing other triggers (chains).

Q1

Explain the phases of database design and the benefits of data modelling.

Show model answer

Design moves from requirement analysis to a conceptual schema (ER/EER, DBMS independent), then a logical schema (relational tables, keys, normalisation), then the physical schema (files, indexes), and finally implementation.

What is a weak entity type? How is it represented and mapped to a relation?

Show model answer

A weak entity type has no key of its own; its entities are identified by a partial key together with the primary key of an owner (identifying) entity through an identifying relationship; participation in it is total. Drawn as a double rectangle with a double diamond, and a dashed-underlined partial key. Example: DEPENDENT of EMPLOYEE.

Q6

Explain specialisation, generalisation, attribute inheritance and the constraints on specialisation.

Show model answer

Specialisation defines subclasses of a superclass by distinguishing characteristics (top-down); generalisation is the reverse (bottom-up: CAR and TRUCK to VEHICLE). A subclass inherits all attributes and relationships of its superclass and adds specific attributes.

Q7

Explain aggregation and categories (union types) in the EER model.

Show model answer

Aggregation allows a relationship set to take part in another relationship (a dashed box around it): "student works on project" is aggregated so that an evaluation or a guide can relate to the pair without redundancy. A category (union type) is a subclass whose members come from one of several superclasses of different types: OWNER of a vehicle is a PERSON, a BANK or a COMPANY, so OWNER ⊆ PERSON ∪ BANK ∪ COMPANY. A shared subclass, in contrast, is a subset of the intersection of its superclasses.

Q8

Describe the algorithm for mapping an ER schema to a relational schema.

Show model answer
  1. Regular entities: one relation each with simple attributes and a primary key.
  2. Weak entities: relation with owner's key as a foreign key; PK = owner key + partial key.
  3. 1:1: foreign key in the total-participation side (or merge, or a relationship relation).
  4. 1:N: foreign key of the 1-side in the N-side relation.
  5. M:N: new relation with both keys as foreign keys (PK = combination) + relationship attributes.
  6. Multivalued attributes: new relation (owner key + the attribute).
  7. n-ary relationships: new relation with all participating keys.
  8. Specialisation: options 8A to 8D.
  9. Categories: a relation with a surrogate key.
Summary: entity → relation; 1:N → foreign key; M:N and n-ary → relation with foreign keys; multivalued → separate relation.

A relation is a table (a set of tuples); a tuple is a row; an attribute is a column; a domain is the set of legal values for an attribute; degree is the number of attributes and cardinality the number of tuples.

Q12

Explain the different types of joins in relational algebra.

Show model answer

A join combines related tuples: R ⋈θ S = σθ(R × S). Equijoin uses only equality; natural join equates all common attributes and keeps them once. Outer joins keep unmatched tuples with NULLs: left (⟕), right (⟖), full (⟗). Semi-join returns the tuples of R having a match in S. An inner join loses dangling tuples; an outer join keeps them.

Q13

Explain the division operation with an example.

Show model answer

R ÷ S returns the values t of the attributes in R but not in S such that (t, s) ∈ R for every s ∈ S. Use it for "for all" queries. Example: takes(student, course) ÷ required(course) with required = {DB, OS, CN} gives the students who took all three. With Amit {DB, OS, CN}, Neha {DB, OS}, Raj {DB, OS, CN, AI} the result is {Amit, Raj}. In SQL it is written with a double NOT EXISTS.

WHERE filters rows before grouping and cannot use aggregates; HAVING filters groups after GROUP BY and can use aggregates. Logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

SELECT department, AVG(marks) FROM Students WHERE attendance >= 75 GROUP BY department HAVING AVG(marks) > 70 ORDER BY 2 DESC;

Q17

What is a view? State its advantages and limitations. When is a view updatable?

Show model answer

A view is a virtual table defined by a stored query; it holds no data of its own.

Show solution

  2. 55000 > ANY: TRUE. 55000 > ALL: greater than 50000, 40000 and 30000, so TRUE.

Trigger design

Design the triggers needed to keep DEPARTMENT.Total_sal equal to the sum of employee salaries. List the events, the condition and the action for each.

Show solution
  1. Event 1, INSERT on EMPLOYEE: condition NEW.Dno IS NOT NULL; action Total_sal = Total_sal + NEW.Salary for NEW.Dno.
  2. Event 2, UPDATE OF Salary: condition NEW.Dno IS NOT NULL; action Total_sal = Total_sal + NEW.Salary − OLD.Salary.
  3. Event 3, UPDATE OF Dno: no condition; add NEW.Salary to the new department and subtract OLD.Salary from the old one.
  4. Event 4, DELETE: condition OLD.Dno IS NOT NULL; action Total_sal = Total_sal − OLD.Salary.
  5. All four are AFTER, FOR EACH ROW triggers because they use NEW and OLD.
Four AFTER row-level triggers (insert, salary update, department update, delete).
